## 2026-06-11 · split UX·remote·sandbox·transport 판정과 2-pass 점검 착수

@claude (질문 6장에 대한 Joker 판정)

- Windows 전략: 1차 출시 게이트로 삼지 않음. ① 코어는 크로스 플랫폼하게 작성
  (CLI↔daemon이 Unix domain socket — Windows는 named pipe 매핑 필요),
  ② 1차 출시 = macOS/Linux + WSL2, ③ native Windows = 이슈로 열어 커뮤니티 기여
  영역으로(기여자 유입 미끼). Antigravity 등 adapter 후보 증가는 contract
  일반화(4-slot) 선행 판정을 강화.
- split UX 판정: "어떤 터미널이든 aiox가 split"은 문자 그대로는 불가 — 외부 제어
  표면이 없는 터미널이 존재(macOS Terminal.app, PowerShell 콘솔, IntelliJ,
  VSCode 터미널 패널). docker compose 모델 권고:
  - `aiox compose up` = agent 세션을 daemon 관리 detached로 기동(daemon 기보유).
  - `aiox attach <agent>` = 보편 표면 — 어떤 터미널에서든 동작. "어떤 터미널이든"
    요구는 split 제어가 아니라 attach 보편성으로 충족된다.
  - view driver(`--ui tmux|wt|iterm2|none`, 설정으로 기본값) = 자동 배치는
    제어 표면이 있는 멀티플렉서/터미널에만 driver로 제공.
  - 경고: detach+attach는 PTY 보유자가 필요 — 자체 PTY 호스팅(node-pty +
    scrollback + resize)은 "미니 tmux" 함정. Phase 1 = tmux를 detach
    백엔드로(mac/linux) + Windows는 wt driver/foreground.
  - detached agent의 1급 개념화는 모바일/remote 비전과 같은 아키텍처 결정.
- remote 3층 분해: L1 사내망 daemon federation(자연 확장, spec §8 location-ready가
  보험) / L2 모바일→로컬 데스크톱 agent(기쁜 카드 — Claude 모바일 앱이 remote MCP
  connector를 이미 지원하고 aiox는 MCP server 코드 기보유 → tailscale/Cloudflare
  Tunnel 뒤로 노출하면 신규 프로토콜 없이 동작. 데모·바이럴 가치 최대) /
  L3 외부 vendor agent(GitHub Copilot·브라우저 GPT — vendor 표면 의존, 가장
  불확실. Google A2A bridge와 같은 카테고리). 권고 순서: local 완성 → L2 → L1 → L3.
- sandbox 3층 정리: ① 실행 sandbox(agent가 돌리는 코드 격리)는 vendor CLI 자체
  보유 — aiox가 만들지 않는 층. ② capability 경계(어떤 agent가 어떤 스킬·MCP·지침을
  받나) = compose.yaml per-agent/공용 지정 = spec §7 capability projection.
  ③ 통신 경계(누가 누구에게) = route directed edge + remote 시 인증·암호화.
  재정의: aiox의 sandbox = "능력과 통신의 선언적 경계", compose.yaml이 선언 표면,
  daemon이 집행자.
- 점검 방식 제안: 2-pass — Pass A = 보안·로직 결함 사냥(읽기 전용 subagent),
  Pass B = 아키텍처·디자인 패턴 평가(방향 맥락을 보유한 main agent 직접 — subagent는
  목표 구조 맥락이 없어 일반론 위험). 산출물 = `docs/reports/` 통합 report 1개.
  수정 실행은 범위 밖(발견·권고까지).

@claude (transport 권고·설정 파일 정리·점검 착수)

- transport 현황 실측: CLI↔daemon = Unix domain socket + newline-delimited JSON
  envelope(`src/daemon/socket-transport.ts`). Windows named pipe 전환 지점이 코드
  주석에 이미 명시돼 있음(deferred, history/57 참조). `src/config/paths.ts`의
  profile namespace(dev/build/release) 설계는 양호.
- transport 권고 — 원칙: "거리마다 다른 transport, 같은 protocol(envelope)".
  ① 로컬 제어 평면(CLI↔daemon): UDS 유지 + Windows는 named pipe(`\\.\pipe\…`).
  Node `net` 모듈이 동일 API로 지원 — `getSocketPath()` 분기만으로 도달. TCP
  loopback은 차선(포트 충돌, 로컬 다중 사용자 접근 제어 약함, Windows 방화벽 팝업).
  ② agent ingress: vendor 표면이 결정(MCP stdio/HTTP loopback/WS) — 현행 유지.
  ③ daemon↔daemon(L1 사내망/L2 remote): WebSocket over HTTPS + token/mTLS —
  `ws` 의존성 기보유, tunnel(tailscale/cloudflared)·프록시 친화, 양방향 push.
  ④ 자체 TCP 바이너리 프로토콜 발명 금지. envelope canonical object화(기존 spec
  방향)가 transport 독립의 전제.
- 설정 파일 책임 분리 제안: user-level `~/.aiox/config.json`(view driver·터미널
  선호·기본 profile — 첫 실행 onboarding이 생성) vs project-level
  `compose.yaml`(topology·capability — repo 커밋 대상). npm postinstall
  interactive는 안티패턴(CI·비대화형 설치에서 깨짐) → 첫 실행 시 onboarding이
  정석. 터미널 자동 감지는 env(`$TERM_PROGRAM`, `$TMUX`, `$WT_SESSION`)로
  저비용 — "맞혀놓고 확인만 받는" onboarding 가능.
- src 규모 실측: 총 11,236줄. 최대 파일 `src/daemon/state.ts` 2,218줄(전체 ~20%)
  — Pass B DX 평가의 1차 증거.
- Pass A subagent(읽기 전용, 공개 전 부끄러운 것 우선) 기동.
