## 2026-06-10 · A2A 응답 대기 polling 원인

@user

- Codex가 Claude에게 `aiox_send_message`를 보낸 뒤 응답을 기다리려고 같은 turn에서
  `exec_command sleep`을 반복했다.
- 이 동작은 정상 workflow가 아니라 원인을 찾아야 할 문제다.
- envelope post-MVP plan에 후속 요구사항을 기록하고, envelope만으로 해결되지 않으면
  MCP instruction 보완도 검토한다.

@codex

- `createSendMessageHandler`는 daemon의 `receiveCodexMessage` 결과를 받은 뒤
  `sent <message_id>`와 dispatch summary를 즉시 반환한다. 상대 agent의 작업 완료나
  reply 도착을 기다리는 API가 아니다.
- daemon의 `receiveCodexMessage`는 message 저장과 대상 delivery dispatch를 수행한다.
  dispatch success는 대상 runtime에 메시지를 주입한 상태이며, 대상 agent의 답변 완료를
  뜻하지 않는다.
- Claude의 실제 답변은 별도 message로 돌아오며, Codex target에는
  `<aiox-channel ...>` 입력을 `turn/start`로 주입해 후속 turn을 시작한다.
- 현재 MCP instruction에는 send 결과가 접수 확인이라는 설명과, 응답을 기다리기 위해
  `sleep` 또는 polling을 하지 말아야 한다는 행동 계약이 없다.

확인된 원인

- send 접수 완료와 원격 응답 완료가 서로 다른 비동기 단계인데 tool result와 instruction이
  이 경계를 agent에게 충분히 설명하지 않는다.
- Codex가 같은 turn 안에서 사용자 요청을 끝까지 처리하려다, 제공되지 않은 응답 대기
  수단을 shell `sleep` polling으로 임의 대체했다.

아직 검증할 점

- 현재 Codex turn이 종료되지 않은 상태에서도 상대 reply의 inbound `turn/start`가 정상적으로
  별도 turn을 재개하는지 확인해야 한다.
- runtime이 이미 turn 진행 중인 경우 inbound injection을 queue, reject, defer 중 어떻게
  처리하는지 확인해야 한다.
- instruction만으로 polling을 막을 수 있는지, send tool 결과나 daemon delivery lifecycle에
  명시적인 pending/reply event 계약이 필요한지 검증해야 한다.

작업 결과

- `plan/post-mvp/envelope-metadata.plan.md`에 send 접수와 원격 응답 완료의 구분,
  `sleep`/polling 금지, inbound envelope turn 재개, 필요 시 MCP instruction fallback과
  회귀 테스트 요구사항을 추가했다.
