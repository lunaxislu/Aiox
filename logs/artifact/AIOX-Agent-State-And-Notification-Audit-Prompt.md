AIOX의 정책과 판정 기준:

- Agent의 작업·명시적 사용자 대기·종료·실패·복구를 실제 관측으로 판단해 aiox-preparing / idle /
  working / awaiting-user / failed로 표시한다.
- 비동기 질문 생성만으로 awaiting-user로 바꾸거나, 개별 도구 오류를 전체 failed로 판단하지 않는
  다.
- Agent의 현재 상태와 개별 메시지의 처리 결과는 분리한다. busy 중 받은 메시지도 수락과 처리 완료
  를 구분해 결과를 귀속한다.
- interrupted는 다른 작업·대기가 없으면 idle로 표시하고 자동 알림은 보내지 않는다. 늦은 도구 완료
  로 중단 결과를 뒤집지 않는다.
- failed는 최종 응답·연결 실패 근거로 판단하고, 실제 새 작업 시작·연결 복구에 따라 해제한다. 현재
  상태가 복구돼도 기존 메시지 결과는 보존한다.
- 전송 시점에 단방향이면 completed·failed를, 양방향이면 failed만 원 발신 Agent에게 시스템 알림으
  로 전달한다. 알림은 추가 알림을 만들지 않는다.

대상 Agent: [Agent 이름]
상황: [이미지 또는 한 줄 설명]

이 상황의 이벤트를 현재 AIOX가 관찰해서 위 기준대로 상태와 이유를 보여주고 있느냐?
AIOX send로 받은 메시지를 처리하는 상황이라면, busy 중 수신도 포함해 해당 메시지의 결과를 추적하
고 위 정책대로 시스템 알림을 보내고 있느냐?
현재 되는 것·안 되는 것·미확인인 것을 근거와 함께 설명해줘.

# AIOX Agent 상태 추적·메시지 결과·자동 알림 검증 프롬프트

너는 AIOX의 Agent 상태 관측과 메시지 처리 결과·자동 알림 흐름을 검토하는 agent다.
먼저 아래 정책과 판정 기준을 이해하고, 대상 vendor의 Agent가 발생시키는 이벤트가 실제로
AIOX의 상태 표시와 메시지 결과·알림까지 연결되는지 확인하라.
특정 이벤트 이름이나 중단 사례 하나에 한정하지 말고 같은 기준을 각 vendor에 적용하라.

이 문서는 조사·검증을 요청하는 프롬프트이며 제품 명세를 대체하지 않는다.
로그는 기록하지 않는다. 별도 구현 지시가 없다면 코드·정책을 변경하지 말고 확인 결과와
부족한 연결을 보고하라. 사용자 실행을 중단하거나 설정·route를 바꾸는 실험은 임의로 하지 않는다.

## 1. AIOX의 상태 추적 정책과 판정 기준

AIOX는 vendor의 관측 가능한 이벤트와 실행·연결 정보를 근거로 Agent의 현재 상태를 추적한다.
모델의 자기 선언이나 화면 문구만으로 상태를 확정하지 않는다. 이벤트 수신 자체를 상태 추적의
완료로 간주하지 않고, 해석·귀속·상태 갱신·소비자 표시까지 확인한다.

### Agent의 현재 상태

현재 상태는 다음 다섯 가지 중 하나로 표현한다. 순서대로 통과하는 다섯 단계가 아니다.

| status           | 판정 기준                                                                      |
| ---------------- | ------------------------------------------------------------------------------ |
| `aiox-preparing` | AIOX 실행·연결·현재 대화의 준비가 아직 완료되지 않음                           |
| `idle`           | 준비된 실행에 현재 진행 중인 작업·미해결 대기·유효한 실패 상태가 없음          |
| `working`        | 현재 작업이 진행 중이며 추론·도구 실행 등의 차이는 이유로 설명                 |
| `awaiting-user`  | 명시적으로 관측된 사용자 입력·승인 대기가 해소되지 않음                        |
| `failed`         | 최종 응답 실패 또는 AIOX 연결 실패가 관측됐으며 해당 실패가 아직 해소되지 않음 |

`status_reason`은 현재 상태의 이유다. 확인되지 않은 이유를 만들지 않고, 이유가 없으면
`null`로 표시하며 이전 이유를 남기지 않는다. Web·MCP `agents_list`는 같은 상태와 이유를
소비해야 하며 CLI의 상태 표시도 같은 관측과 일치해야 한다.

상태 판정에서는 다음을 확인한다.

- 실행 준비, 작업 시작·진행·종료, 입력·승인 대기의 생성·해소, 실패·복구의 근거를 구분한다.
- 여러 작업·대기가 겹칠 때 어느 상태가 우선하는지 owner 계약과 구현을 대조한다.
  한 요청의 해소로 다른 미해결 대기를 지우지 않는다.
- 비동기 질문이 생성됐다는 사실만으로 작업이 멈췄다고 판단하지 않는다.
  명시적 대기 없이 계속 실행하면 `working`이며, 질문 UI의 존재와 Agent 활동 상태는 구분한다.
- Runtime·대화·작업·요청 식별자로 이벤트를 귀속한다. 늦거나 중복된 이벤트, 다른 대화의
  이벤트가 현재 상태를 덮거나 끝난 작업·대기를 되살리지 않아야 한다.
- 실패와 복구를 각각 실제 근거로 판정한다. 일시적인 도구 오류·재시도를 최종 실패로
  단정하지 않으며 관측 누락을 완료·실패로 추측하지 않는다.
- 현재 상태, 전송 가능 여부, 개별 메시지 결과는 별개다. `failed`라는 이유만으로 모든
  입력이 불가능하다고 판단하지 않는다. 종료한 Agent는 별도 여섯 번째 상태를 만들지 않고
  Agent 목록에서 제거하는 계약을 확인한다.

### 개별 메시지의 처리 결과

AIOX `send`의 수락과 수신 Agent의 실제 처리 종료를 구분한다.
`accepted: true`, 입력 주입 성공, 화면 출력, Agent의 현재 `idle`만으로 메시지 처리가
완료됐다고 판정하지 않는다.

수신 Agent의 실행·대화·작업과 해당 메시지의 대상별 delivery를 연결하고, 그 처리 결과를
`completed`, `failed`, `interrupted`로 추적한다. `completed`는 연결된 응답 처리가 끝났다는
뜻이며 산출물의 정확성이나 업무 성공을 보장하지 않는다.

하나의 작업에 여러 입력이 합쳐지거나 여러 대상에게 전송되는 경우에도 결과의 귀속을
보존해야 한다. Agent가 다음 작업을 수행해 `working`이어도 이전 메시지는 `completed`일 수 있다.

### 처리 결과에 따른 자동 알림

알림 여부는 대상별로 전송 시점에 확인한 역방향 전송 가능 여부와 해당 delivery의 결과로
판정한다. 이후 route 변경으로 이미 수락한 요청의 알림 정책을 바꾸지 않는다.

| 전송 시점의 관계 | `completed`            | `failed`               | `interrupted` |
| ---------------- | ---------------------- | ---------------------- | ------------- |
| A→B 단방향       | daemon이 A에 완료 알림 | daemon이 A에 실패 알림 | 알림 없음     |
| A↔B 양방향       | 자동 알림 없음         | daemon이 A에 실패 알림 | 알림 없음     |

`interrupted`를 반드시 사용자의 직접 중단으로 해석하지 않는다. 이 알림 정책에는 세부적인
중단 원인 분류가 필요하지 않으며, 실제 처리 결과가 `interrupted`인지가 기준이다.
다른 결과도 화면 표현이 아니라 귀속 가능한 종료 근거로 판정한다.

알림은 AIOX daemon이 원 발신 Agent의 vendor 입력 경로로 전달한다. Web에 기록하거나
알림 객체를 생성한 것만으로 발신 Agent에게 전달됐다고 보고하지 않는다.
역방향 Agent 전송 권한이 없어도 daemon 알림은 전달하며, 알림 자체가 다시 자동 알림을
유발하지 않아야 한다. 종료한 발신자 대신 같은 이름의 새 Runtime에 알림을 보내지 않는다.

## 2. 대상 Agent의 이벤트를 위 정책에 연결하라

먼저 조사 대상 vendor·버전과 관측 경로를 밝히고 다음 두 흐름을 실제 코드에서 추적하라.

```text
vendor 이벤트·실행/연결 관측
  → adapter/relay 수신 → Runtime·대화·작업·요청 귀속
  → 현재 status/status_reason 갱신 → Web·MCP·CLI 표시

AIOX send → 대상별 수락·delivery 연결 → vendor의 처리 결과 관측
  → 해당 delivery 결과 반영 → 전송 시점 관계에 따른 알림 판정
  → 원 발신 Agent의 vendor 입력 경로로 전달
```

대상의 작업 시작·진행·종료, 도구 실행, 사용자 입력·승인, 비동기 질문, 중단, 오류·연결 손실,
복구·대화 전환 이벤트를 조사하라. vendor마다 이벤트 이름과 수단이 달라도 공통 정책에
어떻게 대응하는지 설명하고, 같은 이벤트 구조를 억지로 요구하지 않는다.

다음 항목을 구분해서 대조표를 작성하라.

| 사용자 상황 | 실제 관측 이벤트·필드 | 현재 상태·이유와 해소 조건 | delivery 결과 | 자동 알림 | 근거·미확인 범위 |
| ----------- | --------------------- | -------------------------- | ------------- | --------- | ---------------- |

각 행에서 이벤트를 제공하지 않는 경우, AIOX가 수신하지 않는 경우, 수신하지만 해석하지 않는
경우, 내부 반영은 되지만 소비자에게 전달하지 않는 경우를 구분하라.
생성 이벤트만으로 미응답·해소 여부까지 추적한다고 설명하지 않는다.
화면의 “중단”, “질문 대기” 같은 문구를 특정 프로토콜 이벤트와 확인 없이 동일시하지 않는다.

정책이 실제로 연결돼 있는지를 중심으로 보고하라.
