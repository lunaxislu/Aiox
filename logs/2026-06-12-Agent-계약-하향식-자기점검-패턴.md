## 2026-06-12 · Agent 계약 하향식 자기점검 패턴

@user

- root `AGENTS.md`, 하위 scope의 `AGENTS.md`와 portable skill 사이에 반복해서 적용할
  수 있는 일반 패턴을 로그로 남기도록 요청했다.
- 나중에 이 패턴을 별도 skill과 자기점검 loop로 만들어 agent 계약의 중복, 누락과
  잘못된 책임 배치를 점검하고 싶다.
- Codex의 독립 의견도 함께 기록해도 된다고 했다.

@codex

### 사용자에게서 확인된 설계 성향

- 먼저 각 문서나 도구가 무엇을 소유하는지 책임표를 만들고, 범용 계약에서 repo 전용
  계약으로 순서대로 정리한다.
- portable skill에는 여러 프로젝트에 적용할 수 있는 행동·형식·상태·절차를 둔다.
  특정 폴더명, plan 구조, repo taxonomy와 현재 작업은 전제하지 않는다.
- root `AGENTS.md`에는 이 repo의 진입점, 현재 작업 선택, 저장 위치와 여러 작업 기록
  도구의 연결 방식을 둔다. portable 절차를 복사하지 않고 어떤 계약을 어디에서
  적용할지만 정한다.
- subtree `AGENTS.md`에는 해당 디렉터리에서만 필요한 추가 제약과 closeout 확인을
  둔다. 상위 계약이나 portable skill을 다시 설명하지 않는다.
- architecture·taxonomy 문서는 영역별 정보 owner와 질문별 authority를 정의한다.
  agent가 언제 어떤 명령을 실행하는지 같은 운영 절차는 정의하지 않는다.
- 책임은 하향식으로 위임한다. 상위 계약은 하위 계약과 skill의 위치·역할을 가리키고,
  하위 계약은 필요한 owner map을 참조한다. 하위 문서가 상위의 현재 작업 규칙을
  역으로 정의하거나 taxonomy가 skill lifecycle을 정의하지 않는다.
- 문구가 애매하면 실제 agent가 어떤 파일이나 개념으로 해석할지 확인한다. 예를 들어
  일반명 `plan`만 쓰지 않고 정식 위치 `plans/`의 plan 문서라고 명시해 legacy
  `plan/`과 구분한다.
- 자동화는 의미 판단을 대체하지 않는다. agent가 의미를 판단하고 script는 위치,
  형식, 원자적 변경과 구조 검증만 담당한다.
- 자동화 도입 전에는 사례와 실패 조건을 먼저 검토하고 dry-run 결과를 수동 기대
  결과와 비교한다. 기존 수동 방법은 검증이 끝날 때까지 fallback으로 유지한다.
- token 절감만으로 도구를 추가하지 않는다. 정확성, 누락 방지, 원자성과 반복되는
  구조 편집 비용을 함께 근거로 삼는다.

### 하향식 계약 모델

| 계층                  | 소유할 내용                                                   | 소유하지 않을 내용                               |
| --------------------- | ------------------------------------------------------------- | ------------------------------------------------ |
| architecture·taxonomy | 영역별 정보 owner, scoped authority, conflict 규칙            | agent 실행 절차, 현재 작업 선택, skill lifecycle |
| root `AGENTS.md`      | repo 진입, 현재 작업 선택, 경로·도구·plan·log 연결, 전역 제약 | portable 기록 형식과 세부 명령 절차              |
| subtree `AGENTS.md`   | 해당 subtree의 추가 제약, owner handoff와 closeout 확인       | 상위 계약 복사, 일반 lifecycle·형식              |
| portable skill        | trigger, 일반 행동·형식·상태·재개·점검·종료 절차              | 특정 repo 폴더·taxonomy·현재 plan 전제           |
| deterministic script  | 생성·검색·검사·상태 변경 등 구조적 조작                       | 완료·취소·owner 선택 같은 의미 판단              |

적용 순서는 현재 파일이 위치한 scope의 상위 `AGENTS.md`에서 하위 `AGENTS.md`로
제약을 좁힌 뒤, 작업 의도에 맞는 portable skill 절차를 적용하고, skill이 지정한
구조 조작만 script에 맡기는 방식이 자연스럽다. taxonomy는 이 실행 순서의 한 단계가
아니라 owner 판단에 사용하는 별도 기준이다.

### 자기점검 loop 후보

1. 점검할 변경과 scope를 명시한다. 전체 repo를 무조건 읽지 않는다.
2. 관련 root·subtree `AGENTS.md`, 발동된 skill과 owner 문서의 필요한 구간만 읽는다.
3. 각 문장을 `taxonomy owner`, `root repo contract`, `subtree contract`, `portable
skill`, `deterministic script`, `중복·불필요` 중 하나로 분류한다.
4. 같은 규칙이 여러 계층에 있으면 실제 owner를 하나 정하고 다른 위치는 참조만
   남기는 안을 만든다.
5. 특정 repo 이름이나 경로를 제거했을 때도 성립해야 portable한지 검사한다.
6. 상위가 하위를 위임하는지, 하위나 taxonomy가 상위의 현재 작업을 역으로 정의하는지
   확인해 순환·역방향 의존을 찾는다.
7. 문구가 agent에게 실제 경로·대상·우선순위를 충분히 특정하는지 확인한다.
8. 자동화 제안은 의미 판단과 구조 조작을 분리하고, dry-run·실패 시 원본 무변경·
   수동 fallback·회귀 테스트가 있는지 확인한다.
9. 결과를 `유지`, `이동`, `삭제`, `참조로 축약`, `사용자 판단 필요`로 보고한다.
10. 점검 단계에서는 파일을 자동 수정하지 않는다. 사용자가 범위를 승인한 뒤 수정하고
    diff와 실제 동작을 다시 검증한다.

### 자기점검 질문

- 이 문장은 여러 프로젝트에 그대로 적용되는가, 이 repo에서만 성립하는가?
- 특정 path·taxonomy·plan 구조가 없으면 규칙이 깨지는가?
- 상위 문서가 하위 문서나 skill에 위임하면 충분한 내용을 다시 복사하고 있지 않은가?
- subtree에만 필요한 추가 제약인가, portable skill의 일반 규칙인가?
- 정보의 owner를 정의하는 문장인가, agent의 실행 방법을 정하는 문장인가?
- 현재 상태와 다음 행동을 durable owner나 frontmatter에 잘못 넣고 있지 않은가?
- 자동화가 agent의 의미 판단을 몰래 수행하거나 기존 workflow를 바꾸지 않는가?
- 실패할 때 원본을 보존하고 사용자가 결과를 preview할 수 있는가?
- 명칭이 실제 경로와 일치하며 legacy 구조와 혼동되지 않는가?
- 이 규칙을 제거하면 다음 agent가 책임, 제약, 현재 상태나 다음 행동을 잘못 이해할
  가능성이 실제로 있는가?

### Skill화에 대한 Codex 의견

- 이 패턴은 한 repo의 임시 규칙보다 여러 agent 계약 검토에 재사용할 가치가 있어
  별도 review skill 후보가 될 수 있다.
- 첫 버전은 read-only 점검 skill이 적절하다. 파일을 읽고 책임 매트릭스, 의존 방향,
  중복·누락과 수정 후보를 보고하되 자동 이동·삭제·수정은 하지 않는다.
- skill trigger는 `AGENTS.md 책임 점검`, `root와 subtree 계약 검토`, `skill과 agent
지침 중복 확인`, `하향식 계약 점검`처럼 명시적인 요청으로 제한하는 편이 좋다.
- 매 작업 후 자동 실행하는 loop는 context 비용이 크다. 계약 파일이나 skill을
  변경했을 때, 새 subtree 계약을 추가했을 때, 또는 사용자가 명시적으로 요청했을
  때만 좁은 범위로 실행하는 것이 적절하다.
- script로 기계 검사할 수 있는 부분은 broken relative link, 존재하지 않는 path,
  동일 문구 반복, frontmatter·heading 같은 구조 사실이다. portable 여부, 책임 owner,
  중복의 정당성, 역방향 의미 의존은 agent가 판정해야 한다.
- 실제 오탐·누락 사례가 쌓이기 전에는 고정 점수나 강제 schema를 만들지 않는다.
  우선 checklist와 보고 형식을 검증한 뒤 필요한 구조 검사만 점진적으로 추가한다.

### opinion.md에서 확인한 사고·검토 습관

- 문장이 얼핏 맞아 보여도 해당 위치의 책임과 맞는지 다시 묻는다. 내용의 옳고 그름과
  그 내용을 소유할 문서가 맞는지를 별도 문제로 본다.
- portable 규칙과 repo 전용 규칙이 한 문단에 섞여 있다고 느끼면 즉시 분리를
  의심한다. 어느 한쪽으로 성급히 옮기기보다 각 문장의 portable 범위를 확인한다.
- 추상적인 용어를 그대로 채택하지 않는다. `증류`, `책임 문서`, `plan`처럼 여러
  의미로 읽힐 수 있는 표현은 실제 행위·owner·경로가 무엇인지 확인하고 더 구체적인
  이름을 찾는다.
- 먼저 자신의 가설을 제시하지만 확정하지 않고 agent의 반대 근거와 trade-off를
  요구한다. `logs/AGENTS.md`에 점검 규칙을 중복해도 되는지처럼 의도와 비용을 함께
  검토한다.
- 누수 방지를 중요하게 본다. 미완료 행동, owner 반영 누락과 다음 세션이 재개할
  context가 사라지는 문제를 구조적으로 예방하려 한다.
- 동시에 점검 비용도 경계한다. 로그를 쓸 때마다 전체 파일을 다시 읽는 식의 안전
  장치는 context와 token 비용을 키울 수 있으므로 시점·범위·깊이 제한을 요구한다.
- 예시를 통해 추상 계약을 검증한다. 전체 완료, 부분 완료와 범위 확장처럼 실제
  상태 전이를 대입해 문구나 자동화가 원하는 workflow를 보존하는지 확인한다.
- 자동화를 선호하지만 기존 수동 흐름과 같은 결과가 나오는지 먼저 확인한다. 오류가
  권위 기록을 손상할 수 있으면 dry-run, fixture 비교와 수동 fallback을 요구한다.
- 분류 경계를 중요하게 본다. 논의가 기존 로그 두 개에 걸쳐 보여도 독립적으로
  재개·종료할 수 있는 수명인지 확인한 뒤 새 로그 여부를 결정하려 한다.
- 다음 세션에서 context가 깨끗해도 질문이 누락되지 않도록, 미결 질문 전체를 먼저
  기록하고 우선순위를 명시하는 방식을 선호한다.
- 일반화를 원하지만 너무 일찍 강제 schema나 자동 판단으로 만들지는 않는다. 반복
  사례와 검증 결과가 생긴 뒤 skill·script·자가점검 loop로 승격하려 한다.

# 결론

  - Promotion rule: 반복 판단은 example이 아니라 rules 문서로 승격한다.

### 일반화 요청 프롬프트

```text
특정 사례를 처리하는 답변으로 끝내지 말고, agent들이 같은 구조 판단을 하도록 일반화해줘.

목표:
- 특정 A -> B -> C 사례에만 맞는 규칙을 만들지 말 것.
- 이 사례에서 반복되는 구조 identity, decision point, invariant를 추출할 것.
- 어느 로그에서 새 로그를 만들든 적용되는 일반 규칙으로 재작성할 것.

작성 방식:
1. Scope를 먼저 정의한다.
   - 이 규칙이 어떤 상황에 적용되는지 쓴다.
   - 예: 현재 작업 중 새 로그를 만들 때, 연결 방식(parent/child, follow-up, transfer, supersede)을 정하는 규칙.

2. Identity rule을 정의한다.
   - 각 구조가 무엇을 의미하는지 identity 기준으로 쓴다.
   - 예: child log의 parent는 “그 child 결과를 소비해야 하는 Work Item”이다.
   - 생성 위치, 대화 순서, pointer chain 모양만으로 parent를 정하지 않는다.

3. Decision table을 만든다.
   - 판단 질문은 “새 로그의 결과를 누가 소비하는가?”로 시작한다.
   - 현재 로그의 Work Item이 소비하면 current log child.
   - known parent의 Work Item이 소비하면 parent Work Item을 새 로그로 재배선.
   - 아무 Work Item도 기다리지 않으면 independent follow-up.
   - 소비 Work Item이 모호하면 후보와 근거를 제시하고 사용자에게 묻는다.

4. Output invariants를 둔다.
   - parent pointer는 frontmatter가 아니라 parent Work Item과 child 첫 기록 블록에 둔다.
   - parent pointer는 정확히 하나의 소비 Work Item을 가리킨다.
   - next pointer는 현재 로그 안의 재개 지점이지 parent/child 관계가 아니다.
   - pointer chain만으로 의존성, 소유권 이전, 복귀 의무를 추론하지 않는다.

5. Negative rules를 둔다.
   - A -> B -> C 같은 chain 사례를 rule의 전제로 만들지 않는다.
   - 자동 역검색, 전체 open 로그 sweep, 양방향 동기화, 순환 pointer를 만들지 않는다.
   - example.md에만 핵심 판단을 두지 않는다.

6. Examples는 decision table을 검증하는 보조 사례로만 둔다.
   - A -> B -> C 예시는 일반 규칙의 한 사례로 작성한다.
   - 예시가 규칙을 대체하지 않게 한다.

7. Harness 후보를 만든다.
   - fresh agent가 이 규칙만 읽고 같은 parent/next pointer/status 판단을 내리는지 확인할 scenario를 제안한다.
   - 실패할 것 같은 ambiguity도 적는다.

답변할 때는 먼저 “이 사례에서 일반화해야 할 구조가 무엇인지”를 말하고,
그 다음 “rules에 들어갈 문장”, “examples에 들어갈 보조 사례”, “harness 후보”로 나눠서 제안해줘.
```

### 핵심 문장

> 이 사례를 해결하지 말고, 이 사례가 드러낸 구조 판단 규칙을 일반화해줘.

### 향후 자기점검 질문 보강

- 지금 답변이 특정 사례에 맞춘 patch인가, 아니면 그 사례가 드러낸 구조 규칙을 추출했는가?
- identity rule, decision table, output invariant, negative rule, ambiguity rule이 모두 있는가?
- 예시가 규칙을 대체하고 있지 않은가?
- 특정 chain 이름이나 사례 모양이 rule의 전제 조건으로 굳어지지 않았는가?
- 여러 agent가 같은 구조 전이(parent 선택, next pointer, status)를 낼 수 있는가?
- fresh-agent harness 없이 "명확하다"고 가정하고 있지 않은가?
