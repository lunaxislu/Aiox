# Log Skill 개선

## 기록 계약

이 로그는 실행 작업 추적이 아니라 log skill 개선 토론의 검토·제안·수렴·반영·리뷰 기록이다.
사용자 지시에 따라 Work Item과 W-id를 만들지 않는다. 후속 실행 항목이 생기면 이 로그 안에서
W-id를 만들지 않고 별도 작업 로그나 owner 문서 검토로 분리한다.

## 2026-07-08 · 초기 리뷰 수렴

Claude가 log skill 문서군을 검토했고, Codex는 제안을 사실로 받아들이지 않고 파일·anchor·도구
help·테스트 표면을 대조했다.

확인한 사실:
- `project-setup.md` 예시 A는 예약 slot(`### Return Target`, `### {Global}`) 상시 생성 계약과
  맞지 않았다.
- `scripts/package-log`가 존재하고 예시에서 쓰이지만, 당시 SKILL 도구 절과 package 계약의 owner
  표면에는 충분히 복원되지 않았다.
- SKILL description의 "로그 점검" trigger가 `loop-rules.md#audit`로 명시 라우팅되지 않았다.
- Route / Contract Gate 일부 종결 분기가 다음 착지 행동을 명시하지 않아 독자가 추론해야 했다.
- `maintenance.md`에는 유지보수 loop의 back-edge는 있었지만 fail 착지, 종료 조건, guard가 충분히
  닫히지 않은 부분이 있었다.

수렴한 판단:
- 구조 전반의 owner 분리는 건강하므로 새 reference를 만들지 않는다.
- 실질 이슈는 stale 예시, package helper owner 부재, audit routing, gate 착지, maintenance loop
  well-formedness를 국소적으로 보수하는 것이다.

반영:
- `project-setup.md` 예시 A에 예약 slot을 맞췄다.
- `SKILL.md`에 audit routing, package-log helper 표면, Return Target 관련 생성 표면을 보강했다.
- `quick-flow.md`와 gate 문구의 착지점을 정리했다.
- `maintenance.md`에 유지보수 loop guard, 종료 조건, fail 착지, 개선 후보와 follow-up 처리 절을
  정리했다.

## 2026-07-08 · package-log repo 경계 위반

후속 리뷰에서 `scripts/package-log`가 repo 전용 integration locator를 기본 출력에 하드코딩한다는
문제가 제기됐다.

확인한 사실:
- `controlling new` 출력에 `logs/AGENTS.md#Package Log Repository Integration`이 기본으로 들어갔다.
- package portable 계약은 repo·harness 전용 mapping을 project integration owner로 분리한다.

수렴한 판단:
- helper가 공식 도구 표면으로 문서화된 이상, repo 전용 locator 기본 출력은 portable log skill
  경계 위반이다.
- 기본은 미출력으로 두고, 필요한 project integration ref는 flag나 env로 주입하는 편이 owner 경계에
  맞다.

반영:
- `scripts/package-log`에서 하드코딩된 repo integration ref를 제거했다.
- `--integration <project-integration-ref>`와 `PACKAGE_LOG_INTEGRATION_REF` 주입 경로를 추가했다.
- 관련 package-log 테스트를 갱신해 기본 미출력과 명시 주입을 검증했다.

## 2026-07-08 · Base/Package 도구 사용 read path 검토

사용자가 `scripts/log`와 `scripts/package-log`를 실제로 적절히 사용하도록 문서가 이끄는지,
Base log와 Package log 양쪽을 함께 검토하라고 요청했다.

확인한 사실:
- Base 쪽은 `SKILL.md ## 도구`, `base-log-examples.md`, `scripts/log --help`, `loop-rules.md`의
  lint boundary로 복원 경로가 이미 닫혀 있었다.
- Package 쪽은 `package-log.md`에 helper locator가 없었고, `package-log-examples.md`의 direct-start
  예시는 생산 행위를 scope로 두면서 결과 markdown만 보여줘 수동 작성 모델로 읽힐 수 있었다.
- `Package Reconcile`은 helper가 직접 지원하는 표면이 아니며, helper는 생성·등록·점검 표면을
  지원한다.

수렴한 판단:
- 새 `tool-usage.md` 같은 구조는 필요 없다.
- SKILL.md에 Base/Package overlay map을 추가하지 않는다. 기존 작업 루프 서두와 package-local
  단락으로 복원 가능하고, 새 map은 phase mapping 사본을 늘려 drift 위험을 만든다.
- loop-rules.md에 mutation 지점별 locator를 추가하지 않는다. Base는 이미 복원되고, per-mutation
  locator는 global tool 규율의 중복 재선언이 된다.
- Package 쪽 helper anchor 부재와 direct-start 예시는 같은 우선순위 묶음으로 고친다.

반영:
- `package-log.md`의 State Ownership / Task Record Contract에 `task new`와 `index add` read path를
  추가했다.
- `package-log.md`의 Fixed Package Skeleton에 `controlling new`와 `controlling detach` read path를
  추가했다.
- `package-log.md`의 Package Closeout / Registry Integrity Check에 `package-log check` read path와
  의미 판정 owner 분리를 추가했다.
- `package-log-examples.md` 공통 읽는 법에 helper command syntax owner가 `../scripts/package-log
  --help`임을 추가했다.
- direct-start 예시에 helper-first `controlling new` 명령 block을 추가했다.

## 2026-07-08 · 수동 편집 경계 재문장화

도구가 지원하지 않는 변경과 수동 편집 허용·보고 조건 사이에 내부 긴장이 있다는 리뷰가 있었다.

확인한 사실:
- 기존 문구는 "사용자가 수동 편집을 지시한 경우에만"이라는 금지형 문장과, 사용자 지시 없이 수동
  편집한 구조 변경의 사후 보고 문장이 함께 있어 두 독해를 만들 수 있었다.
- Package Evidence, Scope 같은 surface 내부 내용은 helper가 지원하지 않지만, Required Context
  bullet은 `log context add/set/delete`가 지원한다.

수렴한 판단:
- 도구가 지원하는 구조 변경은 tool-first가 맞다.
- 도구가 지원하지 않는 구조 변경은 필요한 경우 수동 편집하고 사후 범위·이유를 보고한다.
- Return Target consume/snapshot 변경, `[↓]` 취소·이관·남은 행동 재구성, 파괴적·migration 이동은
  별도 carve-out으로 사용자 사전 확인을 유지한다.

반영:
- `SKILL.md ## 도구`에서 구조 변경 외연을 재문장화했다.
- 후속 리뷰의 지적을 받아, 도구 대상 구조 변경을 "state machine, 재개·복귀 관계, section/block
  골격 변경 또는 `--help`에 명령이 있는 표면 갱신"으로 정리했다.
- carve-out은 "두 도구의 `--help`에 해당 명령이 없는 기존 표면 안의 내부 내용 갱신"으로 좁혔다.

## 2026-07-08 · 예시와 helper 출력 정합 후속

direct-start 예시에 helper 명령을 추가한 뒤, raw skeleton 출력과 bootstrap 후 accepted state의
관계가 오독될 수 있다는 리뷰가 있었다.

확인한 사실:
- `controlling new` raw skeleton은 `Task Index` 아래 `Stable package key` line을 생성한다.
- `package-log check`는 `Stable package key` 선언 부재를 error로 판정한다.
- direct-start 예시는 "결과 markdown 핵심"으로 bootstrap 후 채워진 상태를 보여주며, raw 출력의
  모든 line을 복제하지 않는다.

수렴한 판단:
- 예시는 raw 출력 전체가 아니라 accepted state의 핵심 모양을 보여주는 것이 맞다.
- 다만 raw skeleton의 필수 line을 삭제해도 된다는 신호를 주면 check와 충돌하므로 보존 조건을
  명시한다.

반영:
- direct-start 예시 설명에 "raw skeleton 출력이 아니라 bootstrap 내용을 채운 뒤의 accepted state
  모양"이라고 명시했다.
- 생략한 skeleton line, 예를 들어 `Stable package key`, 는 raw 출력의 placeholder를 유지한다고
  덧붙였다.
