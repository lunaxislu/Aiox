## 2026-08-17 · Kickoff 착수 배경과 W1-W4 근거

G2(Terminal/Compose Minimum) plan Stage 1을 시작하며 확인한 근거를 남긴다. 재조사 없이 이 근거로 W1-W4를 이어가면 된다.

- W1 (state.ts decomposition): `src/daemon/state.ts`는 3376줄 단일 파일이다. pair route 생성 로직(`createBidirectionalPairRoutes`, `state.ts:3257`)이 `slotA`/`slotB` 2개만 찾도록 하드코딩돼 있다(`attachAgent`, `state.ts:653`이 호출). roadmap Phase 2 원문은 "ingress generalization, `state.ts` decomposition, pair-to-N-agent route generalization이 우선 전제다"라고 세 항목을 한 문장으로 묶었을 뿐, `state.ts` decomposition이 구체적으로 어느 항목의 전제인지 문법적으로 확정하지 않는다 — 이걸 결정하는 게 W1이다.
- W3 (naming/스키마): `docs/specs/aiox-compose-contract.md`는 이미 "target command와 schema 이름은 v1 compose contract를 승인할 때까지 provisional"(8-9행)이고 "compose 파일명과 discovery 규칙은 compose 착수 전에 별도 승인"(69행)이라고 열어뒀다. 그런데 spec 본문이 "Docker식 `services`/`scale`/`replica` 은유는 피한다"(28행)면서도 정작 섹션 이름("Compose")과 명령어 동사(`up`/`down`, `aiox compose up`)는 docker compose 이름을 그대로 차용하고 있다 — 이 불일치가 `aiox.yaml` 등 대안 검토의 발단이다.
- W4 (터미널 UI): 사용자 실제 환경은 tmux가 아니라 cmux/ghostty다. 현재 spec의 `--ui tmux|wt|iterm2|none` 목록에는 cmux가 없다.
- compose up의 foreground-only 실행 모델(항상 foreground, `-d` 없음, 재접속 시나리오 없음)은 이미 확정되어 `docs/specs/aiox-compose-contract.md` §6에 반영되어 있다 — 이 로그 범위 밖이라 재론 불필요. 다만 그 spec의 Implementation review note에 `aiox attach`의 존치 여부와 `--ui none`일 때 다중 agent 표시 방법이 열린 채로 남아 있으니 W4 UI 설계에서 같이 확인한다.

### 2026-08-17 16:43 · W1 결정 — state.ts decomposition 비전제, 선택지 C 채택

subagent(Explore) 코드 조사와 핵심 주장 3개(`attachAgent`→`createBidirectionalPairRoutes` 호출부, `createDaemonState` 클로저 경계, `core/pairs.ts:112` 하드코딩)의 직접 검증을 거쳐 W1을 결정한다.

**확인한 사실**
- `state.ts:707-714`에서 `attachAgent`가 `createBidirectionalPairRoutes`를 직접 인라인 호출하는 단방향 흐름뿐이다. dispatch 쪽(`dispatchToPairPeersNow`, 1892-2037행)은 `createBidirectionalPairRoutes`나 `attachAgent`를 호출하지 않고, `runSendMessageTransaction`이 `routes.list().filter(...)`(2811-2813행)로 route 테이블을 조회해서만 소비한다.
- `createDaemonState` 클로저는 619-3078행에서 끝난다(직접 확인). `createBidirectionalPairRoutes`(3257행 부근)와 관련 함수는 그 바깥 모듈 레벨에 있고 `agents`/`routes`/`createId`/`now`를 파라미터로만 받는다 — `queueExpiryTimers`/`deliveryAttempts`/`codexRuntimes` 등 daemon live 상태(클로저 변수)에 전혀 접근하지 않는다.
- `dispatchToPairPeersNow`는 `targetAgent.kind` 기반으로만 분기해 slot 개수 가정이 없다 — dispatch 레이어는 이미 N-agent 대응이 끝난 상태다.
- 2-slot 하드코딩(`"a"`/`"b"` 문자열 매칭)의 실제 위치는 3곳이다: `src/daemon/state.ts`의 `createBidirectionalPairRoutes`(~3257행, ~35줄), `src/core/pairs.ts:112`(`getPairStatus`, `attachments.length === 2 && slots.has("a") && slots.has("b")`, 직접 확인), `src/store/repositories/pairs.ts`(동일 패턴). 셋 다 국소적이고 서로 멀리 떨어진 dispatch/channel 코드와 결합돼 있지 않다.

**판단**
- roadmap이 "ingress generalization + state.ts decomposition이 우선 전제"라 묶은 문구는 Phase 2 전체(vendor 확장, adapter registry 등 더 큰 구조 개편)를 겨냥한 것이지, 이번 pair-to-N-agent 작업 하나만 놓고 보면 그 전제가 성립하지 않는다. 결합도가 낮아 3376줄 전체를 먼저 쪼갤 기술적 근거가 없다 — **선택지 A(전체 decomposition 선행) 기각**.
- pair/route 함수가 이미 파라미터 주입형이라 독립 추출(B) 자체는 저비용이지만, 지금 추출해야 할 구체적 이유(테스트 분리 필요성 등)가 없다. 프로젝트의 선제적 추상화·리팩터 지양 원칙에 비추어 **선택지 B(국소 추출 후 작업) 기각**.

**결정 (사용자 확정)**
선택지 C 채택: `state.ts` 전체 decomposition 없이, 위 3개 파일(`state.ts`의 `createBidirectionalPairRoutes`, `core/pairs.ts`의 `getPairStatus`/`pickFirstOpenSlot`, `store/repositories/pairs.ts`의 동일 패턴)의 slot 판정 로직만 제자리에서 N-slot 순회로 확장한다. `state.ts` 전체 decomposition은 이번 plan의 선행 조건이 아니며, roadmap Phase 2 항목으로 그대로 남는다.

## 2026-08-18 · W2 결정 — pair CLI는 reservation 전용 유지

core/pairs.ts(`createPairReservation`)와 CLI `pair-create`(`src/cli/invocation.ts:240-245`, `invocation.test.ts:53,66`로 직접 확인)를 조사한 결과, `pair` 커맨드는 현재도 이름·status(pending)만 만들고 즉시 종료하며 agent를 붙이지 않는다. launch·attach orchestration(daemon attach + slot 배정 + 실제 child process 실행/foreground 대기/실패 rollback)은 이미 `attach` 커맨드(agent-kind별, `invocation.ts:148-220`)가 1-agent 단위로 갖고 있다.

**판단**
- `docs/decisions/pair-attach-atomicity-and-sentinel.md`가 "attach는 단일 agent 단위 원자적 동작"이라는 X-strict 경계(agents.attach는 pairId를 받지 않음, pairs.attachAgent가 별도)를 daemon 레벨에 이미 못박아뒀다. pair CLI가 다중 agent를 동시에 orchestrate하면 이 경계와 어긋난다.
- `docs/specs/aiox-compose-contract.md:45`가 이미 "`pair`, `connect`, `pending_attach`는 future compose desired state의 seed"라고 명시했다 — pair는 compose가 참조하는 building block으로 설계됐지, compose와 경쟁하는 별도 launcher가 아니다.
- W1에서 승인한 YAGNI 판단(관측된 필요 없이 선제적으로 확장하지 않음)과 같은 결이다. 다중 agent 동시 launch/화면분할 로직을 compose와 pair 두 곳에 중복 구현할 근거가 없다.

**결정 (사용자 확정)**
옵션 A 채택: `pair` CLI는 reservation 전용으로 유지한다. G2 compose(선언적 config) 커맨드가 다중 agent 동시 launch orchestration을 전담하며, 내부적으로 agent마다 기존 `attach` 경로(이미 구현된 단일 agent launch+attach)를 재사용한다. 수동 2-agent pair도 지금처럼 `attach`를 pair마다 두 번 실행하는 방식을 유지한다.

**부수 효과 (owner 반영 필요, 후속 처리)**
`docs/specs/aiox-compose-contract.md:78-83`의 열린 질문("`aiox attach`가 compose 문맥에서도 core 표면으로 남을지")이 이 결정으로 닫힌다 — attach는 compose가 내부적으로 재사용하는 primitive로 남는다. G2 closeout(마지막 stage, "G2 gate evidence 정합화·owner 문서 반영") 시 이 spec의 Implementation review note를 갱신한다.

## 2026-08-18 · W3 결정 — 파일명·명령어 이름·CLI read 방식

config 파일명, 명령어 이름, CLI read 방식 세 항목을 사용자와 대화형으로 결정했다. yaml 스키마(C)는

**결정 (사용자 확정) — 파일명: `aiox.yaml`**

dot 유무를 검토했다. dotfile(`.env`, `.eslintrc`, `.npmrc`)은 도구가 참조하는 부수 메타 설정,
non-dotfile(`docker-compose.yml`, `Cargo.toml`, `package.json`)은 사람이 직접 읽고 편집하는 선언적
manifest라는 것이 생태계 일반 관례다(레포 검증 사실이 아니라 일반 지식으로 구분해 적용). spec
§6(46-51행)이 이미 user-level 취향(`~/.aiox/config.json`, dotdir)과 project-level compose 계약을
분리해 뒀으므로, project 계약 파일인 compose config는 dotfile 자리가 아니라 manifest 자리다.
non-dot `aiox.yaml`로 결정했다.

**결정 (사용자 확정) — 명령어 이름: `aiox host` / `aiox quit`**

`aiox compose up`/`down`을 그대로 쓸지 재검토하며 여러 후보를 논의했다: muster/dismiss,
convene/adjourn, weave/unravel, host/dismiss, invite/dismiss, admit/dismiss, 최종 host/quit.

- 사실 확인: `src/cli/invocation.ts:127-267`의 실제 dispatch는 전부 flat single/hyphenated
  token이다(`connect`/`disconnect`, `daemon-start`/`daemon-stop`, `agent-attach`, `pair-create`).
  `<명사> <동사>` 2단 subcommand 구조(`aiox compose up`)는 이 codebase 어디에도 선례가 없다 — spec
  초안에만 있던 표기다. flat 대칭 command(`connect`/`disconnect`류)가 기존 관례와 맞다.
- `host`가 `docs/specs/aiox-compose-contract.md` §6(35-38행)의 instruction precedence
  용어("host policy", "host-native instruction")와 문자열이 겹친다는 우려를 제기했으나, 재검토
  결과 문법적 역할이 다르다(하나는 precedence 체인의 명사 수식어, 하나는 CLI 동사 명령)는 사용자
  지적을 받아들여 blocking 사유에서 철회했다 — 같은 문서 안에 같은 단어가 다른 의미로 존재한다는
  사실 자체는 남지만 disqualify 근거는 아니다.
- "aiox의 방에 초대되고 퇴장하는" 느낌을 사용자가 선호 방향으로 명시했고, `host`(맞아들인다·자리를

  나가면 끝난다는 실제 lifecycle과 부합, `dismiss`보다 타이핑이 짧다)로 수렴했다.
- 이 결정으로 spec의 `aiox compose up` 표기와 roadmap G2 카드의 동일 표기(357행 부근)가 모두
  stale해진다 — owner 반영은 G2 Stage 2 착수 시 또는 이 Kickoff closeout 시 처리한다(아직 미반영,

### 2026-08-18 13:38 · C 결정 — yaml 스키마 v1 확정, W3 전체 종료

사용자와 대화형으로 yaml 스키마 v1 필드를 확정했다. A(파일명)·B(명령어 이름)·D(CLI read 방식)는
이전 entry에서 이미 확정했으므로 이 entry로 W3 네 항목이 모두 닫힌다.

**결정 (사용자 확정) — 필드명: `name`/`vendor`**

`id` 대신 `name`, `kind` 대신 `vendor`를 쓴다.

- `name`이 `id`보다 정확한 이유: 이 필드는 daemon이 발급하는 실제 `agentId`(routing 내부는
  `sourceAgentId`/`targetAgentId`로 관리됨, W1에서 확인)가 아니라 yaml 안에서 `routes`가 서로
  참조할 때 쓰는 사용자 선언 라벨이다. attach 실행 시점에 실제 agentId가 별도로 생성된다.
- `vendor`는 `docs/decisions/pair-slot-generalization.md` 본문이 이미 개념적으로 쓰는 어휘다
  ("vendor 종류와 무관한", "same-vendor pair", "vendor-neutral", "vendor-pair hardcode"). 다만
  실제 코드 필드명은 `agent.kind`다(사실) — yaml `vendor`는 CLI parse 시 내부적으로 `kind`로
  매핑하는 번역 한 겹이 생긴다. 사용자 대면 계약과 내부 구현 이름이 다른 건 이 프로젝트가 이미
  다른 경계에서도 쓰는 패턴이라 문제로 보지 않는다.

**결정 (사용자 확정) — routes: `agents` → `group`, 리스트 유지(`{ }` hash-set 기각)**

필드명은 `agents`에서 `group`으로 바꾸되, 표현 형태는 `[ ]` 리스트를 유지한다. `{ }`(hash-set)
제안은 검토 후 기각했다: YAML의 `{ }`는 hash-set이 아니라 flow mapping(key: value)이라, 진짜
set을 표현하려면 각 이름에 dummy value를 붙여야 해서 리스트보다 타이핑이 늘어난다. group 내
중복 name 방지라는 실제 목적은 스키마 모양을 바꾸지 않고 CLI parse-time validation으로 해결하기로
했다(파서가 같은 group 안 중복 name을 거부) — 구현 시 Stage 2/4에서 반영할 사항으로 남긴다.

**결정 (사용자 확정) — `instructions`: global + per-agent, 둘 다 optional**

top-level `instructions.global`이 있으면 전체 agent에 주입하고 없으면 생략한다. 각 `agents[]`
entry의 `instructions`가 있으면 해당 agent에 global 위에 추가로 주입하고 없으면 생략한다(사용자가
"추가"라고 표현해 additive layering으로 해석했다).

### 2026-08-18 15:56 · envelope 레이어 분석과 send target 파라미터 확정, agents_list를 v1 step으로 결정

- Canonical wire envelope(`docs/specs/aiox-message-lifecycle.md` §4.1)는 이미 delivery당 단일

- Route 자료구조(`src/core/routes.ts:9-24`, `createDirectedRoutes`)는 이미
  `targetAgentIds: readonly string[]`를 받아 소스 하나에서 N개 route를 만들 수 있다. 이미
  N-capable, 변경 불필요.
- 실제 gap은 agent-facing `send` 요청 스키마(`SendMessageRequest`,
  `src/daemon/state.ts:372-380`)에 target 필드가 없다는 것과, daemon routing 로직

  전체에 무조건 fan-out**한다는 것이다. 2-slot pair에서는 route가 항상 1개라 broadcast와 targeted
  send가 결과적으로 같았지만, N peer full mesh에서는 이게 그대로 "매번 전체 broadcast"가 된다.
- `docs/specs/aiox-message-lifecycle.md` §4.4 에러 vocabulary에 `unknown_target`/`route_not_allowed`가
  이미 예약돼 있어 target 파라미터 도입에 신규 에러 코드가 필요 없다.

**결정 (사용자 확정) — list→send는 병합하지 않고 별도 `agents_list()` tool을 v1 step으로 만든다**

두 방향을 검토했다.

1. `send`/`reply` 응답 payload에 현재 peer 스냅샷을 얹는 방식(신규 tool 없이 병합) — steady-state에서는

   있다.
2. Attach 시점에 daemon이 이미 떠 있는 세션에 `type:event, intent:notification, source.kind:daemon`
   메시지를 기존 delivery 경로(Claude channel push/Codex turn·start, 이미 검증된 메커니즘)로
   push하는 방식 — 1번의 gap을 구조적으로 닫지만, §4.3에 없는 새 notification subtype이 필요해
   복잡도가 늘어난다.

**결정 (사용자 확정) — `send`의 `target`은 필수, `string | string[] | "*"` 형태**

```

```

target을 필수로 만들어 이전 entry(line 159-166)에서 열어뒀던 "target 생략 시 기본 동작(broadcast

daemon 구현 영향(추론, 미구현): `"*"` 케이스는 현재 `runSendMessageTransaction`의 "source의 모든
active route에 fan-out" 로직을 그대로 재사용할 수 있다(코드 변경 없음). 단일/subset target은
route 목록에서 요청된 이름만 필터링하고, 없으면 이미 예약된 `unknown_target`/`route_not_allowed`로
거부하는 신규 로직이 필요하다.

**후속으로 남는 것**

- `"*"`를 `agents[].name`으로 등록하지 못하게 parse-time reserved-word 검증이 필요하다(설계
  제안, 미구현).
- `agents_list()` 자체의 입출력 스키마(응답 필드: name/vendor/role 등)는 아직 미정.
- `description`/`role` 필드명(이전 entry에서 이미 open)도 여전히 미정.
- attach 시 notification push 설계(2안)는 다음 단계 후보로 남아 있으나 착수 안 함.

### 2026-08-18 17:26 · GPT 검토안 재검증 — routes named group 모델 확정, type/directed/policy 결정

사용자가 외부 LLM(GPT 앱)에 self-contained 프롬프트를 넣어 받은 설계안을 사용자 스스로 재종합해
제시했다. AGENTS.md Evidence And Reporting 원칙("타 에이전트의 의견을 무조건 수용하지 않는다")에
따라 그대로 채택하지 않고 기존 로그·plan·코드와 대조 검증한 뒤 사용자와 대화형으로 반영 여부를
결정했다.

**결정 (사용자 확정) — peers-per-agent 모델을 폐기하고 top-level `routes` named group 모델로 전환**

이전 entry들(line 259 이후)에서 쌓아온 `agents[].peers` 필드 기반 설계(각 agent가 자신의 peers를
선언, star vs clique 해석 문제, 단방향을 peers 항목에 `{name, direction}`으로 얹는 방안)를 전부
대체한다. 이유: peers-per-agent 모델은 대칭 관계를 "누가 선언했는가"라는 비대칭적 위치에 두어
소유권이 불명확했다. `routes` 모델은 관계를 별도 top-level named group으로 분리해(설계 원칙
"agent definition과 communication topology는 분리한다") 이 문제를 없앤다. 이로써 이전에 열려
있던 star-vs-clique 질문과 peers 내부 direction object 질문은 모두 moot가 된다.

```yaml
routes:
  - name: frontend
    members: [claude-frontend, codex-reviewer, claude-architect]
```

- 하나의 named group에 속한 `members`는 기본적으로 전원 양방향 full mesh다.
- routing group끼리 member가 겹쳐도 절대 자동(전이적) 병합하지 않는다 — `[A,B,C]`와 `[C,D]`
  그룹이 있어도 A↔D, B↔D는 생성되지 않는다. 각 group은 독립된 통신 도메인이다.
- `agents[]`에 선언된 agent는 routing group 참여 여부와 무관하게 항상 실행된다(기존 결정과 일치,
  재확인).
- 하나의 agent는 여러 routing group에 동시에 속할 수 있다.
- 이 model은 기존 요구사항(로그 초반의 "100명을 group 배열 하나로, N번 반복 안 씀")을 peers 모델
  보다 더 직접적으로 만족한다.

**결정 (사용자 확정) — `vendor` 필드를 `type`으로 통일**

line 440 근처에 이미 기록된 `agents_list()` 응답 스키마의 `vendor` 필드(값: `"claude"`/`"codex"`)를
`type`으로 개명한다. 검증 결과 그 필드의 값 자체가 애초에 회사명이 아니라 구현체 이름이었으므로
개념 충돌 없이 이름만 맞추는 정정이다. `agents_list()` 응답 스키마는 다음으로 갱신된다:

```json
{
  "peers": [
    { "name": "claude-b", "type": "claude-code", "role": "reviewer", "description": "..." },
    { "name": "codex-d", "type": "codex", "role": null, "description": null }
  ]
}
```

**결정 (사용자 확정) — `agents[].type`의 v1 허용 범위**

`type`은 `codex`, `claude-code`, `gpt-app`, `claude-app` 등 aiox가 지원하는 agent implementation을
선택하는 필드로 두되(vendor 개념이 아님 — `type: codex`는 OpenAI라는 vendor를 가리키지 않고 Codex
agent implementation을 가리킴), **v1 validator가 실제로 허용하는 값은 지금 구현된 두 adapter
(`codex`, `claude-code`)로 한정**한다. `gpt-app`/`claude-app`은 스키마가 향후 확장 가능함을 보여주는
문서상 예시일 뿐, 이번 라운드에서 구현하지 않는다. 근거: `plans/g2-terminal-compose-minimum.md`
Notes가 "third vendor support, ... adapter registry/event-boundary 통합"을 Phase 2로 명시적으로
제외하고 있고, 지금 코드베이스(`src/adapters/claude/launcher.ts`, `package.json`의 `pnpm claude`/
`pnpm codex` 스크립트)에는 두 adapter만 실재한다.

**결정 (사용자 확정) — `routes[]`에 `directed`(per-pair override) 추가, `members`는 모든 group에 필수**

routing group은 대칭 mesh만 다루던 것에서, `members`(참여자 집합, 항상 필수)에 `directed`(선택,
개별 pair override)를 얹는 형태로 확장한다. peers 모델의 per-member `direction` 태그 방식은
채택하지 않았다 — group 전체가 대칭인 이 모델에는 "누구 기준의 방향인가"라는 기준점이 없기
때문이다. 처음에는 `members`/`edges`(당시 이름) 택1의 mutually-exclusive 구조로 설계했으나,
`edges`만 있는 group은 참여자 집합이 `from`/`to`에 흩어져서만 드러나 "group 하나의 의미를 그
선언만 보고 이해할 수 있어야 한다"는 설계 원칙에 어긋난다는 지적으로 `members`를 모든 group에
필수로 바꿨다. 이어서 "3명 중 1명이 directed에 안 걸리면 나머지와는 mesh인가"라는 질문으로,
최초에 제시했던 "directed 있으면 전체 mesh를 대체" 규칙이 틀렸음을 확인하고 아래 규칙으로
정정했다.

```yaml
routes:
  - name: frontend
    members: [claude-frontend, codex-reviewer, claude-architect]   # directed 없음 → 전원 mesh

  - name: escalation
    members: [qa-bot, claude-architect, codex-reviewer]
    directed:
      - { from: qa-bot, to: claude-architect }
```

**최종 규칙**: `members` 안의 모든 pair는 기본적으로 양방향 mesh다. `directed`에 명시된 pair만 그
특정 관계가 나열된 단방향으로 좁혀진다. `directed`에 언급되지 않은 pair는 mesh 기본값을 그대로
따른다(전체 대체가 아니라 pair 단위 override). 위 예시에서 qa-bot↔claude-architect는 단방향이지만
qa-bot↔codex-reviewer, claude-architect↔codex-reviewer는 언급이 없으므로 그대로 mesh다.

이 "기본은 mesh, directed는 예외"가 principle 4/5(암묵적 topology 확장 최소화)와 충돌하지 않는
근거: 이 규칙은 group 선언 하나 **안에서만** 적용되는 고정되고 균일한 규칙이라 다른 group을 참조할
필요가 없다 — 위험한 건 cross-declaration 간의 암묵적 병합이었지, 한 선언 내부의 "기본값 + 명시적
override" 자체가 아니다(`members` → mesh 확장 자체도 이미 같은 성격의 기본값이다).

- `directed[].to`는 단일 이름 또는 배열을 허용해 한 source가 여러 target에 broadcast하는 패턴을
  한 줄로 쓸 수 있게 한다. `directed[].from`은 항상 단일 이름 — many-to-many가 필요하면 `directed`
  항목을 여러 줄로 나열한다(cartesian 확장 같은 암묵적 문법은 의도적으로 배제).
- validation(설계, 미구현): `directed[].from`/`to`는 그 group의 `members` 안에 있는 이름이어야
  한다(참여자 집합 밖을 가리키면 에러). 자기 자신을 가리키면 안 된다.
- 이름은 `edges`가 아니라 `directed`로 확정했다 — YAML을 직접 작성·리뷰하는 사람 기준으로
  그래프 이론 용어(edges)보다 의미가 바로 읽힌다(설계 원칙 1, readability).

**결정 (사용자 확정) — directed pair에서 `agents_list()`의 "peers" 의미론**

`agents_list()`가 노출하는 peers는 "호출한 agent가 `send(target:...)`로 실제로 보낼 수 있는 대상"
집합이다(outbound-sendable 기준). `qa-bot → claude-architect` 단방향 edge에서 `claude-architect`가

## 2026-08-18 · W4 결정 — --ui none fallback: 옵션 A(전체 실행 + 포커스 전환), 1차 방향

**결정 대상은 tmux 없는 fallback(`--ui none`)이다.**

agent에만 화면을 붙여서 보다가 다른 agent로 포커스를 전환하는 방식**을 채택한다.

  (`codex resume <threadId> --remote <endpoint>`)까지 활용한다.

**spec §6의 기존 foreground-only/no-reattach 결정과의 관계(혼동 방지용 명시)**: spec line 156-159는
이미 `aiox host` 전체가 항상 foreground이고 "터미널을 닫거나 떠난 뒤 나중에 돌아와 이미 돌고 있는

유지된다 — 옵션 A는 `aiox host`를 껐다가 나중에 다시 켜서 예전 compose 실행에 재접속하는 시나리오가
아니라, **하나의 살아있는 `aiox host` foreground 프로세스가 계속 떠 있는 동안** 그 프로세스가 이미
백그라운드로 띄워 둔 개별 agent 프로세스들 사이에서 사람의 화면 포커스만 전환하는 것이다. compose
전체의 reattach가 아니라 compose 내부 agent 표시 방식(view driver 대체재)의 문제라, 기존 결정과
충돌하지 않는다.

무시나 lint 경고가 아니라 명시적 에러로 막는다. 예:

```yaml
routes:
  - name: escalation
    members: [qa-bot, claude-architect, codex-reviewer]
    directed:
      - { from: qa-bot, to: [claude-architect, codex-reviewer] }
      - { from: qa-bot, to: claude-architect }   # claude-architect가 위에서 이미 나옴 → 에러
```

`to`가 배열인 경우도 펼쳐서 비교해야 한다 — 단순 객체 문자열 비교로는 이 예시의 중복을 못 잡는다.

line 701-705의 나머지 두 항목(이름 전역 uniqueness, dangling reference 처리)과 `command`/`config`의
type별 세부 스키마는 아직 미결정으로 남는다.

## 2026-08-19 · W3 후속 — 이름 유일성 범위와 dangling reference 처리 확정

line 701-705에서 남아 있던 나머지 두 항목을 확정한다.
