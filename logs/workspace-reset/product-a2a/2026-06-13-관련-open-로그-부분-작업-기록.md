## 2026-06-13 · 관련 로그 영향 기록 설계

@codex

### 확인 결과

- taxonomy 로그의 실제 미완료 체크박스는 하나이며, workflow 로그 완료 후 lifecycle 검토를 재개하는 넓은 행동이다. 이번 작업에서 그 안의 Guides·Plans 책임과 owner 연결은 부분 수행됐지만 lifecycle·naming·link 책임은 남아 있다.
- taxonomy 로그에 부분 수행 기록을 추가했고 기존 미완료 행동은 아직 정확하므로 완료·대체하지 않고 유지했다.
- 기존 로그 스킬 구조 개선 로그는 refactoring과 검증을 완료한 `decided` 상태이며 남은 체크박스가 없다.

### 제안 계약

- 이름은 `관련 로그 영향 기록`으로 한다. 현재 로그가 작업 과정의 상세 owner이고, 관련 open 로그에는 그 로그의 미완료 범위에 미친 영향과 남은 범위만 짧게 기록한다.
- trigger는 모든 append가 아니라 작업 checkpoint다: owner 문서·code·test를 실제 변경했을 때, 현재 next를 완료·대체할 때, 다른 로그로 전환할 때, 로그를 닫기 전이다.
- 후보 탐색 순서: 명시된 부모·분리 로그와 활성 plan 단계 로그 -> 현재 기록에 직접 언급된 로그 경로 -> 변경한 owner·workstream 키워드로 `search ... --status open` -> 후보에만 `audit` 실행 후 해당 line 주변과 최신 블록을 읽는다.
- 모든 open 로그 본문을 일괄 읽지 않는다. topic·description 검색에서 후보가 없거나 명시 관계가 없으면 중단한다. semantic 관련성 판단과 본문 수정은 agent가 맡긴다.
- 관련 로그에는 현재 로그 링크, 부분 수행된 미완료 범위, 실제 결과·변경 경로, 남은 범위를 기록한다. 토론과 근거 전체를 복사하지 않는다.
- 체크박스 처리: 전체 완료면 complete, 부분 수행으로 기존 문장이 부정확하면 남은 행동으로 replace, 여전히 정확한 넓은 행동이면 유지하고 진행 기록만 append, 불필요해지면 cancel, 의미가 불명확하면 수정하지 않고 보고한다.
- 1차 반영은 `SKILL.md`에 checkpoint 안전 규칙과 reference pointer를 짧게 추가하고 `references/lifecycle.md`에 trigger·탐색·상태 전이를 상세화한다. 기록 내용 경계는 `recording-contract.md`에 짧게 둔다. script는 현재 `search`와 `audit`로 충분하므로 자동 scanner나 새 명령을 만들지 않는다.

- 취소: 사용자가 관련 로그 영향 기록 계약과 1차 문서-only 반영 범위를 검토·승인하면 log skill과 references를 수정하고 대표 시나리오로 검증한다. — 문서 계약만으로는 과거 섹션 체크리스트 정합화와 중복 next 방지를 해결할 수 없어 도구 설계 범위를 추가한다

## 2026-06-13 · 섹션 체크리스트와 resolve 도구 개선 요구

@user

- `작업-로그-시스템-구축.md`처럼 과거 섹션형 체크리스트가 후속 블록에서 실제 완료·대체됐어도 원래 `[ ]`가 남아 audit에 계속 잡히는 문제도 log skill·도구 개선 범위에 포함해야 한다.
- wrapper 유지 후 제거처럼 후속 결정으로 상태가 바뀐 항목과 후속 작업 순서처럼 여러 항목이 순차 완료된 목록이 원래 위치에서 정리되지 않아 로그 전체 상태가 맞물리지 않는 사례를 제시했다.

@codex

- 현재 `append`는 마지막 실제 `- [ ] 다음:` 한 항목만 complete·replace·cancel할 수 있다. 일반 섹션 체크리스트의 임의 항목은 처리하지 않으므로, 후속 기록에서 완료가 명백해도 원래 `[ ]`는 그대로 남고 `audit`·close guard가 계속 보고한다.
- 이 문제는 관련 open 로그 영향 기록과 연결되지만 구분되는 도구 요구다. 하나는 다른 로그의 영향 범위를 찾는 문제이고, 다른 하나는 선택한 로그 내부의 기존 미완료 항목을 안전하게 해소하는 문제다.
- 도구가 후속 본문 의미를 자동 판정해 일괄 수정하면 안 된다. agent가 audit 결과와 후속 기록을 대조해 항목별 완료·취소·이관을 결정한 뒤, 도구는 정확히 지정된 항목만 검증·변환하는 방식이어야 한다.
- 후보 방향: `audit` 출력에 안정적인 대상 식별 정보(줄 번호와 원문 유지)를 사용하고, append 또는 별도 resolve 명령에 `--line`과 기대 원문을 함께 전달해 동시 수정·잘못된 줄 변경을 거부한다. complete는 `[x]`, cancel·transfer는 체크박스를 일반 기록으로 바꾸고 이유·대상 경로를 남긴다.
- 여러 항목을 한 번에 처리할 때는 각 대상과 mode를 명시한 입력을 검증한 후 원자적으로 적용해야 한다. 자동으로 모든 미완료 항목을 정리하거나 후속 블록만 보고 의미를 추론하지 않는다.
- 추가 guard: append 본문에 실제 미완료 `다음:`이 있는데 `--next`도 제공하면 동일·복수 재개 행동이 생길 수 있으므로 거부하거나 한 경로만 쓰도록 검증한다. 이번 설계 로그에서 동일 next가 중복 생성된 실제 사례를 수동 정리했다.
- 따라서 1차 문서-only 반영 전에 도구 개선 범위를 함께 설계한다: cross-log 후보 탐색 계약, 현재 로그 임의 체크리스트 resolve API, append의 복수 next guard, 테스트 fixture와 원자성·동시 수정 불변.

- 취소: cross-log 영향 기록과 현재 로그 체크리스트 resolve를 함께 만족하는 최소 CLI·계약·테스트 설계안을 작성해 사용자 검토를 받는다. — 후속 블록의 취소 서술만으로는 원래 체크박스가 구조적으로 해소되지 않는 위험을 추가했다

## 2026-06-13 · 후속 서술과 구조 상태 불일치 위험

@user

- 후속 작업 순서의 원래 `[ ]` 목록을 그대로 둔 채 아래에 첫 항목을 `취소:`로만 기록하는 방식은 사람이 전체 로그를 읽을 때는 이해할 수 있지만 hook·onramp·script가 구조적으로 소비할 때 위험하다고 지적했다.

@codex

- 동의한다. 현재 `audit`과 `set-status` guard는 구조적인 `[ ]`만 보고 후속 `취소:` 문장과 연결하지 않는다. 따라서 취소·완료·이관을 새 블록에만 서술하면 원래 체크박스는 계속 활성 미완료로 남는다.
- onramp는 현재 로그 본문을 직접 해석하지 않지만, agent가 onramp 포인터를 따라 `audit`하거나 미완료 행동을 읽을 때 오래된 목록을 현재 작업으로 오인할 수 있다. 향후 hook이 미완료 항목을 요약하면 같은 문제가 더 커진다.
- 구조 원칙: 체크리스트 상태 변경은 원래 항목에 반영되어야 한다. 완료는 `[x]`, 취소·대체·이관은 원래 `[ ]`를 체크박스가 아닌 `취소:`·`대체:`·`이관:` 기록으로 변환하고 이유·새 owner·대상 로그를 남긴다. 후속 블록의 설명만으로 원래 체크박스를 해소했다고 간주하지 않는다.
- 목록 일부만 순차 처리할 때도 각 원래 항목을 즉시 resolve해야 한다. 전체 목록 아래에 하나의 `취소:`를 추가하거나 새 블록에 완료 사실만 쓰는 패턴은 금지한다.
- 도구 요구에 `resolve`의 구조적 postcondition을 추가한다: 지정 항목은 적용 후 audit 결과에서 사라져야 하고, 변환된 기록에는 원문과 mode·이유·대상 경로가 남아야 한다. 여러 항목 일괄 처리도 전부 검증된 경우에만 원자 적용한다.
- 문서 계약에는 hook·onramp·script 같은 구조 소비자가 후속 서술을 의미적으로 결합하지 않는다는 전제를 명시한다. agent가 기록할 때 서술 기록과 구조 상태를 같은 checkpoint에서 함께 갱신해야 한다.

- 취소: cross-log 영향 기록, 임의 체크리스트 resolve와 구조 소비자 안전을 함께 만족하는 최소 CLI·계약·테스트 설계안을 작성해 사용자 검토를 받는다. — 사용자가 다음 작업을 도구 취약점, 스킬 기능과 문서 리팩터링의 세 축으로 확정했다
