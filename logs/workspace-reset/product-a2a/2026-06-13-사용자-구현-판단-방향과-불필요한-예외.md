## 2026-06-13 · dry-run 필요성 검토와 사용자 판단 기준

## 질문

@codex

- `--dry-run`을 항상 실행하지 않고 선택적으로 유지할 사례로 mode 선택이 불확실한
  경우, multiline next나 복잡한 기존 형식, script 자체 변경 검증과 사용자의 적용 전
  diff 요청을 제시했다.
- 과거 dry-run 검증에서 빈 next 허용, replace reason의 backslash escape 처리와 닫히지
  않은 frontmatter 허용 문제를 발견했으므로 preview가 보호 가치를 가질 수 있다고
  설명했다.
- 잘못된 frontmatter가 append에 도달할 경로로 사용자 수동 편집, 과거 도구로 만든
  기존 로그, 동시 작업이나 중단으로 손상된 파일, 로그가 아닌 파일을 append 대상으로
  잘못 선택하는 경우를 제시했다.

@user

- mode 선택이 불확실하다면 dry-run으로 해결할 문제가 아니라 agent가 상태 전이 계약에
  따라 완료·유지·대체·취소·이관 중 올바른 의미를 판단해야 한다고 보았다.
- multiline next나 복잡한 기존 형식은 이해 가능한 사례지만, 정상 생성·기록 계약에서
  실제로 발생하는지 먼저 확인해야 하며 막연한 예외로 기능을 유지하지 않는다.
- script 변경 검증은 사용자가 명시적으로 지시하고 여러 번 검증하게 하므로 선택적인
  일반 workflow 사례가 아니다. 사용자가 최종 diff를 직접 확인하므로 별도 diff 요청도
  dry-run 존치 근거가 아니다.
- 빈 next는 script가 빈 값과 공백을 거부하도록 작성하면 해결된다. reason의 backslash
  escape는 구현이 리터럴을 정확히 보존해야 하는 correctness 문제이며 dry-run의 책임이
  아니다.
- 로그는 `new`로 생성하고 log skill로만 기록하므로 사용자가 직접 편집할 경로는 없다.
  과거 도구로 만든 로그도 현재 append 대상이 되는 손상 파일이라는 실제 근거가 없으면
  도달 가능한 예외로 보지 않는다.
- 사용자가 작업 흐름을 통제하는 harness이므로 동시 writer나 중단으로 파일이 손상되는
  상황을 전제하지 않는다.
- 로그가 아닌 파일을 append 대상으로 선택하는 것은 정상 입력 예외가 아니라 log
  skill이나 agent가 대상을 잘못 선택한 오류다. 이를 사용자가 부담할 예외 처리 근거로
  삼지 않는다.
- 기록 가치와 체크박스 상태 전이 계약, script 입력 guard와 회귀 테스트가 각 책임을
  맡는다면 apply 전에 같은 결과를 다시 미리보는 `--dry-run`은 중복이므로 삭제한다.

## 결론

- `--dry-run`은 삭제한다. 정상 append는 검증된 단일 apply 경로로 즉시 반영한다.
- 빈 next는 script가 공백과 빈 값을 거부하는 입력 guard로 해결한다.
- reason의 backslash와 escape 문자는 구현이 리터럴을 보존하도록 처리한다. 이는 변환 correctness이며 preview 단계의 책임이 아니다.
- frontmatter 검증은 append가 잘못된 대상을 수정하지 않도록 하는 방어적 guard로 남길 수 있지만, 정상 workflow에서 발생 가능한 사용 사례로 보지 않는다.
- 의미 판단 오류는 기록 계약과 상태 전이 계약으로 막고, 파일 변환 오류는 script guard와 회귀 테스트로 막는다. dry-run은 두 문제의 근본 해결책이 아니다.
- multiline이나 비정형 로그 같은 사례도 정상 생성·기록 계약 밖이라면 dry-run 존치 근거로 사용하지 않는다.

## 피드백

- 사용자는 추상적으로 가능하다는 이유만으로 예외 경로와 안전 단계를 유지하는 것을 원하지 않는다. 실제 승인된 workflow에서 도달 가능한지 먼저 증명해야 한다.
- agent는 수동 편집, 과거 도구, 동시 writer, 중단 손상처럼 현재 계약이 배제한 상황을 자동으로 가정하지 않는다.
- 잘못된 agent 선택이나 skill 동작은 사용자 입력 예외로 돌리지 않고 agent·skill의 오류로 분류한다.
- 의미 판단, 입력 검증, 변환 correctness와 preview를 분리한다. 한 계층의 문제를 다른 계층의 중복 안전 단계로 덮지 않는다.
- guard와 회귀 테스트로 결정적으로 차단할 수 있는 오류는 해당 위치에서 해결하고, 일반 workflow에 반복 확인 단계를 추가하지 않는다.
- 기능을 유지하려면 막연한 방어 가치가 아니라 실제 도달 경로, 발생 가능성, 기존 보호 장치로 해결되지 않는 잔여 위험을 제시해야 한다.
- 사용자는 최종 결과를 직접 검토한다. agent가 사용자의 확인을 대신한다는 이유로 매 작업에 별도 preview 의식을 강제하지 않는다.
- 구현과 문서화에서는 정상 경로를 단순하게 유지하고, 불필요한 예외 처리와 중복 절차가 시스템의 책임 경계를 흐리지 않게 한다.
