## 2026-06-11 · 코드베이스 현황 파악 결과

조사 범위: `src/store/schema.ts`, `src/core/messages.ts·deliveries.ts`, `src/daemon/api.ts·state.ts(부분)`,
`src/adapters/{codex,claude}/*`, `src/adapters/router.ts·contract.ts`.

spec §4 대비 현황:

- envelope: canonical object 없음. text framing 2종이 분리 구현 — Claude는
  `<channel source="aiox" chat_id origin>`(channel-server.ts `buildChannelNotification`),
  Codex는 `<aiox-channel source message_id>`(state.ts:1699 daemon 하드코딩). protocol
  version 필드 없음. correlation 명칭도 chat_id(Claude) vs message_id(Codex)로 불일치.
- messageId/deliveryId: DB에는 둘 다 존재(`message_deliveries.id`). fan-out
  `1 message = N deliveries`는 `createFanOutMessage`로 구현됨. 단 envelope에는
  messageId만 노출되고 deliveryId는 어디에도 노출 안 됨 → reply correlation은
  parent_message_id 기반.
- type/intent/reply_expected: `messages.type`(question/instruction/status/event/reply)만
  존재. intent는 prompt 텍스트 `Intent:` prefix(LLM 책임), reply_expected 없음 — plan의
  전제와 코드가 일치.
- route: directed edge 구현됨(`routes` unique(source,target)).
- mailbox/redrive: deferred 시 delivery를 `queued`로 되돌리지만 **재전송 트리거 없음**
  (`dispatchToPairPeers` 호출처 4곳 전부 send/reply 수신 시점). offline target 메시지는
  queued로 방치.
- store: production daemon `:memory:`(run.ts:25) — 재시작 시 전체 상태 소실.
  durable 경로는 scaffold(`config/paths.ts`).
- daemon authority/token: Codex ingress token + Claude channel token 검증 존재.
- pair 결합: schema와 dispatch가 pair(slot a=codex, b=claude) 2-agent 전제에 강결합
  (`dispatchToPairPeers`, agents.pair_slot migration). spec의 N-agent/route 일반화와 거리.

ingress 표면 확인:

- Claude: aiox plugin(MCP server) stdio + HTTP loopback ingress. inbound는 MCP
  **custom notification** `notifications/claude/channel`(experimental capability
  `claude/channel`)로 푸시 — 사용자 prompt 표면이 아니라 별도 표면. tool은
  `send(text)`/`reply(chat_id,text)`.
- Codex: egress는 MCP server(`aiox_send_message`/`aiox_reply`), inbound는 daemon이
  app-server WebSocket `turn/start`에 text input으로 주입(injector.ts) — **사용자 입력과
  같은 표면이라 TUI에 사용자 메시지처럼 표시됨**. proxy가 TUI↔app-server 사이에서
  활성 thread binding 추적.
- adapter contract는 `inject()` 단일 메서드 — spec의 4-slot(launch/ingress/egress/identity)
  중 ingress만 추상화됨. launch/attach·identity는 state.ts/launcher에 산재.

Intent label·`[[CONCLUDE]]` 규칙은 양쪽 MCP instruction 텍스트에 하드코딩
(channel-server.ts CLAUDE_CHANNEL_INSTRUCTIONS, mcp-server.ts CODEX_INGRESS_INSTRUCTIONS).

## 2026-06-11 · Codex/Claude ingress 표면 조사 결과

Codex (로컬 codex-cli 0.137.0의 `codex app-server generate-json-schema` 덤프로 확인):

- **`thread/inject_items` 실존** — "Raw Responses API items to append to the thread's
  model-visible history" **without starting a user turn** (공식 app-server 문서로 교차
  확인: https://developers.openai.com/codex/app-server ). 사용자 입력이 아닌 raw item
  (developer message 등)으로 envelope을 model history에 주입하는 표면이 protocol 수준에서
  존재. 단 turn을 시작하지 않으므로 "주입 후 어떻게 turn을 깨우나"와 TUI 표시 여부는
  실험으로 검증 필요. spec §9의 defer 항목이 현행 버전에서 실제 사용 가능 상태.
- **`turn/steer` 실존** — 진행 중 turn에 input 추가 (`expectedTurnId` precondition).
  "Codex turn 진행 중 inbound 메시지" 처리의 공식 표면 후보.
- **`turn/started`/`turn/completed` 서버 알림 실존** (completed/interrupted/failed status)
  — daemon이 target turn 완료를 구독해 reply lifecycle 이벤트("작업중→완료")를 만들 수
  있는 기반. polling 문제의 구조적 해법 재료.
- `turn/start`에 `clientUserMessageId` 필드 확인(spec의 deliveryId 후보와 일치),
  `outputSchema`(턴 최종 메시지 JSON Schema 제약)도 존재 — structured reply에 활용 가능.

Claude (Claude Code 2.1.170):

- 현재 aiox 방식 = plugin의 stdio MCP server가 `notifications/claude/channel` custom
  notification으로 푸시 (experimental capability `claude/channel`). 사용자 prompt 표면이
  아니므로 "작업 중 출력"처럼 보이는 것은 맞음.
- **idle 세션에서 MCP notification silent drop 이슈 실재** —
  https://github.com/anthropics/claude-code/issues/61797 (open/stale, maintainer 무응답).
  같은 표면으로 30-instance multi-agent를 굴리는 다른 사용자가 sequence number +
  Stop hook 기반 passive ack + 재전송(TCP식)을 직접 구현해 우회. → aiox delivery
  lifecycle에 ack/retransmit이 필요하다는 강한 외부 근거.
- 외부 프로세스의 메시지 주입 공식 표면은 아직 feature request 단계
  (https://github.com/anthropics/claude-code/issues/27441 ,
  https://github.com/anthropics/claude-code/issues/36665 ).
- Claude ingress 대안 지도: (1) 현 channel notification(TUI 유지, drop 위험),
  (2) Stop hook으로 turn 종료 시 mailbox 확인 + block/inject — 커뮤니티 검증 패턴
  (https://dev.to/agent-room/how-a-claude-code-stop-hook-unlocks-async-multi-agent-collaboration-no-polling-required-2e0e ),
  단 idle 상태는 못 깨움 → (1)+(2) 조합이 보완적, (3) headless
  `--input-format stream-json`/Agent SDK — TUI 포기 대신 완전 제어(aiox-native runtime
  후보), (4) tmux send-keys류 prompt_only fallback.

판단에 미친 영향: Codex 쪽은 spec §4/§5가 요구하는 구조화 ingress·turn lifecycle 구독이
현행 protocol로 구현 가능(Tier 2 side_channel 상향 가능). Claude 쪽은 현 표면이
experimental + drop 위험이라 delivery ack/재전송 또는 Stop hook 보완 없이는 reply
lifecycle 보장이 약함.

## 2026-06-11 · 시장·경쟁·상업화 조사 결과

Google A2A (이름 충돌 변수):

- 2025-06-23 Linux Foundation 기증, 2026-04 기준 **150+ 조직 지원, v1.2**, Azure AI
  Foundry/Amazon Bedrock AgentCore/Google Cloud 네이티브 통합, 엔터프라이즈 프로덕션
  사용 중 (https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year ).
- "A2A"는 이미 업계 고유명사. aiox가 "A2A standard를 정의한다"고 자칭하면 이름 충돌 +
  "기존 표준 재발명" 인상. 단 실질 영역은 다름 — Google A2A는 HTTP 기반 opaque remote
  agent 간 task 위임(enterprise), aiox는 local-first에서 기존 CLI coding agent
  (사용자가 이미 구독한 Codex/Claude TUI)를 잇는 control plane + compat layer.

1st-party 잠식 (가장 큰 시장 변수):

- **Claude Code Agent Teams** (실험, v2.1.32+, https://code.claude.com/docs/en/agent-teams ):
  teammate 간 직접 messaging + **mailbox** + shared task list(file locking) + idle
  notification + TeammateIdle/TaskCreated/TaskCompleted hooks. "메시지는 자동 배달되어
  polling 불필요"를 1st-party가 구현. **단 Claude Code 인스턴스 전용(single-vendor)**,
  1 lead/1 team, nested 불가.
- Codex도 subagents 제공 (https://developers.openai.com/codex/subagents ).
- 함의: (1) aiox spec §4의 mailbox/delivery/idle 알림 설계 방향이 vendor 1st-party로
  검증됨, (2) single-vendor 협업 시장은 vendor가 직접 가져감 → aiox의 생존 공간은
  **cross-vendor local 협업**으로 좁혀지고 동시에 명확해짐.

생태계 지도:

- **Conductor** (conductor.build): Claude Code/Codex/Cursor 병렬 + worktree 격리 +
  머지/PR GUI. 데스크톱 오케스트레이션 선점.
- **kanbots** (481★, MIT): kanban GUI로 11종 CLI agent 디스패치, per-run worktree,
  stream-JSON 파싱. agent 간 대화가 아니라 task dispatcher — aiox와 카테고리 다름.
- **microsoft/apm** (2.8k★, MIT): agent 설정 의존성 관리자 — instructions/skills/MCP/
  hooks를 `apm.yml` manifest로 선언, lockfile, policy 거버넌스. multi-agent
  orchestration 아님. **aiox §6 compose·§7 capability projection과 정면으로 겹침** —
  §6/§7 자작 전에 차별화/연동 검토 필요한 선행 사례.
- microsoft/conductor: GitHub Copilot SDK + Anthropic Agent SDK로 YAML multi-agent
  workflow — MS도 이 공간 진입.
- multiclaude(Dan Lorenc), swarms 등 오픈소스 다수. tmux send-keys류 스크립트 다수.

상업화 환경 변수:

- **Anthropic 빌링 분리 (2026-06-15 시행)**: Claude 구독이 1st-party tool용과
  3rd-party agent/SDK용 풀로 분리, 3rd-party는 월 Agent SDK credit($20 Pro/$100 Max5x/
  $200 Max20x) 차감 (https://the-decoder.com/claude-subscriptions-get-separate-budgets-for-programmatic-use-billed-at-full-api-prices/ ).
  aiox는 Claude Code TUI 자체를 띄우므로 1st-party 사용으로 계산될 가능성이 높지만
  (Conductor "Big Terminal Mode 영향 없음" 유사), SDK/headless 경로로 전환하면 3rd-party
  풀에 걸림 — **ingress를 headless/SDK로 바꾸는 선택지의 경제성에 직접 영향**.
- 이 카테고리 오픈소스 대부분 수익화 없음(MIT). GUI 제품(Conductor)만 유료화 시도.
