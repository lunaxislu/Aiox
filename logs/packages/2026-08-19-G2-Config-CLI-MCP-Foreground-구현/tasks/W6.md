#### Corrected ownership and observable result

```text
HostController / production terminator
  └─ hostId + agentName에 serial signal intent 1건 기록
       └─ 기존 daemon API/socket
            └─ hosted aiox claude/codex wrapper가 자신의 ChildProcess에 signal 전달
                 └─ 성공 delivery ack 기록
                      └─ terminator가 ack 뒤에만 다음 window/grace 시작
                           └─ 기존 자연 종료 detach로 host-agent row 소멸 확인
```

- Raw PID는 저장하거나 외부 process에서 사용하지 않는다. Vendor child의 실제 `ChildProcess`를
  소유한 hosted wrapper만 signal을 전달한다.
- Intent는 last-value overwrite가 아니라 agent별 monotonically ordered serial delivery다. 아직
  ack되지 않은 intent가 있으면 다음 intent를 덮어쓰거나 앞질러 기록하지 않는다.
- Wrapper는 spawn된 자신의 child에만 현재 pending intent를 전달한다. `child.kill(signal)`이
  `true`를 반환한 경우에만 같은 sequence의 delivery ack를 기록한다. `false` 반환이나 throw는
  ack가 아니며 pending intent를 보존해 retry/failure policy가 실제 상태를 숨기지 않는다.
- Terminator는 request write가 아니라 같은 host/agent/sequence의 successful delivery ack를
  기다린다. Double-press/grace/force-confirm 시간은 해당 signal의 ack 뒤부터 계산한다.
- Starting agent에 먼저 기록된 intent는 child spawn 뒤 owning wrapper가 전달할 수 있어야 한다.
  Host A/Host B/standalone 동명 agent는 host-qualified identity로 격리한다.

#### Delivery and confirmation policy

```text
Codex:  enqueue SIGINT → delivery ack
        → 5000ms 동안 row absence 확인
        → enqueue SIGKILL → delivery ack
        → 2000ms 동안 row absence 확인 → 아니면 실패

Claude: enqueue SIGINT → delivery ack
        → 1000ms 동안 row absence 확인
        → enqueue second SIGINT → delivery ack
        → 5000ms 동안 row absence 확인
        → enqueue SIGKILL → delivery ack
        → 2000ms 동안 row absence 확인 → 아니면 실패
```

- Row가 intent 요청이나 ack 대기 중 먼저 사라지면 termination 성공이다. Intent request/ack transport
  실패나 delivery 불가가 row 소멸로 확인되지 않으면 성공으로 보고하지 않는다.
- 공개 vendor report는 terminal Ctrl+C와 외부 OS SIGINT가 동일하거나 version 간 안정적임을
  증명하지 않는다. AIOX acceptance는 wrapper가 신호를 실제 child에 전달하고 프로세스 소멸을
  관찰하는 데 한정하며 vendor hook/interactive semantics는 residual uncertainty다.

#### Atomic terminate-all invariant

- `completeTerminateAllAndUnregisterHost`는 claimed request의 controller ownership과 함께
  `request.hostId === supplied hostId` 및 `request.kind === "terminate_all"`을 transaction 안에서
  검증한다.
- Host A의 requestId와 Host B의 hostId 조합 또는 non-`terminate_all` request는 structured failure를
  반환하고 request/host를 하나도 변경하지 않는다.

- `new|add|remove|route|list`는 positional host name 예약어다.
- Parser는 token shape, required/duplicate/unknown flag, enum, non-empty value, minimum block
  count를 검증한다. CLI-only create의 cross-reference semantics는 기존 config semantic
  validator를 공통 source로 재사용한다.
- Running-host mutation validation은 current snapshot, natural exit, explicit remove, overlapping
  route union을 반영한다. Exact helper/type/file name은 구현자 재량이다.

#### Agent and route runtime

```text
daemon attach/runtime prepare → starting
기존 agent CLI vendor spawn success → ready
vendor spawn failure 또는 TUI exit → detach → row + incident edges 삭제
```

- DB row 존재나 surface create는 ready 증거가 아니다.
- Effective topology는 named groups/directed overrides의 합집을 ready agent 집합에서 계산한다.
- Natural TUI exit은 runtime row/edge만 제거하고 group membership을 보존한다.
  같은 이름이 다시 ready가 되면 재참여한다.
- Explicit remove는 membership과 관련 directed override도 제거한다.

#### Failure contract

- Invalid YAML/CLI: daemon/DB/surface side effect 없이 구체 진단 + exit 1.
- Static integration failure: daemon/host/agent/surface side effect 없이 원인 + help URL +
  `No agents were started.` + exit 1.
- Dynamic preflight failure: daemon은 남을 수 있지만 host/agent/surface는 없고 같은
  integration 진단 + exit 1.
- N번째 agent failure: 그 agent runtime/attachment만 정리하고 성공 agent와 ready subset
  routes는 계속한다. 생성된 surface에는 관여하지 않는다.
- All-agent failure: host/agent/effective routes runtime을 삭제하고 daemon과 이미 생성된
  surface에는 관여하지 않은 채 host exit 1.
- Integration help message/URL은 중앙 mapping/formatter가 소유하고 category 간 automatic
  fallback은 없다.
- Integration 진단의 정확한 문구, error code, README/GitHub URL과 product anchor는
  위 필수 요소와 중앙 관리 경계 안에서 구현자가 정한다. 일반 YAML/CLI validation 오류에는
  help URL을 강제하지 않는다.

#### Stage 5C execution contract — named routes, effective edges, running mutations

Objective:

```text
other shell host add/remove/route
→ existing daemon request relay + name/path host lookup
→ foreground HostController validates the full current snapshot and batch
→ agent declarations + named groups/directed overrides mutate
→ ready agents intersect declared topology
→ daemon flattened effective edges synchronize
→ structured result returns to the requesting CLI
```

- Observable contract:
  - `host add`는 repeated agent blocks와 optional route blocks를 한 batch로 처리한다. 전체 batch의
    구조·현재 snapshot reference validation은 side effect 전에 끝나고, 그 뒤 실제 agent surface
    launch failure는 agent-local이다.
  - named group은 member pair의 양방향 edge를, directed override는 선언된 방향 edge를 만든다.
    overlapping groups/overrides의 같은 edge는 union으로 한 번만 존재하며 하나의 group을 제거해도
    다른 선언이 요구하면 유지된다.
  - effective edges는 현재 `ready` agent 집합과 선언 topology의 교집합이다. Natural exit은 runtime
    row/incident effective edges만 제거하고 membership/override declaration을 보존하며 같은 name이
    다시 ready가 되면 재참여한다.
  - explicit `host remove` 성공은 agent declaration, group membership과 해당 agent가 source/target인
    directed overrides를 함께 제거한다. 다른 host/standalone의 동명 agent에는 영향이 없다.
  - `host route` add/direct/remove는 현재 host snapshot 기준으로 검증되고, 성공 결과가 반환되기 전에
    controller declaration과 daemon effective edges가 일치해야 한다.
  - 관리 CLI는 기존 daemon socket/request-result relay와 0/1/N name lookup + `--path`
    disambiguation을 재사용한다. 별도 coordinator/socket/process를 만들지 않는다.
- Failure and commit contract:
  - invalid batch, unknown/duplicate agent, dangling/non-member/self-loop route, conflicting route
    mutation은 side effect 없이 구조화된 실패로 반환한다.
  - `host add`의 validation 통과 뒤 개별 launch failure는 성공 agent와 유효 route declaration을
    되돌리지 않고 agent별 결과로 반환한다. 실패 agent는 ready subset에 없으므로 effective edge에
    참여하지 않는다.
  - explicit remove에서 runtime termination/detach가 실패한 agent는 declaration과 effective state를
    유지하고 실패로 반환한다. 성공한 agent만 declaration과 topology에서 제거한다.
  - declaration mutation과 effective-edge sync가 실패하면 성공으로 보고하지 않는다. 기존
    controller/daemon state를 불일치시킨 채 commit하지 않도록 현재 owner primitive를 추적해 가장
    작은 transactional 또는 rollback 경계를 사용한다.
- Required source trace:
  - parsed/normalized `host-add|host-remove|host-route` → CLI invocation → daemon
    `submit/takeHostControlRequestResult` payload/result.
  - `HostController.handleNextControlRequest()`, existing adapter launch and runtime terminator,
    `reconcile()` ready snapshot.
  - daemon/store route owner, host-qualified routable agent IDs, incident-edge cleanup and socket schema.
  - parser/normalizer current-snapshot validation boundary and user-facing result/error formatting.
- Allowed write-set:
  - Stage 5C에 직접 필요한 `src/cli/**`, `src/core/**`, `src/daemon/**`, `src/store/**`, `src/host/**`.
  - 위 source의 focused regression을 위한 `tests/unit/**`, 필요한 기존 integration test의 running
    mutation/effective-edge slice.
  - Stage 5C execution trace/candidate result를 위한 이 W6 task record.
  - 추가 dependency, product adapter, architecture/spec/plan/controlling log 수정은 허용하지 않는다.
    owner drift는 수정하지 말고 candidate effect로 보고한다.
- Required TDD increments:
  1. current-snapshot validation과 no-side-effect invalid mutation.
  2. named group + directed override union을 ready host-qualified IDs의 effective edges로 sync.
  3. natural exit 후 declaration 보존과 same-name re-ready 재참여.
  4. `host add` mixed batch, agent-local launch failure와 route result.
  5. `host remove` 성공/termination failure의 partial result 및 declaration cleanup.
  6. `host route` add/direct/remove overlap reconciliation.
  7. 다른 shell의 socket-backed request/result와 name/path lookup E2E.
- Excluded:
  - Stage 5D production foreground polling/control loop, production runtime terminator와 host-new
    foreground completion.
  - YAML Stage 6, product adapters Stage 7–9, W7 `aiox quit`.
  - compatibility alias/fallback/dual-read-write, generic event bus, persistent HostDefinition.
- Verification:
  - increment별 실제 RED → 최소 GREEN → focused regression.

    tests, full vitest, `git diff --check`, W6 Markdown/log/package integrity.

Discovery facts (이번 contract review에서 source 직접 확인, 추측 아님):

- `case "host-new"`/`case "host-list"`(`src/cli/invocation.ts:476-481`)는 여전히 명시적
  not-implemented stub이다. 프로덕션 코드 어디에도 `createHostController`/`createAdapterRegistry`
  호출이 없고, `AgentRuntimeTerminator`(`src/host/agent-runtime-terminator.ts`)는 인터페이스와
  fake(`fake-agent-runtime-terminator.ts`)만 있고 실제 구현이 없다(grep 확인).
- `case "host-add"/"host-remove"/"host-route"`(`invocation.ts:441-475`)는 이미
  `submitHostControlRequest`/`waitForHostControlResult`로 relay하지만, 이 request를 claim하는
  foreground loop가 아직 없어 오늘 기준 production에서는 이 요청들이 완료되지 않고 daemon에
  pending으로 남는다 — Stage 5D가 이 gap의 유일한 소비자다.
- Vendor 프로세스(실제 `claude`/`codex` 바이너리)는 daemon도 HostController도 아닌 surface의
  `aiox claude/codex --host-id` CLI 프로세스가 `child_process.spawn`으로 직접 소유한다
  (`src/adapters/claude/launcher.ts:112`, `src/adapters/codex/launcher.ts:50/99`). 그 CLI
  프로세스는 ready 보고 후 daemon에 아무것도 poll하지 않고
  `waitForHostedTuiExit(child, onReady)`를 그냥 await하며 blocking wait한다
  (`invocation.ts:227-249,300-320`).
  daemon/HostController는 이 vendor 프로세스의 PID를 전혀 모른다(grep 확인 — 기존 `pid` 필드는
  daemon 자신의 PID(`aiox status`)뿐).
- `ClaudeChannelRuntime`(`src/daemon/state.ts:58-64`)은 메타데이터(agentId/endpoint/tokenHash)뿐이고
  dispose()/kill 핸들이 없다. Codex의 `codexRuntime`(app-server)은 daemon이 직접 소유한 별도
  child process라 `disposeRuntime()`으로 죽일 수 있지만, 이건 vendor TUI 자체가 아니라 TUI가
  연결하는 backend다.
- `host --list`는 대응하는 `api.listRunningHosts()`가 이미 Stage 3에 있어(`src/daemon/api.ts:129,600`)
  설계 공백이 아니라 단순 wiring 누락이다.

Termination design decision (사용자 확인 완료, 2026-08-31 세션 — 순서대로 검토·기각·재검토됨):

- 최초 검토안(daemon polling)은 기각했다: surface CLI 프로세스가 daemon을 향해 "종료 요청됐나?"를
  반복 poll하는 새 request kind를 추가하는 안이었으나, AIOX가 전부 로컬 데스크톱 앱만 지원하는
  전제(Category A/B/C 전부 로컬) 아래에서는 불필요했다 — 같은 머신의 어떤 프로세스든 PID만
  알면 `process.kill(pid, signal)`로 직접 signal을 보낼 수 있어(부모-자식 관계 불필요) poll이나
  새 request kind 없이도 termination이 가능함을 재검토로 확인했다.
- Ctrl+C(SIGINT) 재현이 실제 vendor 종료 경로로 확인됐다: Codex는 SIGINT 1회가 세션 전체를
  즉시 종료시킨다(공개 이슈 `openai/codex#1245`, `#14708`). Codex는 SIGTERM도 SIGINT(Ctrl-C)와

race가 생겨 테스트가 타이밍에 의존하게 된다. 대신 ready/exit는 항상 `start()` 완료 이후 도착하는
비동기 이벤트로 다루고, `controller.listAgents()`로 현재 starting/ready subset을 언제든 조회할 수
있게 했다. Increment 2의 "성공 결과가 ready agent subset을 제공" 요구는 이 live-query seam으로
충족했다 — `start()`의 return payload 자체를 ready 완료까지 블로킹하지 않는다. 이 판단을
공개한다(사용자가 다른 semantics를 의도했다면 정정 대상).

#### N번째 surface/CLI 실패, all-agent 실패

- N번째 `createSurfaceAndStart` 실패(surface/cli-start 두 stage 모두 HostController 관점에서는
  단일 reject) → `api.detachHostAgent`만 호출, 앞선 성공 agent는 `trackedAgents`에 그대로 유지,
  다음 agent 계속 시도.
- 선언된 agent 전원이 launch 실패(`request.agents.length > 0 && startedCount === 0`) →
  `api.unregisterRunningHost` 호출 후 컨트롤러 내부 상태 clear, `stage: "all_agents_failed"`.
- 개별 agent의 ready 이전/이후 exit(`onExit`)은 `trackedAgents`에서 제거 + `api.detachHostAgent`만
  수행 — 다른 agent, 다른 host, standalone agent에 관여하지 않는다.
- surface close는 애초에 `HostAdapterSurfaceHandle`에 존재하지 않는 method다(구조적으로 호출
  불가) — 별도 검증 테스트로 이를 명시했다.

#### control request claim/complete seam

`handleNextControlRequest()`가 컨트롤러 자신의 `hostId`/`controllerId`로 `api.claimHostControlRequest`
호출 → `terminate_all`은 실제 terminate-all을 수행하고 `{ok:true}`로 complete, `host_add`/
`host_remove`/`host_route`는 claim은 하되 `{ok:false, reason:"not_supported_in_current_stage"}`로
**명시적으로 complete**(pending 방치 없음, placeholder success 아님). 구현 중 실제 버그를
발견·수정했다: `terminate_all`을 관계 릴레이로 처리할 때 먼저 `unregisterRunningHost`부터 부르면
그 트랜잭션의 `failAllInFlightForHost`(Stage 3 accepted)가 지금 처리 중인 이 request 자체를
`claimed`→`failed`로 먼저 바꿔버려, 뒤이은 `completeHostControlRequest`가
`host_control_request_not_claimed`로 실패한다 — 요청자가 성공 대신 실패를 보게 되는 순서
버그였다. **complete를 먼저, unregister를 나중**으로 고쳤고, mutation spot-check(순서를 일부러
되돌려 해당 테스트가 정확히 이 증상으로 RED가 되는지 확인)로 교차 검증했다.

#### terminate-all primitive

추적 중인 모든 handle에 대해 먼저 `trackedAgents`에서 제거(pre-clear, `requestTermination()`의
side effect로 `onExit`가 동시에 fire해도 재감지 없이 no-op) → `handle.requestTermination()`
best-effort 전체 요청 → `api.unregisterRunningHost` → 내부 상태 clear. 두 번째/세 번째 호출은
`hostId===null`을 먼저 보고 매번 결정적으로 `{ok:false, reason:"host_not_running"}` 반환(daemon
재검증 없이 short-circuit, 중복 unregister 없음). 다른 host/standalone agent에는 관여하지
않는다 — 통합 테스트로 두 host를 동시에 띄우고 한쪽만 terminate한 뒤 다른 쪽이 그대로임을
직접 확인했다.

#### HostAdapter에서 제거한 책임 / daemon 상태 기반 observation 흐름

```text
surface + CLI start 성공
  → host agent는 starting (registerRunningHost가 이미 기록)

기존 agent CLI가 daemon에 vendor spawn 성공 보고 (Stage 5+, 이번 범위 밖)
  → daemon host agent ready (markHostAgentReady)
  → controller.reconcile()이 api.listHostAgents(hostId)로 관찰
  → 로컬 tracked 상태 ready로 갱신

기존 agent CLI가 detach/자연 종료 보고 (Stage 5+, 이번 범위 밖)
  → daemon host agent 삭제 (detachHostAgent)
  → controller.reconcile()이 관찰
  → 해당 agent가 로컬 tracked 목록에서 제거
```

`reconcile()` 호출 시점/주기(polling interval, foreground loop UX)는 고정하지 않았다 — Stage 5
설계 몫으로 남겨뒀다. `start()`는 여전히 개별 agent의 ready를 기다리지 않는다(non-blocking
start 유지, Stage 4 candidate의 기존 결정과 동일).

#### direct/relayed terminate-all 성공·실패

```text
terminateAll() / relayed terminate_all
  → tracked 전체에 대해 terminator.terminate(hostId, agentName)
  → 성공한 agent: detachHostAgent + tracked 제거 (즉시, 결과 판정 전)
  → 전원 성공
      direct:  unregisterRunningHost → resetState → {ok:true, hostId}
      relay:   complete({ok:true}) 먼저 → unregisterRunningHost → resetState
               (Stage 4 candidate가 고친 "complete 먼저, unregister 나중" 순서를 유지)
  → 1개 이상 실패 (unregister/resetState 하지 않음, host와 실패 agent 그대로 유지)
      direct:  {ok:false, reason:"termination_failed", failures:[{name, reason}, ...]}
      relay:   complete({ok:false, failures:[{name, reason}, ...]}), host 유지
```

다른 host/standalone agent는 이번 correction에서도 관여하지 않는다(신규 테스트로 확인).

#### Blocker 3 — terminate-all result와 unregister 정합

- 원인: candidate의 relayed `terminate_all`이 `completeHostControlRequest({ok:true})`를 먼저
  호출해 requester가 성공을 관찰하게 한 뒤 `unregisterRunningHost()`를 실행하고 그 결과를 무시했다
  — unregister가 실패해도 requester는 이미 success를 받은 뒤였다. Direct `terminateAll()`도
  `unregisterRunningHost()` 결과와 무관하게 항상 `resetState()`를 호출해 실패해도 controller
  identity를 잃었다.
- 왜 "complete 먼저"였는지(과거 Stage 4 교훈)와 단순히 순서만 뒤집을 수 없는 이유: Stage 3
  accepted `unregisterRunningHost()`는 자신의 트랜잭션 안에서 해당 host의 모든 in-flight
  request를 `failAllInFlightForHost()`로 강제 실패시킨다. Unregister를 먼저 부르면 지금 처리
  중인 바로 이 `terminate_all` request 자신이 아직 `claimed` 상태라 그 정리 로직에 걸려
  `failed`로 먼저 바뀌어 버리고(Stage 4가 이미 겪은 자기충돌 버그), 뒤이은 `completeHostControlRequest()`가
  `host_control_request_not_claimed`로 실패한다.
- 해결(신규 원자 daemon operation, 새 socket/coordinator 아님): `src/daemon/host-runtime.ts`에
  `completeTerminateAllAndUnregisterHost({hostId, requestId, controllerId, successResult})`를
  추가했다. 하나의 트랜잭션 안에서 (1) 대상 request를 먼저 `completed`로 전이시키고(이후
  `failAllInFlightForHost`의 `status in ('pending','claimed')` 필터가 더 이상 이 request를
  건드릴 수 없게 만듦), (2) host row를 제거하고, (3) 나머지 in-flight request를 기존과 동일하게
  `host_unregistered`로 정리한다. Host가 이미 없으면 같은 트랜잭션에서 대상 request를
  `{ok:false, reason:"host_not_running"}`으로 completed 처리하고
  `{ok:true, unregistered:false, reason:"host_not_running"}`을 반환한다 — request가 미해결로
  남는 경우가 없다. `src/daemon/api.ts`에 동일 이름으로 매핑 wiring(`mapRunningHost`/`mapHostAgent`
  재사용)을 추가했다. 소켓 dispatch는 `Object.hasOwn(api, method)` 기반 범용 dispatcher라
  `socket-transport.ts` 자체는 무수정이다.
- `HostController.handleNextControlRequest()`의 `terminate_all` 분기: 전체 agent 성공 시
  `completeTerminateAllAndUnregisterHost()`를 호출해 `{ok:true, unregistered:true}`일 때만
  `resetState()`한다. 호출이 reject하거나 `{ok:true, unregistered:false}`/`{ok:false}`이면
  identity를 그대로 유지하고 requester에게 structured failure(`host_unregister_failed` 또는
  daemon이 준 reason)를 반환한다.
- `HostController.terminateAll()`(direct): `unregisterRunningHost()` 호출을 try/catch로 감싸고,
  reject 또는 `{ok:false}` 모두 `{ok:false, reason:"host_unregister_failed", detail}`을 반환하며
  `resetState()`를 호출하지 않는다. `TerminateAllResult`에 이 reason을 추가했다.
- RED(mutation으로 확인, 실제로 원복 전 실행): `host-controller-control.test.ts`의 direct
  terminateAll 신규 테스트 2건 — `resetState()`를 unregister 결과 확인 전에 무조건 호출하도록
  되돌리자 두 테스트 모두 실제로 RED(하나는 성공 result가 반환됨, 하나는 identity가 null로
  사라짐)로 확인한 뒤 원복해 GREEN 재확인.
- GREEN: `vi.spyOn`으로 (a) `unregisterRunningHost` reject, (b) `unregisterRunningHost`
  `{ok:false}`, (c) `completeTerminateAllAndUnregisterHost` reject, (d)
  `completeTerminateAllAndUnregisterHost`가 `{unregistered:false}` 반환 — 4가지 경우 모두
  controller identity 보존 + structured failure 반환을 확인. 성공 경로는 실제 daemon state로
  request completed와 host 소멸이 항상 함께 관찰됨(원자성)을 별도 테스트와
  `host-runtime-api.test.ts`의 소켓 E2E 테스트로 확인.

#### Blocker 4 — raw PID 직접 signal 제거

- 원인: candidate가 ready 시점 vendor child의 PID를 `host_agents.pid`에 1회 기록하고,
  `AgentRuntimeTerminator`(HostController와 같은 프로세스)가 그 PID로 직접
  `process.kill(pid, signal)`을 호출했다. Vendor exit와 detach report 사이 또는 wrapper 비정상
  종료 시 그 PID가 stale해질 수 있고, OS가 재사용한 PID에 signal이 갈 수 있다.
- 해결(사용자가 지정한 책임 흐름 그대로 구현, 새 socket/coordinator/generic event bus 없음):
  vendor child의 실제 OS-level 소유자는 항상 hosted `aiox claude/codex --host-id` CLI 프로세스뿐이다.
  `AgentRuntimeTerminator`는 이제 PID를 전혀 모르고 기존 daemon API에 `(hostId, agentName)` 스코프
  termination intent만 기록하며, hosted CLI가 자신이 소유한 `ChildProcess` handle에 그 intent를
  적용한다.
  - `src/store/repositories/host-agents.ts`/`src/daemon/host-runtime.ts`: `pid` 필드와
    `MarkHostAgentReadyRequest.pid`(필수였음)를 완전히 제거했다(pre-v1, compatibility 필드 유지
    안 함). 대신 `pendingSignal: NodeJS.Signals | null` + `pendingSignalSeq: number`(매 요청마다
    증가 — 같은 신호명이 반복돼도 "새 intent"로 구분 가능, Claude 2회째 SIGINT에 필요)를 추가하고,
    신규 `requestTermination({hostId, name, signal, now})` repository 메서드와
    `requestHostAgentTermination` host-runtime/API 메서드를 추가했다.
  - `src/store/schema.ts`: migration 10(candidate가 이번 세션에서 추가해 아직 커밋되지 않은 것)을
    `pid` 컬럼 추가에서 `pending_signal`/`pending_signal_seq` 컬럼 추가로 그 자리에서 재정의했다
    — 이미 릴리스된 적 없는 uncommitted migration이라 11번을 새로 만들지 않고 10번 자체를
    고쳤다.
  - `src/daemon/api.ts`: `HostAgentDto.pid` 제거, `pendingSignal`/`pendingSignalSeq` 추가.
    `requestHostAgentTermination` API 메서드 추가(`mapHostAgentTransition` 재사용).
  - `src/host/production-agent-runtime-terminator.ts` 전면 재작성: `sendSignal`/`process.kill`
    옵션과 `agent.pid === null` 조기 실패(`agent_pid_unknown`)를 전부 제거했다. 이제 각 신호
    라운드마다 `api.requestHostAgentTermination()`을 best-effort로 호출(throw해도 swallow —
    row-absence poll이 여전히 유일한 권위)하고 동일한 `isAgentGone`/`waitUntilGone` polling으로

#### Foreground loop 보강

- `src/host/host-foreground-loop.ts`: tick이 throw하면(예: 진짜 daemon 연결 끊김, 실제
  `reconcile()`/`syncHostEffectiveRoutes` 실패) 기존처럼 stderr에 로그만 남기고 무한히 계속
  재시도하는 대신, loop를 즉시 멈추고 신규 필수 콜백 `onFatalError(error)`를 정확히 1회 호출한다.
  `reconcile()`과 control request 처리는 기존 `ticking` 재진입 방지 플래그로 계속 겹치지 않고,
  idle 상태 busy-spin 없음도 유지된다. 성공적인 terminate-all은 여전히 `onTerminated()`로만
  종료된다.
- `src/cli/invocation.ts`의 `case "host-new"`: foreground loop를 감싸는 Promise에 `reject` 경로를
  추가해 `onFatalError`가 실제 `InvocationError`(exit 1, 원인 메시지 포함)로 표면화되도록 했다 —
  이전에는 이 콜백 자체가 없어 이런 실패가 로그만 찍고 프로세스가 조용히 계속 도는 상태였다.
- RED: `host-foreground-loop.test.ts`의 "reports a tick failure to stderr and keeps ticking
  afterward"(기존, 정확히 이 잘못된 동작을 검증하던 테스트)를 "a tick failure stops the loop and
  reports it through onFatalError exactly once, instead of retrying forever"로 재작성했다 — 이
  변경 자체가 명세 위반을 고정하던 테스트를 새 계약에 맞게 correction한 것이다. `onTerminated`가
  두 번째 호출되지 않는지 확인하는 회귀 테스트도 추가했다.
- GREEN: tick throw → 정확히 1회 `onFatalError` 호출 + loop 정지(이후 tick 없음) + stderr에 원인
  기록 확인.
