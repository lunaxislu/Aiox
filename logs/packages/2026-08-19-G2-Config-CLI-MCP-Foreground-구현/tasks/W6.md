- Objective: `aiox host`는 cwd의 `aiox.yaml`을 전체 검증한 뒤 `agents[]`의 모든
  agent를 각각 vendor-native foreground TUI로 실행하고, TUI/runtime readiness에 성공한
  agent들 사이에 `routes[]` topology를 연결하며, host가 이 process·signal·cleanup
  lifecycle을 소유한다.
- Observable result:
  - `type: codex`의 각 agent는 각각 Codex TUI process/UI로 보여야 한다.
  - `type: claude-code`의 각 agent는 각각 Claude TUI process/UI로 보여야 한다.
  - Claude는 기존 `launchClaudeStaticMcpChannel()` 계약, 즉 optional
    `--append-system-prompt <text>` +
    `--dangerously-load-development-channels server:<channel>` argv와 agent identity env를
    사용한다.
  - `--bg`, background session id, `claude stop`, resume/attach를 기본 host 경로에
    사용하지 않는다.
- Composition:
  ```text
  aiox host control plane
  ├─ config load + semantic validation
  ├─ signal ownership
  ├─ agent-local prepare/attach
  ├─ agent-local vendor TUI launch/readiness
  ├─ successful-agent route wiring
  └─ watcher + agent-local/global cleanup

  view launch consumer
  ├─ agent A distinct terminal surface → Codex/Claude TUI
  ├─ agent B distinct terminal surface → Codex/Claude TUI
  └─ agent N distinct terminal surface → Codex/Claude TUI
  ```
- Execution order:
  1. `loadAioxConfig(cwd)` → `validateAioxConfigSemantics(config)`. 이 단계 실패는 lifecycle
     side effect 전 global failure다.
  2. 첫 lifecycle side effect 전 SIGINT/SIGTERM handler를 등록한다.
  3. agent별로 attach에 필요한 runtime/token을 준비하고 해당 agent의 distinct view에
     vendor TUI를 실행한다. TUI readiness까지를 해당 agent의 하나의 시도로 본다.
  4. TUI launch/readiness 실패는 agent-local이다. 해당 agent의 runtime/token/row/incident
     route/view만 awaited cleanup하고 진단을 출력한 뒤 다음 agent launch를 계속한다.
     이미 성공한 TUI/agent를 rollback하지 않는다.
  5. 모든 launch 시도 후 readiness/등록 성공 agent 집합으로 route를 구성한다.
     mesh route는 성공 member들 사이에 유지하고, directed edge는 from/to 둘 다
     성공한 경우만 연결한다. 한 connect 실패는 그 edge/source 진단으로 남기고
     다른 연결과 TUI를 계속 유지한다.
  6. watcher는 TUI/runtime unexpected loss를 agent-local departure로 처리하여 해당
     agent/incident route/view만 정리하고 나머지를 계속 유지한다.
  7. SIGINT/SIGTERM/명시적 host 종료에서만 현재 성공 집합 전체를 정리한다.
     watcher 중지 → TUI/view 종료 → agent detach/route 제거 → signal handler 제거 순서를
     지키고 cleanup은 정확히 한 번만 수행한다.

**C. signal↔loss 양방향 cleanup race — 수정**

- 결함(재확인): `cleanUpAll()`이 `pendingLossCleanups`를 `await Promise.allSettled([...])`로 정확히
  한 번만 snapshot한다(빈 배열이어도 `await`는 항상 최소 1 microtask tick을 yield함). signal→loss
  순서에서 이 한 번의 await가 yield하는 그 정확한 gap에 loss가 등록되면(agent를 `active`에서
  동기적으로 먼저 삭제) 그 loss cleanup은 이미 소비된 snapshot에도, 아직 찍히지 않은 `active`
  snapshot에도 잡히지 않아 완전히 untracked가 된다.
- Red: `tests/unit/cli/host.test.ts`에 결정론적 microtask-timing 테스트 추가 — a,b가 active인 채
  foreground에서 signal 발생 → 정확히 2번 중첩된 `queueMicrotask`(빈 pendingLossCleanups snapshot
  이후 그 await가 풀리기 직전 지점에 착지하도록 실측으로 보정, 테스트 주석에 근거 명시) 뒤 b의
  view loss 발생 → b의 `detachAgent`는 controllable(외부에서 resolve하는) promise로 pending.
  실행 결과 `hostSettled`가 gate를 열기 전에 이미 `true`로 관찰되어(기대 `false`) 정확히 서술된
  race로 실패.
- 수정: `cleanUpAll()`의 단일 await를 `for(;;)` 루프로 재작성 — `pendingLossCleanups`가 비어있지
  않으면 그것만 await하고 `continue`(재확인), 비어있으면 그제서야 `active`를 snapshot+clear하고
  그 배치를 cleanup한 뒤 루프 top으로 돌아가 다시 `pendingLossCleanups`를 확인한다. 두 snapshot이
  같은 synchronous 구간에서 연달아 일어나 그 사이에 아무것도 끼어들 수 없는 지점(빈 pending 확인
  직후, await 없이 바로 이어지는 active snapshot)에서만 루프가 종료된다. 무한 대기나 임의 timeout은
  추가하지 않았다 — 루프는 실제 in-flight agent cleanup 수만큼만 반복되고 종료를 보장한다.
- Green: 신규 테스트 PASS — `hostSettled`가 gate 개방 전 `false`, `order`에 `detach:b:end`가
  gate 개방 전 없음, gate 개방 후 host가 resolve하고 a/b 각각 정확히 1회 detach됨을 확인. 이
