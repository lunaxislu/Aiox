- Attempt 1 source/owner trace completed. The current UDS server appends decoded chunks to a per-connection string and splits only on newline (`src/daemon/socket-transport.ts:62-87`); completed lines are parsed only afterward and parse failure already uses `id:"unknown"` (`:180-205`, `:245-278`). The persistent client multiplexes request IDs and ignores unmatched response IDs, then rejects every pending request when the socket closes (`:287-378`). The Claude ingress accumulates every raw request chunk before UTF-8 decode/JSON parse (`src/adapters/claude/channel-server.ts:565-582`, `:733-751`), while the injector serializes `{content}` and maps every explicit non-2xx, including a future 413, to `claude_channel_push_failed` (`src/adapters/claude/injector.ts:32-52`). Owner documents fix NDJSON framing, a 30 s client timeout, canonical UTF-8 text, and the Claude 202/400/404 plus non-2xx failure meaning, but no request/body byte maximum (`docs/decisions/uds-transport-and-framing-contract.md:7-24`; `docs/architecture/local-runtime-daemon-transport-api.md:41-54`; `docs/architecture/local-runtime-claude-adapter.md:175-204`; `docs/specs/aiox-message-lifecycle.md:11-83,421-443`).
- Attempt 1 policy synthesis: recommend a 1 MiB (1,048,576-byte, delimiter excluded) daemon request-line ceiling and a separately justified 4 MiB (4,194,304-byte, complete encoded body) Claude `/send` ceiling. These are candidate release policies, not recovered governing facts. The UDS value caps one interactive RPC line while remaining far above the directly inspected protocol/test examples; the HTTP value accounts for the second JSON serialization of canonical envelope text. A Node built-in calculation over 100,000 repeated ASCII, backslash, newline, Korean and emoji characters observed HTTP-body/request-line byte ratios of about 1.00, 2.00, 1.50, 1.00 and 1.00 respectively, so using the same numeric ceiling would reject some daemon-accepted escape-heavy messages. Four MiB leaves framing margin above the observed approximately 2x expansion without introducing configuration.
- Attempt 1 lifecycle synthesis: any UDS over-limit line is connection-fatal because safe request identity is unavailable before parsing and parsing an already rejected oversized line defeats the boundary. Emit at most one raw NDJSON error `{id:"unknown",ok:false,error:{reason:"request_too_large",message:"Daemon socket request exceeds 1048576-byte limit"}}`, stop reading/dispatch, flush it best-effort, then destroy the offending connection; the official multiplexed client will observe close rejection because it correctly ignores unknown IDs. Both newline-before-overflow and a completed oversized line use this behavior, and no pipelined line after the first overflow is dispatched. For HTTP, reject a valid decimal `Content-Length > 4194304` before body accumulation; otherwise count every raw Buffer chunk and reject when cumulative bytes first exceed the same HTTP ceiling, including chunked input. Return `413` with `{error:"payload_too_large"}` and `Connection: close`, do not parse or notify MCP, do not drain an attacker-controlled remainder for keep-alive, and destroy after response `finish` (with error/close fallback). A local Node built-in probe confirmed this pause → 413/`Connection: close` → response-finish destroy sequence flushes the typed body and closes the connection on the current runtime.
- Attempt 1 deterministic regression seams: UDS tests should cover exact-limit fragmented UTF-8 acceptance; max+1 before newline; a completed oversized line containing an apparent ID that still yields `id:"unknown"`; oversized-first plus valid pipelined `status` proving no API invocation and close; and a fresh connection succeeding afterward. HTTP tests should cover exact-limit `Content-Length` acceptance, declared over-limit pre-rejection without notification, chunked exact-limit acceptance, chunked max+1 413/close/no notification, and a fresh connection succeeding. Injector regression should assert HTTP 413 remains the existing explicit `claude_channel_push_failed` result, not unavailable/unconfirmed or a new delivery reason.
