- Objective: adopt a **manual retransmit attempt lifecycle model** so that one `{deliveryId, attempt, requestId}` separates a non-terminal observation from exactly one terminal outcome, **and align the operator-facing result (daemon API + MCP tool) with that lifecycle**. Event model: manual attempt start emits `delivery_manual_retransmit` (unchanged); post-write timeout / response loss / WS drop emits **`delivery_manual_retransmit_unconfirmed`** (non-terminal observation, original stays `unconfirmed`); immediate or late same-`requestId` success emits **`delivery_manual_retransmit_delivered`** (terminal, exactly one, original → `delivered`); immediate or late same-`requestId` JSON-RPC application reject emits **`delivery_manual_retransmit_rejected`** (terminal, exactly one, original stays `unconfirmed`). This removes the current double-terminal defect (a timeout emits `delivery_manual_retransmit_failed` at `src/daemon/state.ts:956`, then a late reject emits a second `delivery_manual_retransmit_failed` at `src/daemon/state.ts:1974`) and the contradictory "failed event but delivered" outcome on timeout→late-success.
- Operator-facing result model (daemon API + MCP tool) — **new in revision 2.** The daemon `retransmitUnconfirmedDelivery` result and the MCP tool text reflect the **immediate** outcome; late resolution is observed via delivery status + terminal event (the tool has already returned). Naming note: the **event** `delivery_manual_retransmit_failed` is removed; the **API result reason** string `manual_retransmit_failed` is a distinct identifier that is **retained but narrowed** to no-attempt failures only. Classifier:
  - immediate success → `ok: true` (delivered); MCP renders the existing delivered/accepted text.
  - **post-write ambiguity** (a write was issued but no correlated success/reject arrived: timeout, response loss, WS drop, binding-uncertain acknowledgement) → `ok: false, reason: "manual_retransmit_unconfirmed"` (meaning "target acceptance unknown"); MCP renders a **non-error** result conveying "manual retransmit sent for `<id>`; target acceptance unknown (unconfirmed)" — it must NOT go through `errorResult`; original stays `unconfirmed`; emits `delivery_manual_retransmit_unconfirmed`.
  - **explicit immediate JSON-RPC application reject** → `ok: false, reason: "manual_retransmit_rejected"`; MCP renders a reject-meaning result; original stays `unconfirmed`; emits `delivery_manual_retransmit_rejected`.
  - **no-attempt failure** (no write issued: unresolved target, runtime unavailable/deferred, resume failed, missing ready runtime/bound thread) → keep `ok: false, reason: "manual_retransmit_failed"` (accurate: the retransmit could not be performed); plus the existing validation reasons (`delivery_not_found`, `delivery_not_unconfirmed`, `duplicate_risk_confirmation_required`); MCP renders an error result; original delivery is unchanged; no terminal manual lifecycle event is emitted (the removed `_failed` event is not reintroduced).
  - **late resolution** (async, after the tool returned): late same-`requestId` success → status `delivered` + one `delivery_manual_retransmit_delivered`; late same-`requestId` reject → status stays `unconfirmed` + one `delivery_manual_retransmit_rejected`.
