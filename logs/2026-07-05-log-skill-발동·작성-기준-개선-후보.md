## 2026-07-05 · 개선 후보 개설 — record framing과 entry nesting

### 2026-07-05 00:19 · 사례와 개선 후보 (record framing · entry nesting)

이 로그는 이번 세션에서 관찰된 log skill 작성 기준 문제를 개선 후보로 기록한다. 아래 후보는 아직 반영안이 아니라 관찰·제안이며, 실제 skill 반영은 W1에서 loop-rules.md/maintenance.md 대조와 사용자 승인을 거친다.

#### 사례 (확인한 사실)

- `logs/2026-07-03-log-skill-package-log-model-discussion.md`의 W2 진행 중, Claude가 아직 사용자 승인 전인 Identity 초안을 "## 2026-07-04 · W2 섹션 수렴 (1) — Identity 확정"이라는 **top-level `##` entry**로, 제목에 **"확정"**을 달아 append했다.
- @user는 두 가지를 지적했다: (a) 승인 전이므로 "확정"이 아니라 Claude 제안/의견으로 재작성할 것, (b) 진행 중 작업의 하위 step이므로 top-level entry가 아니라 sub-entry로 nesting할 것.
- Claude는 해당 entry를 "## 2026-07-04 · W2 섹션별 초안 수렴 세션 — Claude 제안 (미승인, 진행 중)" 아래 "### (1) Identity — Claude 제안 (미확정)" sub-entry로 재작성했다.

#### 개선 후보 A — record framing: 승인 전 제안 vs 승인 후 확정

- 문제(확인한 사실): agent가 아직 승인 전인 제안·의견을 record에서 "확정"처럼 서술하면, 다른 agent나 다음 세션이 이미 결정된 사실로 오독할 수 있다.
- 후보(의견): Record 규칙에 "승인·결정 gate를 통과하지 않은 내용은 제안·의견으로 명시하고, 확정·결정 어휘를 쓰지 않는다"를 명문화.
- [확인 필요] AGENTS.md는 확인한 사실/추론/의견 구분을 요구하지만(Evidence And Reporting), 이것이 log record의 승인 전/후 status framing으로 loop-rules.md의 Record 규칙에 이미 반영돼 있는지는 미확인. W1에서 loop-rules.md#record와 대조한다.

#### 개선 후보 B — entry nesting: 진행 중 작업 하위 step = sub-entry

- 문제(확인한 사실): 진행 중인 한 작업 단위의 하위 step(예: 섹션별 초안 수렴의 각 섹션)을 매번 top-level `##` dated entry로 append하면, 로그 표면상 별개 작업 단위처럼 보여 진행 구조가 평평해진다.
- 후보(의견): 새 top-level block/entry는 unit이 바뀔 때만, 같은 진행 중 unit의 하위 step은 해당 block 아래 sub-entry(`###`)로 둔다는 기준을 명문화.
- [확인 필요] loop-rules.md#log-blocks가 block 분리(새 unit 여부) 판정은 소유하나, block 내부 하위 step을 sub-entry로 둘지에 대한 nesting 기준이 명시돼 있는지는 미확인. W1에서 loop-rules.md#log-blocks·#record와 대조한다.

#### 경계와 다음

- 이 로그는 후보 기록·구체화만 소유한다. log skill(SKILL.md/references/loop-rules.md)·scripts 수정은 W1에서 미반영 확인 후 사용자 승인을 받아 진행한다.
- 두 후보가 이미 반영돼 있으면 W1은 "이미 반영됨" 확인으로 닫고, 미반영이면 반영안(owner 파일·문구·검증 경로)을 제시한다.

### 2026-07-05 · 개선 후보 C — entry 하위 append tooling (package-log 대화 사례)

@user 관찰: 현재 log skill(`scripts/log`)은 로그 블록과 entry만 append하게 되어 있는데, **entry 하위에도 append**할 수 있게 해야 한다. 이 후보의 owner 축은 문서 규칙(A·B)이 아니라 **tooling(`scripts/log`)**이라 별도 Work Item(W2)이 소유한다.

#### 문제 (확인한 사실)

- `scripts/log`의 구조 추가 명령은 `block add`(새 `## date` 블록, body=stdin)와 `entry add`(블록 heading 바로 뒤 `### entry`, body=stdin)뿐이다.
- `entry add --after-line`은 반드시 기존 `## date` unit block heading을 가리켜야 한다. 실측 에러: `--after-line은 기존 날짜 unit block heading을 가리켜야 합니다.` → 기존 entry 아래나 sub-entry 뒤에 append하는 명령이 없다. block heading을 anchor로 쓰면 새 entry가 기존 entry들보다 **앞에** 삽입된다.

#### 사례 (확인한 사실) — package-log 토론 로그

- `logs/2026-07-03-log-skill-package-log-model-discussion.md`에서 `### (1)~(6)` 중첩 sub-entry, 각 `####` 하위 절, 의존 표면 map 표, 그리고 `(5) 정정`·`(6) 보강`·`(6) 결정` 같은 후속 append를 만들어야 했다.
- 이 구조는 `scripts/log`로 만들 수 없어 전부 **수동 Edit**로 처리했다. **이 개선 후보 C를 이 로그에 append하는 것 자체도 같은 이유로 수동 Edit**로 했다 — 한계의 직접 증거.

#### 개선 후보 (의견)

- `entry add`(또는 신규 `subentry add`)가 **기존 entry/sub-entry 아래에 append**할 수 있게 확장한다. append anchor를 entry heading 줄로 지정하고, 중첩 heading 레벨(`###`/`####`)을 지정할 수 있게 한다.
- 이 tooling 개선은 **개선 후보 B(진행 중 하위 step = sub-entry nesting)를 도구로 실행 가능**하게 뒷받침한다. 현재는 B를 지키려면 수동 Edit밖에 없다.

#### 경계

- 이건 **tooling(`scripts/log`)** 축 개선이다. A(record framing)·B(nesting 규칙)는 문서 규칙(loop-rules.md) 축이고, C는 그 규칙을 도구로 실행 가능하게 만드는 축이다.
- [확인 필요] 수동 Edit 우회는 가능하나 skill 원칙("도구가 지원하는 로그 구조 변경은 도구로 수행")과 어긋난다. 실제 스크립트 확장 범위(append anchor·heading 레벨·원자성·validation 정합)는 W2에서 확인·구체화한다.

### 2026-07-05 17:01 · 개선 후보 D — host 편집 정책과 log tool 사용 규칙 충돌

#### 사례와 직접 원인 (확인한 사실)

- `logs/2026-07-03-log-skill-package-log-model-discussion.md` W3 기록에서 Codex는 `Return Target: None` 추가와 W3 block/entry append를 `apply_patch`로 수행하고, 각 변경 뒤 `.agents/skills/log/scripts/log check <file>`를 실행했다.
- `Return Target`을 기존 로그에 추가하는 명령은 현재 log tool에 없으므로 그 변경은 tool 지원 밖이었다. 반면 top-level block/entry append는 `block add`와 `entry add`가 지원하므로 log skill만 보면 해당 명령을 사용해야 했다.
- 그러나 이 실행 환경의 상위 파일 편집 정책은 로컬 파일 수정에 `apply_patch` 사용을 요구한다. Codex는 하위 log skill의 “지원하는 구조 변경은 도구로 수행”보다 상위 정책을 우선해, 지원되는 append에도 log mutation 명령을 사용하지 않았다.
- 이 우회로 log tool의 atomic snapshot/concurrent-change guard와 append 후 long-log hint 경로는 실행되지 않았다. `apply_patch` context match와 사후 `log check`가 구조 정합을 확인했지만 두 guard를 동일하게 대체한 것은 아니다.

#### 개선 후보 (의견)

- 이 사례는 `scripts/log` 기능 부족으로 분류하지 않는다. host가 script mutation을 금지하거나 특정 editor를 강제하는 환경에서 생기는 **execution-policy conflict**다.
- portable 지침에 예외가 필요하다면 다음 최소 계약만 검토한다: 상위 host 정책을 우선하고 허용된 편집 수단을 사용하며, tool 우회 이유와 범위를 보고하고, 즉시 `log check`를 실행하고, bypass된 atomicity·long-log hint 같은 guard를 별도로 점검한다.
- host 정책 충돌 하나를 해결하려고 새 log command를 추가하지 않는다. W3에서 기존 `SKILL.md`/maintenance가 이 예외를 이미 포괄하는지 먼저 대조하고, 미반영일 때만 owner·문구·검증안을 제시한다.

#### Reconcile

- 기존 W1(record framing/nesting), W2(sub-entry tooling)와 원인·완료 조건이 다르므로 W3를 추가했다. 현재 재개 지점은 W1을 유지하며 이 entry는 개선 후보 기록만 수행한다.
