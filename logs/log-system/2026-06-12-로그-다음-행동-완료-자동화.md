- 반복 patch가 불필요한 token을 소비하지 않게 하고 싶다.

@codex

- 현재 log script는 `new`, `search`, `audit`, `set-status`만 제공한다. 이번 작업의
  직전 체크박스 완료 처리는 script가 아니라 `apply_patch`로 수행했다.
- script가 후속 기록을 읽고 실제 완료 여부를 판단하게 해서는 안 된다. agent나
  사용자가 완료를 판단한 뒤 구조적 변경만 명시적으로 요청해야 한다.
- 권장 최소안은 `complete-next <파일>` 명령이다. fenced code 밖에서 가장 최근의
  미완료 `- [ ] 다음:` 하나만 `[x]`로 바꾸고, 대상이 없거나 파일이 로그가 아니면
  실패한다. 변경한 항목을 출력해 호출자가 확인할 수 있게 한다.
- 새 블록의 사용자 의도, 판단, 근거, 수행·검증 결과와 새 `다음` 행동은 의미를 가진
  기록이므로 agent가 계속 작성한다. 이를 고정 CLI 인자로 만들거나 script가 생성하지
  않는다.
- 이 최소안은 기존 줄을 찾고 교체하는 patch context와 실수를 줄이지만, 새 블록의
  의미를 증류하는 token까지 없애지는 않는다. `complete-next + append` 결합 명령은
  실제 반복 비용이 더 확인될 때만 후속으로 검토한다.
- 구현 시 script usage·dispatch, fenced code 제외 로직 재사용, 성공·실패 회귀 테스트와
  log skill의 도구 명령 목록 갱신이 필요하다.

- Revised: `complete-next <파일>` 단독 명령 -> 자유 형식 블록 추가와 이전 `다음`
  해결, 새 `다음` 생성을 한 번에 수행하는 `append` 명령 -> 실제 반복 patch 전체를
  줄이고 부분 진행과 전체 완료를 구분하기 위해 범위를 확장했다.

  기록한다.
- `--next "<행동>"`은 새 블록 끝에 `- [ ] 다음: <행동>`을 추가한다. 새 next를
  추가하면서 기존 미완료 next가 있으면 `--complete-next` 또는 `--revise-next` 중
  하나를 요구해 죽은 체크박스 누적을 막는다.
- 이전 next가 없거나 상태 변경 없이 조사 기록만 추가할 때는 resolve 옵션과
  `--next` 없이 append할 수 있다. resolve 옵션 둘은 상호 배타적이다.
- 대상은 frontmatter가 있고 `status: open`인 로그 파일이어야 한다. resolve 대상이
  없거나 옵션이 모순되거나 stdin 본문을 읽지 못하면 원본을 바꾸지 않고 실패한다.
- 파일 변경은 임시 파일에서 완성한 뒤 교체해 원자적으로 처리한다. fenced code
  판정은 기존 구조 검사 로직을 재사용한다.
- script는 완료·부분 완료 여부, 본문 내용과 새 next의 적절성을 판단하지 않는다.
  agent가 mode와 내용을 결정하고 script는 형식·위치·원자적 변경만 담당한다.
- 구현 범위는 bundled script의 usage·dispatch·append 구현, log skill의 명령 목록과
  append 사용 계약, 성공·실패 회귀 테스트다. root `AGENTS.md`, `logs/AGENTS.md`,
  taxonomy 문서와 기존 로그 본문은 수정하지 않는다.
- token 절약은 기존 줄과 patch context를 다시 전송하는 비용을 줄이는 수준이다. 새
  블록의 의미 있는 본문은 계속 agent가 작성해야 하므로 본문 자체 token은 줄지 않는다.
