# 작업 기록 Workflow

작업 기록의 최상위 운영 규칙은 `AGENTS.md`, 로그 형식과 판단 절차는 log skill,
결정적인 파일 조작은 `scripts/log`가 소유한다. 이 문서는 사용자가 어떤 요청을 하면
agent가 어떻게 행동하는지와 실제 작업 흐름을 설명한다.

책임 문서는 각 범위의 현재 권위지만 명시적 사용자 검토와 승인으로 변경할 수 있다.
중요한 구현 전에 agent는 현재 계약, 미결 결정, 현실적인 선택지와 영향, 권고를 설명한다.
가설을 조용히 계약으로 승격하거나 구현 편의를 위해 계약을 임의 변경하지 않는다.

## 세 계층

작업 기록 workflow는 세 계층으로 나뉜다.

1. **사용자 요청과 log skill**
   - 자연어 요청의 의도를 해석한다.
   - 기록할 범위와 주제, 기존 로그 추가 또는 새 로그 생성을 판단한다.
   - 점검 결과의 의미는 agent가 후속 기록과 대조해 판단한다.
2. **`scripts/log`**
   - `new`, `search`, `audit`, `set-status` 같은 결정적인 조작만 수행한다.
   - 로그 내용의 의미를 판단하거나 본문을 자동 수정하지 않는다.
3. **`scripts/onramp`**
   - 세션 시작 시 open 로그와 활성 plan을 얇게 보여준다.
   - 현재 작업을 선택하거나 본문 상태를 재구성하지 않는다.

## `$log` 요청은 무엇인가

`$log`는 엄격한 CLI 문법이 아니라 agent에게 log skill을 사용하라는 표시다. 뒤에 붙는
자연어가 실제 의도를 정한다. `$log 점검`과 `$log 현재 내용 기록해줘`는 같은 skill을
사용하지만 서로 다른 작업이다.

| 사용자 요청 | agent 동작 | 본문 수정 |
| --- | --- | --- |
| `$log` | open 로그 목록을 보여준다 | 없음 |
| `$log 현재 내용 기록해줘` | 마지막 기록 이후 현재 논의를 증류해 적절한 로그에 기록한다 | 있음 |
| `$log A부터 B까지 기록해줘` | 지정 구간 안에서 기록 가치가 있는 내용만 증류한다 | 있음 |
| `$log 이 로그 이어서 써줘` | 지정 로그의 최신 기록과 미완료 행동을 읽고 이어 쓴다 | 있음 |
| `$log 전에 인증 방식 어디서 정했지?` | topic과 description으로 관련 로그를 검색한다 | 없음 |
| `$log 점검` | 현재 작업 로그의 미완료 항목을 분류해 보고한다 | 없음 |
| `$log 열린 로그 전부 점검` | 사용자가 명시한 모든 open 로그를 점검한다 | 없음 |

별도 `$log 정리` 기능은 없다. 점검은 읽기와 보고에서 끝난다. 사용자가 점검 결과를
보고 구체적으로 수정하라고 지시하면 그때 `[x]`, 취소 또는 분리 규칙을 적용한다.

## 기존 방식의 문제와 현재 해결

기존 workflow에는 다음 문제가 있었다.

- `description`에 현재 단계와 첫 행동을 넣어 시간이 지나면 검색 설명이 낡았다.
- 과거 `- [ ] 다음:`이 수행된 뒤에도 닫히지 않아 현재 행동처럼 남았다.
- `다음 작업`, `현재 상태` 같은 블록 제목이 과거 기록에서도 현재처럼 보였다.
- 미완료 항목을 기계적으로 찾는 방법이 없어 긴 로그를 사람이 전부 읽어야 했다.
- 미완료가 남은 로그도 실수로 `decided`나 `superseded`로 바꿀 수 있었다.

현재 workflow는 다음처럼 해결한다.

- `description`은 로그 주제를 찾기 위한 안정적인 설명만 소유한다.
- 현재 상태와 재개 위치는 본문의 최신 기록과 미완료 행동이 소유한다.
- 직전 `다음:` 행동을 수행하면 새 블록을 쓰기 전에 `[x]`로 닫는다.
- 블록 제목은 시간이 지나도 의미가 변하지 않는 주제명을 사용한다.
- `$log 점검`은 `scripts/log audit`으로 미완료 위치를 찾고 agent가 의미를 분류한다.
- `set-status` guard는 미완료가 있으면 종료 상태 전환을 거부한다.
- 자동 hook은 현재 도입하지 않았다. 수동 점검과 종료 guard로 충분한지 먼저 사용한다.

## Agent의 판단 기준

로그를 기록하거나 재개할 때 agent는 다음 순서로 판단한다. 이 기준은 Codex와 Claude가
같은 사례를 독립 판정한 하네스로 검증했다.

1. **기록 가치**: 빼면 다음 agent가 의도, 결정, 근거, 제약, 상태나 다음 행동을
   오해하는가?
2. **범위**: 사용자가 지정한 시작점·종료점 또는 현재 논의 범위를 우선한다.
3. **주제 수명**: 별도로 재개·결정·종료해야 하는 작업인지 판단한다.
4. **대상 로그**: 같은 주제의 open 로그가 있으면 추가하고, 없으면 새 로그를 만든다.
5. **정보 변화**: 기존 의도·판단·제약·상태·다음 행동에 변화가 없으면 기록하지 않는다.
   수행한 작업·검증 결과와 사용자 승인·거부도 상태나 결정의 변화로 보며, 이 기준은
   기록할 내용의 범위를 좁히지 않는다.
6. **모호성**: 주제 경계가 불명확하면 여러 로그로 과도하게 나누지 않는다.
7. **재개 선택**: 여러 open 로그 중 현재 작업이 특정되지 않으면 사용자에게 선택을
   요청한다.
8. **종료 조건**: 책임 문서·코드·테스트 반영, 구현·검증 완료, 미완료 0을 모두
   만족해야 종료한다.

하네스는 실행 도구가 아니라 판단 기준을 맞추기 위한 일회성 비교 방식이다. agent가
`skip`, 기존 로그 `append`, 새 로그 `new`, 여러 로그 `split` 중 무엇을 선택하는지와
근거를 비교했고, 차이를 만든 일반 기준만 skill에 반영했다.

## 세션 시작과 재개

Claude와 Codex의 `SessionStart`는 같은 `scripts/onramp`를 호출한다. onramp는 다음만
보여준다.

- 모든 open 로그의 경로, topic, description
- `[>]` 단계가 있는 활성 plan과 해당 단계

이 출력은 후보 목록이지 현재 작업의 권위가 아니다. agent는 다음 순서로 재개한다.

1. 사용자 요청, 활성 plan의 현재 단계 또는 부모 로그의 분리 포인터로 대상 로그를
   정한다.
2. 대상 로그의 아래쪽 최신 기록과 모든 미완료 행동을 확인한다.
3. 가장 아래의 유효한 `- [ ] 다음:`에서 첫 행동을 찾는다.
4. 여러 후보가 남으면 임의 선택하지 않고 사용자에게 묻는다.
5. 작업 전 현재 할 일과 읽을 범위를 짧게 보고한다.

`description`은 현재 단계나 첫 행동이 아니다. 로그를 열기 전에 관련 로그인지
판별하는 검색 index다.

## 작은 작업

로그 하나의 체크리스트로 다음 행동을 알 수 있으면 plan을 만들지 않는다.

```markdown
---
topic: 로그인 기능 구현
description: 로그인 화면과 서버 인증 흐름을 구현하고 검증한다
status: open
---

## 2026-06-11 · 실패 경로 검증

- [x] 화면과 서버 연결
- [ ] 다음: 잘못된 비밀번호와 만료 세션을 테스트한다.
```

다음 세션에서 테스트를 수행했다면 직전 항목을 닫고 새 블록을 쓴다.

```markdown
- [x] 다음: 잘못된 비밀번호와 만료 세션을 테스트한다.

## 2026-06-12 · 인증 오류 처리

- 잘못된 비밀번호와 만료 세션 테스트가 통과했다.
- [ ] 다음: 성공 경로 회귀 테스트를 실행한다.
```

## 현재 논의를 기록

사용자 요청:

```text
$log 현재 내용 기록해줘
```

agent는 마지막 기록 이후 현재 논의에서 기록 가치가 있는 내용만 추린다. 같은 주제의
open 로그가 명확하면 바로 추가한다. 단순 반복이나 설명만 있었다면 기록하지 않는다.

새 로그가 필요하거나 여러 주제로 나뉘거나 대상이 불명확하면 다음처럼 대상을 먼저
짧게 알리고 시행한다.

```text
현재 논의는 인증 정책과 배포 절차라는 두 작업 수명으로 나뉩니다.
인증 정책은 기존 로그에 추가하고 배포 절차는 새 로그로 기록합니다.
```

## 지정 범위를 기록

사용자는 시작점과 종료점을 자연어로 지정할 수 있다.

```text
$log 내가 "세션 만료"를 물어본 부분부터 현재까지 기록해줘
$log "JWT 제안"부터 "세션으로 결정"한 부분까지 기록해줘
```

agent는 지정 범위 밖의 대화를 포함하지 않고, 범위 안에서도 반복 설명과 단순 확인은
생략한다. 범위 안에 여러 독립 작업이 있으면 주제 수명별로 분류한다.

## 독립 질문을 분리하고 다음 세션에 재개

현재 작업과 별도로 재개·결정·종료해야 하는 질문만 새 로그로 분리한다.

부모 로그:

```markdown
- [ ] 다음: `logs/2026-06-11-인증-방식.md`의 결정을 확인한 뒤 서버 연결을 재개한다.
```

분리 로그는 부모를 읽지 않아도 이해할 수 있게 작성한다. 다음 세션에는 부모 포인터가
분리 로그를 재개 대상으로 특정한다. 분리 로그를 완료하고 부모로 돌아오면 포인터를
`[x]`로 닫고 후속 행동을 기록한다.

독립적으로 보류한 open 로그는 부모 포인터가 없다. onramp에 후보로 표시될 뿐 현재
작업으로 자동 선택되지 않는다. 사용자의 요청이나 plan 단계로 특정되지 않으면 agent가
어떤 작업을 재개할지 묻는다.

## 큰 작업과 plan

독립된 큰 단계 여러 개의 순서를 별도로 관리해야 할 때만 얇은 plan을 만든다.

```markdown
# 문서 정리

- [x] 분류 -> `logs/2026-06-09-문서-분류.md`
- [>] 점검 -> `logs/2026-06-10-문서-점검.md`
- [ ] 이동
- [ ] 삭제
```

plan은 단계 순서, 상태와 단계 로그 포인터만 소유한다. 토론, 상세 체크리스트, 검증
결과와 재개 context는 현재 단계 로그가 소유한다.

## 로그 점검

사용자 요청:

```text
$log 점검
```

현재 작업이 하나로 특정되면 agent는 다음을 수행한다.

1. `scripts/log audit <파일>`로 fenced code 밖의 실제 `- [ ]` 위치를 찾는다.
2. 각 항목 뒤의 후속 기록을 읽는다.
3. `완료가 명백함`, `계속 유효함`, `판단 필요`로 분류한다.
4. 근거와 수정 제안을 보고한다.
5. 로그 본문은 수정하지 않는다.

여러 로그 중 대상이 불명확하면 후보와 재개 지점을 보여주고 사용자가 선택하게 한다.
모든 open 로그를 점검하려면 사용자가 `$log 열린 로그 전부 점검`처럼 범위를 명시한다.

점검 보고 뒤 사용자가 수정하라고 승인하면 다음 규칙을 적용한다.

- 수행 완료가 후속 기록으로 명백함: `[x]`
- 결정 변경으로 행동이 무효가 됨: 체크박스를 제거하고 `취소:`와 이유 기록
- 후속 질문을 다른 로그로 분리함: 원래 로그의 `다음:`에 분리 로그 경로와
  결정 확인 뒤 현재 작업을 재개할 행동을 기록
- 여전히 필요한 행동: 그대로 유지
- 의미가 불명확함: 사용자 판단 전까지 수정하지 않음

## 로그 종료

다음을 모두 만족할 때만 `decided`로 닫는다.

- 결정이 책임 문서, 코드 또는 테스트에 반영됨
- 필요한 구현과 검증이 끝남
- 미결 질문과 미완료 체크박스가 없음

여기서 "필요한 구현과 검증"은 해당 로그가 소유한 작업 범위를 뜻한다. 조사·질의응답
로그가 결론과 향후 구현 요구를 책임 문서에 반영해 수명을 마쳤다면, 미래 구현 자체를 그
로그에서 완료할 필요는 없다. 대신 구현을 완료한 것처럼 표시하지 않고, 남은 요구의 현재
owner와 수행 시점을 본문에 명시한 뒤 기존 체크박스를 이관 또는 취소로 정리한다. 미래
구현을 실제로 시작할 때는 당시 책임 문서를 기준으로 별도 작업 로그나 plan을 만든다.

```sh
scripts/log set-status logs/2026-06-11-로그인-기능.md decided
```

`set-status`는 `audit`과 같은 검사를 사용한다. 미완료가 하나라도 있으면 위치를
출력하고 exit code 1로 거부한다. 항목이 실제로 죽었는지는 판단하지 않으므로 먼저
agent와 사용자가 완료·취소·분리를 결정해야 한다. `open` 전환은 항상 허용한다.

단순 중단이나 보류는 `open`으로 유지한다. 같은 로그의 결정이 바뀌면 새 블록에
`Revised: 이전 -> 현재 -> 이유`를 남긴다. 종료된 로그 전체를 새 로그가 대체할 때만
이전 로그를 `superseded`로 바꾼다.
