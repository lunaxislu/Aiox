# Claude Channel Registration & Trust Model

이 문서는 Step 11에서 구현되는 Claude Code adapter의 채널 등록 메커니즘과 토큰 기반 신뢰 모델에 대해 설명한다.

## 1. 아키텍처 배경

Claude CLI는 외부의 직접적인 제어를 허용하지 않는 폐쇄형 구조를 가진다. 따라서 `aiox daemon`이 Claude에게 메시지를 보내기 위해서는 Claude가 실행한 **MCP Channel Server**가 데몬을 찾아와 자신의 위치(Endpoint)를 알리는 **등록 모델(Registration Model)**이 필요하다.

## 2. 보안 핸드쉐이크 (Token-based Handshake)

임의의 프로세스가 데몬에 채널로 등록되는 것을 방지하기 위해, 일회용 입장권인 **Token**을 이용한 핸드쉐이크 과정을 거친다.

### 텍스트 플로우: 등록 및 인증 과정

```text
[ aiox CLI (Launcher) ]       [ aiox Daemon (Controller) ]       [ Claude MCP Channel ]
      |                             |                                  |
      | 1. "alpha"용 입장권 요청      |                                  |
      |---------------------------->|                                  |
      |                             | 2. One-time Token 생성 (UUID)     |
      |                             |    (장부에 "alpha" 예약어로 기록)    |
      |                             |                                  |
      |<----------------------------|                                  |
      |    발급된 Token 수령         |                                  |
      |                             |                                  |
      | 3. Claude 실행 + Token 주입  |                                  |
      |===============================================================>|
      |    (파일 또는 환경변수 경유)    |                                  | (Channel Server 기동)
      |                             |                                  |
      |                             | 4. 등록 요청 (register)           |
      |                             |    - 요원 이름: "alpha"           |
      |                             |    - 통신 주소: "http://..."      |
      |                             |    - 보안 티켓: "UUID-TOKEN" <----+ (전달받은 토큰 제출)
      |                             |<---------------------------------|
      |                             |                                  |
      |                             | 5. 토큰 검증 (Trust Verification)|
      |                             |    - 일치하면 엔드포인트 저장       |
      |                             |--------------------------------->|
      |                             |          "인증 성공 / 등록 완료"     |
      |                             |                                  |
      |                             | 6. 실제 메시지 푸시 (Push)        |
      |                             |--------------------------------->|
      |                             |    (저장된 주소로 메시지 전송)      |
```

## 3. 핵심 구성 요소

### Token (One-time Ticket)
*   **형식:** UUID (v4)
*   **성격:** Step 10의 `thread_id`가 대화방 ID라면, Token은 **보안 입장권**이다.
*   **용도:** 채널 서버의 정체성(Identity)을 증명하고, 데몬과의 신뢰 관계를 1회성으로 수립한다.

### Endpoint Discovery
*   Claude 채널 서버는 기동 시 사용 가능한 포트를 동적으로 점유한다.
*   이 동적 주소는 **Registration** 과정을 통해서만 데몬에게 전달되므로, 데몬은 주소를 미리 알 수 없다.

## 4. 설계 결정 및 제약 (D2: Ownership Boundary)

*   **소유권(Ownership):** 데몬은 채널 서버를 직접 관리(spawn/kill)하지 않는다. 대신 **"유효한 토큰으로 등록된 엔드포인트"**만을 논리적 경계로 관리한다.
*   **토큰 전달 경로:** Claude CLI의 환경변수 차단 특성으로 인해, 토큰은 파일 시스템(One-time Ticket File)이나 `.mcp.json` 수정을 통해 전달되어야 한다. (현재 Spike R에서 검증 중)
*   **저장 방식:** 엔드포인트 정보는 휘발성(Memory-only)이다. Claude 세션이 종료되면 해당 주소는 더 이상 유효하지 않으므로 DB에 영구 저장하지 않는다.

## 5. 보안의 필요성

토큰 기반 인증이 없다면 다음과 같은 보안 사고가 발생할 수 있다.
1.  **Identity Theft:** 악의적인 로컬 프로세스가 "나는 alpha다"라고 주장하며 데몬에 주소를 등록.
2.  **Data Leakage:** 데몬은 가짜 주소를 믿고 사용자의 민감한 AI 메시지를 공격자에게 전송.

따라서 입장권(Token) 검증은 분산된 채널 모델에서 **시스템의 무결성을 지키는 핵심 장치**이다.
