# 로그 선택과 수명 계약

이 문서는 로그 선택·재개·분리·점검·반영·종료 또는 도구 변경을 다룰 때 읽는다.

## 목차

- 상태 의미
- 기록 범위와 주제 경계
- 로그 선택과 생성
- 재개
- 별도 로그 분리
- 지연 cross-log 정합화
- 점검
- 권위 있는 결과 반영
- 종료와 대체
- 형식과 도구 변경

## 상태 의미

- `open`: 질문이나 작업이 남아 있다. 여러 open 로그와 보류된 로그를 허용하며 현재
  선택된 작업이라는 뜻이 아니다.
- `decided`: 결정 반영, 필요한 작업과 검증 완료, 남은 일 없음이 모두 충족됐다.
- `superseded`: 다른 로그가 이 로그 전체의 작업 수명을 대체했다.

현재 단계와 handoff는 status가 아니라 본문의 최신 기록과 Work Items에서, 재개 위치는
미완료 Resume Pointer에서 찾는다.

## 기록 범위와 주제 경계

사용자가 기록 범위를 지정하면 우선한다. 시작점부터 현재까지, 특정 논의, 직전 제안이나
답변처럼 지칭할 수 있다. `현재 내용`은 현재 논의의 마지막 기록 이후부터 지금까지를
기본으로 해석한다. 범위가 모호하면 해석한 범위를 짧게 알린 뒤 진행하고 사용자가 이후
정정할 수 있게 한다.

한 주제는 독립적으로 재개하고 결정하며 종료할 수 있는 하나의 작업 수명이다. 같은
세션에서 다뤘는지나 내용의 크기가 아니라 이후 별도로 이어서 완료해야 하는지를 기준으로
경계를 정한다.

여러 내용이 있으면 기록 생략 기준을 먼저 적용하고 남은 내용을 작업 수명별로 묶는다.
서로 다른 수명인지 불명확하면 여러 로그로 나누지 않는다.

## 로그 선택과 생성

1. 프로젝트 진입 계약, 사용자 지정과 명시적 Resume Pointer를 먼저 따른다.
2. 포인터가 없으면 `search "<주제>" --status open`으로 같은 주제의 로그를 찾는다.
3. 충분히 관련 있는 로그가 있으면 이어 쓰고, 없으면 다른 로그에 억지로 합치지 않고
   `new`로 하나를 만든다.
4. 새 로그 생성, 여러 로그 분리 또는 대상이 불확실한 경우에는 기록 범위, 주제, 대상과
   근거를 짧게 알린 뒤 시행한다. 이 보고는 승인을 기다리는 단계가 아니다.

빈 로그 skill 호출에는 쓸 내용을 요구하지 않고 `search --status open` 결과를 보여준다.
과거 결정을 찾을 때는 `search "<검색어>"` 결과의 관련 파일만 읽는다. 새 결정이 과거
확정 결정과 충돌하거나 재논의될 가능성이 있을 때만 status 제한 없이 검색한다.

## 재개

`audit --resume <파일>`로 Resume 불변을 확인한 뒤, 미완료 Resume Pointer, 본문
아래쪽의 최신 기록과 Work Items를 확인한다. Resume이
가리키는 첫 행동을 찾고 의도·근거·제약을 이해할 만큼 앞선 맥락만 읽는다. 후속 기록으로
완료가 명백해도 recording-contract.md의 전이 규칙으로 원래 항목을 갱신해야 한다. 미완료
Resume이 여러 개면 자동 선택·수정하지 않고 구조 오류로 보고한다. 완료·취소·분리 여부가
불명확해도 독단으로 바꾸지 않는다.

active Resume Pointer가 Work Items 섹션과 떨어진 위치에 있어도 정상이다. 현재 작업
범위는 active Resume 하나만으로 판단하지 말고 Work Items 섹션을 함께 확인한다.

여러 open 로그가 있고 사용자 요청, 프로젝트 포인터나 명시적 Resume Pointer로
하나가 정해지지 않으면 open 상태만으로 현재 작업을 추측하지 않는다. 관련 후보와 각
Resume Pointer를 보여주고 사용자가 선택하게 한다.

## 별도 로그 분리

후속 질문은 기본적으로 같은 로그에 이어 쓴다. 별도로 재개·결정·종료해야 하거나
독립적인 검색 가치가 생겼을 때만 새 로그로 분리한다.

현재 로그에서 별도 수명의 작업을 새 로그로 분리하고 다음 재개를 그 로그로
단일화하려면, 현재 로그의 Resume Pointer가 새 로그 하나를 가리키게 한다.

```markdown
- [ ] Resume: Complete `<분리 로그 경로>`.
```

분리 로그는 자체 topic, description, Work Items와 Resume만으로 이해할 수 있어야 한다.
한 open 로그는 다른 로그 하나만 forward로 가리키고, 가리켜진 로그는 역참조하지 않는다.
두 로그 상태를 자동으로 양방향 동기화하지 않고, Resume Pointer 순환도 만들지 않는다.
가리킨 로그가 끝나도 현재 로그는 자동으로 바뀌지 않는다.

Resume 연결만으로 의존성, 소유권 이관이나 복귀 의무가 생기지 않는다. 그런 의미는
본문이나 Work Items에 명시된 경우에만 해석한다. 병렬 진행, 별도 owner, 여러 agent
분배나 나중 선택이 목적이면 새 로그를 Resume으로 잇지 않고 독립 open 로그로 둔다.

## 지연 cross-log 정합화

현재 작업이 다른 로그의 범위에 영향을 줬는지 찾기 위한 역방향 검색이나
owner·workstream 키워드 검색은 하지 않는다. 로그는 권위 있는 결과물이 아니므로 모든
open 로그를 작업 시점마다 동기화하지 않는다. 정합화는 명시적으로 연결된 로그이거나,
그 로그를 다시 소비하는 agent가 행동의 대상을 식별할 수 있을 때 일어난다. 연결도 없고
대상도 식별할 수 없는 cross-log drift는 탐지하지 않으며, owner가 정확한 한 stale 상태를
오류로 보지 않는다.

현재 작업 문맥에서 경로를 이미 알고 있는 로그는 필요한 경우 바로 갱신할 수 있다.
여기에 해당하는 경로는 사용자 지정, 프로젝트 진입 포인터, 현재 Resume Pointer와 현재
기록에 직접 명시된 로그뿐이다. 새 관련 로그를 발굴하기 위한 `search`는 하지 않는다.

로그 A가 Resume으로 로그 B를 가리키는 경우 B는 A를 역참조하지 않는다. B만 재개한
agent는 A를 찾거나 수정하지 않고 B만 기록한다. 나중에 A를 재개한 agent가 Resume의 B
경로를 열어 결과를 확인하고 다음처럼 처리한다.

- B가 아직 open이면 B의 Resume을 따라간다.
- B의 작업이 끝났으면 A의 기존 Resume을 해소한다. A의 작업이 계속 남아 있고 현재 흐름이
  B에서 분리됐거나 이어지는 다른 open 로그 C로 계속되면 A의 Resume을 C로 재배선한다.
  A의 남은 작업이 C와 무관하면 A 자신의 다음 행동으로 갱신하고 C는 독립 open으로 둔다.
  A의 작업 수명도 끝났으면 A를 닫는다.
- B의 결과가 A의 범위를 일부만 수행했으면 A에 실제 결과와 남은 범위만 기록한다.

재배선할 때는 그것이 단순 흐름 정리인지, 의존성이나 복귀 범위 변경인지 본문에 기록한다.
onramp은 닫힌 B를 자동 우회하지 않는다.

명시적 링크가 없어도, Resume이나 Work Item을 수행하기 전에 그 행동의 대상
파일·코드·문서가 명확하면 현재 상태를 먼저 확인한다. 이는 별도 cross-log 탐색이 아니라
원래 작업에 필요한 확인이며 다음처럼 처리한다.

- 대상이 의도대로 이미 반영됐으면 재수행하지 않고 항목을 완료하거나 남은 범위로
  축소한다.
- 대상이 다른 방향으로 바뀌어 있으면 조용히 재수행하거나 수용하지 않고 결정 충돌로
  보고한다.
- 아직 반영되지 않았으면 그대로 수행한다.

현재 문맥에서 A와 B를 모두 알고 있어 즉시 정합화하는 경우에는 같은 절차를 그 시점에
수행할 수 있다. 그렇지 않으면 그 로그가 다시 소비될 때까지 오래된 상태로 남는 것을
허용한다. 토론과 근거 전체를 로그 사이에 복사하지 않는다.

## 점검

사용자가 로그 점검, 특정 로그 점검 또는 열린 로그 전체 점검을 요청하면 다음 순서를
따른다.

1. 사용자 요청, 프로젝트 포인터 또는 Resume Pointer로 대상을 정한다.
2. 대상이 하나로 정해지지 않으면 후보와 Resume Pointer를 보여주고 선택을 요청한다.
   사용자가 전체 open 로그를 명시한 경우에만 모두 점검한다.
3. `audit <파일> [파일...]`로 구조적 미완료 항목을 찾는다.
4. 각 항목을 같은 로그의 후속 기록과 대조한다.
5. `완료가 명백함`, `계속 유효함`, `판단 필요`로 분류하고 근거를 보고한다.
6. 점검 중에는 완료·취소·분리를 적용하거나 로그를 수정하지 않는다.

별도 로그 정리 동작은 만들지 않는다. audit은 의미를 판정하거나 대상을 임의로 고르지
않는다.

## 권위 있는 결과 반영

확정된 결론이나 영구 규칙으로 프로젝트의 권위 있는 결과를 바꿔야 하면 다음 순서를
따른다.

1. agent가 반영 후보와 이유를 보고한다.
2. 사용자가 책임과 위치를 리뷰하고 승인한다.
3. 승인 후 지정된 문서, agent 계약, 코드, 테스트 또는 다른 결과물을 수정하고 검증한다.
4. 로그에는 사전 반영 예정 위치를 권위처럼 기록하지 않는다.
5. 실제 반영 후 변경 경로와 검증 결과를 수행 사실로 기록할 수 있다.

반영 위치가 미정이면 Resume도 위치를 선결정하지 않는다.

```markdown
- [ ] Resume: Report candidate owners for this conclusion and request user review.
```

권위 있는 결과에서 로그를 역참조하도록 강제하지 않는다. 반영 관계용 frontmatter나
`source`, `related`, `distill_to` 필드를 추가하지 않는다.

## 종료와 대체

다음을 모두 만족할 때만 `set-status <파일> decided`를 실행한다.

1. 결정이 본문에 기록됐다.
2. 권위 있는 결과를 바꿔야 하는 결정은 승인된 위치에 반영됐다.
3. 필요한 구현과 검증이 끝났다.
4. 미결 질문과 미완료 체크박스가 없다.

단순 중단이나 보류는 open으로 유지한다. 별도 최종 결과 섹션을 강제하지 않는다. 같은
로그의 결정이 작업 중 바뀌면 open을 유지하고 이전 결정, 새 결정과 변경 이유를 남긴다.

로그의 자체 작업 수명이 끝났으면 다음에 시작할 새 작업을 Resume으로 달아 open을
연장하지 않는다. 남은 일이 없으면 Resume을 해소하고 decided로 닫으며, 새 작업은 독립
로그로 시작한다.

조사나 질의응답 로그가 결론과 후속 구현 요구를 적절한 owner에 반영해 그 주제의 작업
수명을 끝냈다면, 미래 구현 자체를 같은 로그에서 완료할 필요는 없다. 구현을 완료한
것처럼 표시하지 말고, 남은 요구를 명시적으로 이관하거나 정리한 뒤 닫는다. 이관할 때는
기본적으로 `Transferred:` 마커를 사용하고 무엇이 어디로 왜 이관되는지 기록한다.

새 로그가 기존 로그 전체를 대체할 때만 이전 로그를 superseded로 바꾼다. 이전 로그에는
새 로그 경로, 대체 이유와 기존 미완료 범위의 이관 사실을 명확히 남긴다. 이관은 기본적으로
`Transferred:` 마커로 표시하되, 무엇이 어디로 왜 이관되는지가 드러나면 되고 고정 형식은
요구하지 않는다.

이 드문 흐름에서 기존 Resume은 append의 취소 mode로 해소한다. 기존 Work Items는 append가
구조적으로 전이하지 않으므로, agent가 의미를 판단한 뒤 일반 편집으로 활성 `[ ]`를 완료
표시나 일반 기록으로 바꾼다(이력은 지우지 않는다). 변경 후 `audit`으로 활성 미완료가
없음을 확인하고, 새 로그에 현재 유효한 Work Items와 Resume을 작성한 뒤 이전 status를
변경한다.

decided와 superseded 로그는 결정 과정과 근거를 추적하는 기록이므로 삭제하지 않는다.
필요할 때 search로 찾는다.

## 형식과 도구 변경

- 사용자 결정 없이 frontmatter 필드나 명령을 추가하지 않는다.
- 한 사례 때문에 skill이나 script를 바꾸지 않는다.
- 현재 본문 형식으로 처리하기 어려우면 임의 변경 전에 문제와 이유를 보고한다.
- 기존 로그 확인이 필요하면 검색 범위와 context 비용을 검토하고 관련 로그만 좁게 읽는다.
- 본문으로 처리할 수 없고 여러 로그에 적용되는 일반 문제라면 프로젝트가 지정한 작업
  기록 위치에 문제, 일반성 근거와 선택지를 남긴다. 지정 위치가 없으면 사용자에게
  보고하고 변경 여부를 결정하게 한다.

판단 기준:

1. 현재 본문으로 처리할 수 있는가?
2. 이번 사례만의 문제인가, 여러 로그에 적용되는 일반 문제인가?
3. 형식이나 도구 변경을 사용자가 결정했는가?
