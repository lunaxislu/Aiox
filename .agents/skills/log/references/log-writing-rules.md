# 로그 작성 규칙

이 문서는 로그 생성, 날짜별 기록 블록 작성, 기록 품질, 생략 기준, 외부 출처, status
전환을 다룬다. Work Items와 pointer 전이는 `work-items-rules.md`가 소유한다.

## 기록 기본

기록은 형식보다 의미 복원을 우선한다. 다음 질문에 답할 수 있어야 한다.

- 무엇이 결정, 변경, 완료, 취소, 이관됐는가?
- 왜 그렇게 판단했는가?
- 현재 유효한 다음 행동은 무엇인가? 없다면 왜 없는가?
- 어떤 파일, 로그, owner 문서, 검증 결과나 외부 출처가 판단에 영향을 줬는가?
- 이전 기록과 달라진 점이 있다면 무엇이 대체됐고 무엇이 아직 남았는가?

기록 여부는 "이 내용을 빼면 다음 agent가 의도, 판단, 근거, 제약, 현재 상태 또는 남은
일을 잘못 이해할 가능성이 있는가?"로 판단한다. 애매하면 결정, 근거, 제약과 미결 사항은
남긴다.

## 기록할 내용

- 사용자의 의도, 질문, 제약, 피드백, 승인과 거부
- agent의 제안, 선택지, 판단과 근거
- 반대 근거, 동의되지 않은 의견과 보류 이유
- 결정과 결정이 변경된 이유
- 수행한 작업과 검증 결과
- 남은 질문, Work Items와 next pointer
- 판단이나 후속 확인에 사용한 외부 출처
- 외부 자료에서 확인한 사실과 그 사실이 판단에 미친 영향

수행 결과, 검증 결과, 사용자 승인·거부, 우선순위 변경은 의미 변화로 본다. 기존 로그에
이미 있는 내용을 반복했을 뿐 의도, 판단, 제약, 현재 상태 또는 next pointer가 달라지지
않았다면 추가하지 않는다.

## 기록 품질

좋은 로그는 정확할 뿐 아니라 전달력, 목적성, 접근성을 갖춰야 한다.

- 전달력: 다음 agent가 결정, 근거, 현재 상태, 남은 일을 빠르게 이해할 수 있게 쓴다.
- 목적성: 재개, 판단, 검증, 반영에 필요한 내용만 남기고 대화 덤프나 설명용 반복을 피한다.
- 접근성: 제목, bullet, 화자 표시, 경로, Work Item id를 사용해 필요한 정보를 쉽게 찾게 한다.
- 시간 안정성: 시제, 접속사, 논리 관계가 시간이 지나도 의미가 유지되게 쓰고, 완료 사실,
  취소 이유, 보류 조건, 다음 행동을 구분한다.

## 로그 블록

- 블록은 `## YYYY-MM-DD · <주제>` heading 아래 시간순으로 둔다.
- 한 블록에는 서로 관련된 질문, 조사나 작업 한 묶음만 둔다.
- 사실, 관찰, 판단은 일반 bullet로 쓰면 읽기 쉽다.
- 발언 주체를 구분해야 의미가 명확해질 때 `@user`, `@codex`, `@claude`, `@gemini`처럼
  실제 화자를 쓸 수 있다. 토론 없이 수행 결과만 기록하면 화자 표시는 생략한다.
- 결정이 바뀌면 이전 결정, 새 결정과 변경 이유를 반드시 기록한다.

질문과 답변마다 즉시 기록하지 않는다. 결정·제약 확정, 의미 있는 조사 결과, 작업·검증
완료, 주제 전환이나 중단처럼 의미 변화가 확정되는 checkpoint에서 한 블록으로 증류한다.

## 생략할 내용

- 반복 질문과 같은 의미의 답변
- 단순 확인이나 진행 발언
- 사용자 이해만을 위한 설명과 예시
- 판단에 영향을 주지 않은 검색 과정과 실패한 검색어
- 외부 자료의 긴 원문
- 이미 기록된 배경의 반복
- 대화 전체의 원문 덤프

설명이나 예시를 통해 조건이 새로 확정됐다면 예시는 버리고 확정된 조건만 기록한다.

## 외부 출처

프로젝트의 권위 있는 문서, 외부 문서나 링크를 판단 근거로 사용했다면 결론의 근거가 된
경로나 URL, 확인한 사실, 그 사실이 판단에 미친 영향을 함께 기록한다. 판단에 사용하지
않은 검색 링크는 남기지 않고 원문을 길게 옮기지 않는다.

## Frontmatter

frontmatter는 구조 소비자가 읽는 최소 index다. 다음 세 필드만 사용한다.

- `topic`: 로그의 짧은 제목
- `description`: 본문을 열지 않고 필요한 로그인지 판별하는 안정적인 설명
- `status`: 로그의 수명인 `open`, `decided`, `superseded`

`description`에는 현재 단계, handoff, next pointer를 넣지 않는다. 현재 진행 상태는 본문의
최신 기록과 Work Items가 소유한다.

## 로그 선택

사용자가 지정한 로그나 주제가 있으면 우선한다. 프로젝트 진입 계약이 현재 로그를 지정하면
그 로그의 Work Items, next pointer, 최신 기록을 읽는다.

대상이 정해지지 않았을 때는 관련 open 로그 후보를 찾는다. 후보가 하나로 정해지지 않으면
`open` 상태만으로 현재 작업을 추측하지 않고 후보와 각 next pointer를 보여준 뒤 사용자가
선택하게 한다.

## 로그 생성

새 로그는 하나의 문제, 질문, 조사, 구현 흐름을 별도로 재개하고 결론이나 상태를 정리해야
할 때 만든다. 같은 세션에서 다뤘는지나 내용의 크기가 아니라 이후 별도로 이어서 다루고
마무리할 수 있는지를 기준으로 경계를 정한다. 서로 다른 수명인지 불명확하면 여러 로그로
나누지 않는다.

Work Item이 필요한 로그:

```markdown
---
topic: <짧은 제목>
description: <안정적인 index 설명>
status: open
---

## Work Items

- [>] W1 <첫 행동>

## YYYY-MM-DD · <첫 기록 주제>
```

Work Items가 없는 조사나 토론 로그:

```markdown
---
topic: <짧은 제목>
description: <안정적인 index 설명>
status: open
---

## Work Items

## YYYY-MM-DD · <첫 기록 주제>

- 질문:
- 판단 범위:
- 종료 판단 기준:
```

Work Items가 없는 로그는 첫 블록에 질문, 판단 범위, parent pointer가 있다면 복귀할 위치,
종료 판단 기준을 명확히 남긴다.

## 권위 있는 결과 반영

확정된 결론이나 영구 규칙으로 프로젝트의 권위 있는 결과를 바꿔야 하면 다음 순서를 따른다.

1. agent가 반영 후보와 이유를 보고한다.
2. 사용자가 책임과 위치를 리뷰하고 승인한다.
3. 승인 후 지정된 문서, agent 계약, 코드, 테스트 또는 다른 결과물을 수정하고 검증한다.
4. 로그에는 사전 반영 예정 위치를 권위처럼 기록하지 않는다.
5. 실제 반영 후 변경 경로와 검증 결과를 수행 사실로 기록할 수 있다.

반영 위치가 미정이면 next pointer도 위치를 선결정하지 않는다. 권위 있는 결과에서 로그를
역참조하도록 강제하지 않는다. 반영 관계용 frontmatter나 `source`, `related`,
`distill_to` 필드를 추가하지 않는다.

## Status guide

- `open`: 질문이나 작업이 남아 있다. 여러 open 로그를 허용하며 현재 선택된 작업이라는
  뜻이 아니다.
- `decided`: 결정 반영, 필요한 작업과 검증 완료, 남은 일 없음이 모두 충족됐다.
- `superseded`: 다른 로그가 이 로그 전체의 작업 수명을 대체했다.

## Status 전환과 종료 점검

작업이 끝났거나 세션을 마치기 전에는 status 전환 후보인지 점검한다.

- 현재 Work Item의 전이가 필요한가?
- `[>]` next pointer는 하나이며 현재 재개 지점을 가리키는가?
- 완료, 취소, 이관한 항목의 이유와 결과가 본문에 남았는가?
- known graph 안의 parent/child pointer를 소비해야 하는가?
- Work Items가 없는 조사·토론 로그라면 답·결론, known parent 반영, 남은 질문이 정리됐는가?
  정리됐으면 Decided 절의 hard rule에 따라 `decided`로 전환한다.
- 권위 있는 결과 반영이나 검증이 남았는가?
- 로그 전체가 `decided` 또는 `superseded` 후보인가?

## Decided

`decided`는 이 로그의 질문, 조사, 작업 수명이 끝났다는 뜻이다. 다음을 모두 만족할 때만
`decided`로 바꾼다.

1. 결정이나 결과가 본문에 기록됐다.
2. 권위 있는 결과를 바꿔야 하는 결정은 승인된 위치에 반영됐다.
3. 필요한 구현과 검증이 끝났다.
4. 미결 질문과 미완료 체크박스가 없다.
5. known graph 안의 parent/child 복귀가 필요한 경우 처리됐다.

다섯 조건이 모두 충족됐으면 `decided` 후보로만 두지 말고 `decided`로 전환한다. Work Items가
있다는 이유만으로 완료된 로그를 `open`에 남기지 않는다.

`decided`로 바꿀 때는 마지막 기록 블록에 최소한 다음을 남긴다.

- 최종 결정이나 결과
- 반영한 위치와 검증 결과, 또는 반영이 필요 없는 이유
- 남은 일이 없다는 판단 근거
- parent/child pointer를 소비했다면 parent에 반영한 내용

Work Items가 없는 조사·토론 로그는 다음을 모두 만족하면 `decided` 후보로만 두지 말고
`decided`로 전환한다. 이는 위 Decided 조건을 구현·검증이 없는 로그에 구체화한 것이지
완화한 것이 아니다.

1. 로그가 시작한 질문에 답이나 결론이 났다.
2. 남은 질문이 없다.
3. 필요한 반영이 끝났다. known graph 안에 parent pointer가 있으면 그 parent에 결과를
   반영하고(체크·이관·다음 행동 포함), 결론이 권위 있는 결과를 바꿔야 하면 승인된 위치
   반영까지 끝낸다. 반영 대상이 없으면 충족된 것으로 본다.

세 조건이 충족됐는데도 "아직 후보"라며 `open`으로 남기거나 "중단"으로 재라벨하지 않는다.
답이 안 났거나 남은 질문이 있으면 그 미결이 곧 다음 행동이며, 그때만 `open`으로 유지한다.
로그의 자체 작업 수명이 끝났으면 새 작업을 next pointer로 달아 open을 연장하지 말고 독립
로그로 시작한다.

## Superseded

새 로그가 기존 로그 전체를 대체할 때만 이전 로그를 `superseded`로 바꾼다. 로그가 스스로
질문에 답하고 결론을 내 끝나는 것은 `decided`이며 `superseded`가 아니다. `superseded`는
다른 로그가 이 로그의 범위를 통째로 이어받아 더 이상 이 로그에서 재개하지 않을 때만
쓴다. 이전 로그에는 새 로그 경로, 대체 이유, 기존 미완료 범위의 이관 사실을 남긴다. 대체
후에도 결정 과정과 근거를 추적해야 하므로 로그를 삭제하지 않는다.

`superseded`로 바꿀 때는 마지막 기록 블록에 최소한 다음을 남긴다.

- 대체 로그 경로
- 대체 이유
- 기존 미완료 Work Items를 각각 어떻게 처리했는지
- 기존 next pointer를 어떻게 해소했는지
- 기존 로그에서 더 이상 재개하지 않아야 하는 이유

`superseded`로 바꾸기 전에 기존 미완료 Work Items와 next pointer를 모두 해소한다.

1. 기존 미완료 Work Item마다 완료, 취소, 이관, 대체 로그로의 이전 중 무엇인지 판단한다.
2. 대체 로그가 이어받는 항목은 대체 로그에 유효한 Work Item이나 재개 지점이 있는지
   확인한다.
3. 이전 로그의 `[>]`와 `[ ]` Work Item은 더 이상 남아 있지 않게 해소한다.
4. 어떤 항목도 의미 없이 사라지지 않게 이전 로그의 마지막 기록 블록에 처리 결과를 남긴다.

```markdown
# Case 1: 새 로그가 그대로 이어받음
- [x] W2 Transferred: Review log skill examples. → logs/new-log-skill-design.md — 새 로그가 이 범위를 이어받는다

# Case 2: 새 로그가 여러 항목을 더 큰 범위로 대체함
- [x] W3 Transferred: Patch old recording contract. → logs/new-log-skill-design.md — 새 로그의 W1이 W3/W4 범위를 통합해 다시 정의한다
- [x] W4 Transferred: Patch old lifecycle notes. → logs/new-log-skill-design.md — 새 로그의 W1이 W3/W4 범위를 통합해 다시 정의한다

# Case 3: 더 이상 필요 없음
- [x] W5 Cancelled: Add temporary compatibility note. — 새 구조가 compatibility note 없이 문제를 해결한다
```
