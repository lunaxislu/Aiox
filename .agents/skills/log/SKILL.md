# 작업 로그

작업의 질문, 판단, 결정과 진행을 `logs/`에 주제별로 기록한다. 로그는 하나의
문제나 작업 주제가 끝날 때까지 이어 쓰는 메모장이며, 현재 작업 문맥과 세션 간
handoff도 본문에서 제공한다.

로그는 확정된 제품·기술 계약, 영구 운영 규칙, 상세 가이드나 여러 독립 작업의 전체
순서를 소유하지 않는다. log skill은 plan의 존재나 구조를 전제로 하지 않는다.

도구는 공용 `scripts/log`를 사용한다.

## Frontmatter

frontmatter는 다음 세 필드만 사용한다.

- `topic`: 로그의 짧은 제목.
- `description`: 본문을 열지 않고 검색 결과에서 필요한 로그인지 판별하기 위한
  안정적인 index 설명. 현재 단계나 다음 행동을 넣지 않는다.
- `status`: 로그의 수명.
  - `open`: 아직 질문이나 작업이 남아 있다. 여러 open 로그와 보류된 로그를
    허용하며, 현재 선택된 작업이라는 뜻이 아니다.
  - `decided`: 결정 반영, 필요한 작업과 검증 완료, 남은 일 없음이 모두 충족됐다.
  - `superseded`: 다른 로그가 이 로그 전체를 대체했다.

현재 진행 상태와 handoff는 frontmatter가 아니라 본문의 최신 기록과 미완료 행동에서
찾는다. `status`는 `scripts/log set-status`로만 바꾼다. `scripts/log`는 로그
생성·검색·구조 점검·상태 변경만 담당하고, `description`과 본문은 agent가 직접
편집한다.

## 본문에 남길 내용

본문은 날짜별 블록을 시간순으로 이어 쓴다. 다음 agent가 작업을 이어가는 데 필요한
의미를 증류한다.

- 사용자의 의도, 질문, 제약, 피드백, 승인과 거부
- agent의 제안, 선택지와 판단
- 판단 근거와 반대 근거
- 동의되지 않은 의견과 보류 이유
- 결정과 결정이 변경된 이유
- 수행한 작업과 검증 결과
- 남은 질문, 미완료 작업과 다음 행동
- 사용자나 agent가 제공한 외부 링크와 GitHub 저장소
- 외부 자료에서 확인한 내용과 그것이 판단에 미친 영향

외부 문서·링크를 판단이나 결정의 근거로 사용했다면, 결론의 근거가 된 출처 URL,
확인한 사실과 그 사실이 판단에 미친 영향을 함께 기록한다. 판단에 사용하지 않은
검색 링크는 기록하지 않고, 원문을 길게 옮기지 않는다.

## 생략할 내용

- 반복 질문과 같은 의미의 답변
- 단순 확인이나 진행 발언
- 사용자 이해만을 위한 설명과 예시
- 판단에 영향을 주지 않은 검색 과정과 실패한 검색어
- 외부 자료의 긴 원문
- 이미 기록된 배경의 반복

설명이나 예시로 조건이 새롭게 확정됐다면 예시는 버리고 확정된 조건만 기록한다.

기록 여부는 다음 질문으로 판단한다.

> 이 내용을 빼면 다음 agent가 의도, 판단, 근거, 제약, 현재 상태 또는 남은 일을
> 잘못 이해할 가능성이 있는가?

그렇다면 기록한다. 애매하면 결정·근거·제약·미결 사항은 남기고,
설명·단순 확인·검색 과정은 버린다.

## 본문 형식

- `## YYYY-MM-DD · <주제>` 형식의 날짜별 블록을 사용한다.
- 블록 제목의 `<주제>`는 시간이 지나도 의미가 변하지 않는 이름으로 쓴다.
  `다음`·`현재`·`최종`처럼 작성 시점에 상대적인 표현은 피한다. 본문 끝의
  `- [ ] 다음:`은 재개 행동을 표시하는 별도 형식이므로 이 제한에 해당하지 않는다.
- 한 블록에는 서로 관련된 질문, 조사나 작업 한 묶음만 둔다.
- 기본 골격은 `@user`와 실제 agent 화자 아래에 의미를 증류한 bullet을 두는
  형식이다. 자유 형식은 이 골격 안에서 고정 섹션을 강제하지 않는다는 뜻이며,
  대화 전체를 자유롭게 덤프한다는 뜻이 아니다.
- 토론 없이 수행한 작업과 검증만 기록하는 블록은 화자 없이 체크리스트와 결과만
  둘 수 있다.
- 발언 원문을 옮기지 않고 작업을 이어가는 데 필요한 의미를 bullet로 증류한다.
- 사용자의 질문, 답변, 피드백, 승인과 거부는 `@user`로 기록한다.
- agent 발언은 실제 agent에 따라 `@codex`, `@claude`, `@gemini` 등으로 기록한다.
- `@agent`, `@user-answer` 같은 공통·별도 화자 표시는 사용하지 않는다.
- 승인과 거부는 `승인:`, `거부:`처럼 행위와 범위를 분명히 쓴다.
- 사실, 관찰과 판단은 일반 bullet로 기록하고 수행할 행동에만 체크박스를 사용한다.
- 결론이 없어도 이후 판단, 선택지, 제약이나 남은 작업에 영향을 준 조사, 제안,
  관찰과 보류 질문은 기록한다. 영향을 주지 않은 탐색 과정은 생략한다.
- 모든 블록에 같은 섹션이나 `conclusion`을 강제하지 않는다.
- 작업을 멈출 때는 본문 끝에 `- [ ] 다음: ...`으로 재개할 행동을 남긴다.
- 새 블록을 이어 쓸 때 직전 `- [ ] 다음:`이 가리킨 행동을 수행했다면 새 블록을
  쓰기 전에 해당 항목을 `[x]`로 닫는다. 결정 변경으로 무효가 됐다면 기존 취소
  규칙을 따르고, 분리 로그를 처리했다면 기존 분리 절차를 따른다. 이 규칙은 직전
  행동만 대상으로 하며 새 블록마다 본문 전체를 판정하게 하지 않는다.

결정이 바뀌면 이전 기록을 지우지 않고 새 블록에
`Revised: 이전 -> 현재 -> 이유`를 남긴다.

결정이 바뀌어 무효가 된 미완료 행동은 완료로 닫지 않는다. 체크박스를 떼고 취소
사유를 붙여 재개 대상에서 제외하되, 줄은 지우지 않는다. 새 행동은 `Revised`와 새
`- [ ] 다음:`이 가리킨다.

```markdown
- 취소: <기존 행동> — <취소 이유 또는 대체 행동>
- [ ] 다음: <새 행동>
```

## 질문을 별도 로그로 분리할 때

후속 질문은 기본적으로 같은 로그에 이어 쓴다. 별도로 재개·결정·종료해야 하거나
독립적인 검색 가치가 생긴 질문만 크기가 아닌 수명과 검색 가치를 기준으로 새 로그로
분리한다.

분리할 때 원래 로그의 다음 행동은 다음처럼 기록한다.

```markdown
- [ ] 다음: <분리 로그 경로>의 결정을 확인한 뒤 현재 작업을 재개한다.
```

분리 로그는 자체 `topic`, `description`, 본문만으로 이해할 수 있어야 한다. 원래
로그를 역참조하거나 두 로그의 상태를 양방향으로 동기화하지 않는다. 분리 로그가
끝나도 원래 로그는 자동으로 바뀌지 않는다. 원래 로그를 재개할 때는 `- [ ] 다음:`에
기록된 분리 로그 경로를 직접 열어 결정과 결과를 확인하고(`--status open` 검색에
의존하지 않는다), 확인을 마치면 해당 체크박스를 완료 처리하고 후속 행동을 기록한다.

## 로그를 남길 때

사용자가 기록 범위를 지정하면 그 범위를 우선한다. 시작점부터 현재까지, 시작점부터
종료점까지, 현재 내용·현재 논의, 직전 제안·답변처럼 특정 내용을 지칭할 수 있다.
`현재 내용`은 현재 진행 중인 논의에서 마지막 기록 이후부터 지금까지를 기본으로
해석한다. 직전 답변만 가리키는 것이 명확하면 그 답변만 대상으로 한다. 범위가
모호하면 추측한 기록 대상을 짧게 알린 뒤 그 범위 안에서 기록 가치가 있는 내용만
증류한다. 사용자는 이후 정정할 수 있으며, 이 보고는 응답을 기다리는 단계가 아니다.

한 주제는 독립적으로 재개하고 결정하며 종료할 수 있는 하나의 작업 수명이다. 같은
세션에서 다뤘는지보다 이후 별도로 이어서 완료해야 하는지를 기준으로 주제 경계를
판단한다.

세션 종료 때 대화를 한꺼번에 옮기는 것을 기본으로 삼지 않는다. 결정이나 제약이
확정됐을 때, 이후 판단에 영향을 주는 조사 결과가 나왔을 때, 작업과 검증을 마쳤을
때, 다른 주제로 전환할 때, 작업을 중단하고 다음 행동을 정할 때를 기록
체크포인트로 삼는다. 각 체크포인트에서도 기록 가치가 있는 내용만 남기며, 모든
시점에 파일을 자동으로 수정하는 것은 아니다.

정해진 기록 범위에 여러 내용이 있으면 먼저 생략 기준을 적용하고, 남은 내용을 위의
작업 수명별 주제로 묶는다. 그다음 각 주제마다 같은 주제의 open 로그를 검색한다.
서로 다른 작업 수명인지 분명하지 않으면 여러 로그로 나누지 않고 하나의 주제로
묶는다. 충분히 관련 있는 기존 로그가 있으면 그 로그를 사용하고, 없으면 다른 로그에
억지로 합치지 않고 묶은 주제로 새 로그 하나를 만든다. 이 해석과 대상은 기록 전에
짧게 알리고 이후 정정할 수 있게 한다.

기존 로그에 이미 있는 내용을 다시 언급했을 뿐 의도, 판단, 제약, 현재 상태 또는
다음 행동이 달라지지 않았다면 추가하지 않는다. 이 항목 중 새 정보나 변화가 있을
때만 기존 로그에 새 블록을 이어 쓴다. 수행한 작업·검증 결과와 사용자 승인·거부도
현재 상태나 결정의 변화로 보며, 이 기준은 위의 `본문에 남길 내용` 범위를 좁히지
않는다.

1. 방금 정리된 문제나 작업 주제를 고른다. 세션 전체를 옮기지 않는다.
2. `scripts/log search "<주제>" --status open`으로 같은 주제의 열린 로그를 찾는다.
3. 의미 변화가 있고 대상 기존 로그가 명확하면 새 날짜 블록을 바로 이어 쓴다. 여러
   주제라도 각각 대상이 명확하면 로그 개수와 무관하게 바로 이어 쓴다. 새 로그 생성,
   하나의 내용을 여러 로그로 나누는 분리 또는 대상이 불확실한 경우에는 기록 범위,
   주제, `append`·`new` 대상과 근거를 짧게 알린 뒤 시행한다. 이 보고는 응답을
   기다리는 단계가 아니며 사용자는 이후 정정할 수 있다.
4. 새 로그가 필요하면 `scripts/log new "<주제>" [설명]`으로 만든다.
5. `description`은 안정적인 검색용 주제 설명으로 작성한다.
6. 본문에 필요한 문맥을 증류하고, 미완료 행동이 있으면 체크박스로 남긴다.

빈 `/log` 요청에는 쓸 내용을 요구하지 않고 열린 로그를 보여준다.

```sh
scripts/log search --status open
```

과거 결정을 찾을 때는 `scripts/log search "<검색어>"`로 검색하고 결과로 나온 관련
파일만 읽는다. 새 결정이 과거 확정 결정과 충돌하거나 재논의 소지가 있을 때만 status
필터 없이 전체를 검색해 과거 근거를 확인하고, 그 외에는 open 로그 검색으로 충분하다.

로그를 재개할 때는 본문 아래쪽의 최신 기록과 미완료 체크박스부터 확인한다. 가장
아래의 미완료 항목에서 현재 재개 지점을 찾되, 다른 미완료 항목도 함께 확인한다.
다른 미완료 항목을 확인하다 후속 기록으로 수행 완료가 명백히 확인되면 `[x]`로
닫는다. 완료·취소·분리 여부가 불명확하면 독단으로 변경하지 않고 사용자에게
보고한다. 전체 로그 스캔이나 취소·분리의 자동 의미 판정을 의무화하지 않는다.
여러 open 로그가 있고 사용자 요청, plan의 현재 단계 또는 부모 로그의 분리 로그
포인터로 재개할 로그가 하나로 정해지지 않으면 `open` 상태만으로 현재 작업을
추측하지 않는다. 관련 후보와 각 로그의 재개 지점을 짧게 보여주고 어떤 작업을
재개할지 사용자에게 확인한다.

## 로그를 점검할 때

`$log 점검`, `$log 이 로그 점검`, `$log 열린 로그 전부 점검`처럼 사용자가 점검을
요청하면 별도 skill이나 엄격한 CLI식 인자 체계를 만들지 않고 이 skill이 처리한다.

1. 사용자 요청, plan의 현재 단계 또는 부모 로그의 분리 로그 포인터로 대상 로그를
   정한다.
2. 대상이 하나로 정해지지 않으면 관련 open 로그 후보와 각 재개 지점을 보여주고
   사용자에게 선택을 요청한다. 사용자가 전체 open 로그를 명시한 경우에만 모두
   점검한다.
3. 정해진 파일을 `scripts/log audit <파일> [파일...]`로 검사한다.
4. 출력된 미완료 항목을 같은 로그의 후속 기록과 대조한다.
5. 각 항목을 `완료가 명백함`, `계속 유효함`, `판단 필요`로 분류하고 근거와 함께
   보고한다.
6. 점검 중에는 `[x]`, 취소나 분리를 적용하지 않고 로그 본문을 수정하지 않는다.

별도 `$log 정리` 동작은 만들지 않는다. 실제 수정은 점검 보고를 본 사용자의 구체적
지시와 기존 완료·취소·분리 규칙에 따라 수행한다. `scripts/log audit`은 구조적 사실만
출력하며 의미를 판정하거나 점검할 로그를 임의로 선택하지 않는다.

## 책임 문서에 반영할 때

확정된 제품·기술 계약이나 영구 규칙은 책임 있는 문서, 코드 또는 테스트에 반영한다.

1. agent가 반영 후보와 이유를 사용자에게 보고한다.
2. 사용자가 책임과 위치를 리뷰하고 승인한다.
3. 승인 후 해당 문서, 코드 또는 테스트를 수정하고 검증한다.
4. 로그에는 사전 반영 예정 위치를 권위처럼 기록하지 않는다.
5. 실제 반영 후에는 수행한 작업 사실로 변경 경로와 검증 결과를 기록할 수 있다.

반영 위치가 아직 승인되지 않았다면 다음 행동은 위치를 선결정하지 않고 기록한다.

```markdown
- [ ] 다음: 이 결론의 반영 후보를 보고하고 사용자 리뷰를 받는다.
```

위치가 이미 승인됐다면 승인된 위치에 반영하고 검증하는 행동으로 기록한다.

책임 문서에서 로그를 역참조하도록 강제하지 않는다. 반영 관계를 관리하기 위한
frontmatter나 `source`, `related`, `distill_to` 같은 필드도 추가하지 않는다.

## 로그를 닫을 때

다음을 모두 만족할 때만 `scripts/log set-status <파일> decided`를 실행한다.

1. 결정이 본문에 기록되고 필요한 책임 문서, 코드 또는 테스트에 반영됐다.
2. 필요한 구현과 검증이 끝났다.
3. 미결 질문과 미완료 체크박스가 없다.

단순 중단이나 보류는 `open`으로 유지한다. 본문에 결정 과정과 사용자 승인이 이미
있으므로 별도의 최종 결과 섹션을 강제하지 않는다.

같은 로그의 결정이 작업 중 바뀌면 `open`을 유지하고 `Revised`를 남긴다. 종료된
로그 전체를 새 로그가 대체할 때만 이전 로그를 `superseded`로 바꾼다.

새 로그가 기존 로그 전체를 대체할 때는 이전 로그에 새 로그 경로와 대체 이유를
남긴다. 이전 로그의 미완료 행동은 체크박스를 제거해 이관 사실과 새 로그 경로를
기록하고, 새 로그에 현재 유효한 미완료 행동으로 작성한다. 그 뒤 이전 로그의 status를
`scripts/log set-status <파일> superseded`로 바꾼다. 이전 로그는 이력으로 보존한다.

```markdown
- superseded by `<새 로그 경로>` — <대체 이유>
- 이관: <기존 미완료 행동> -> `<새 로그 경로>`
```

`decided` 로그는 결정 과정과 근거를 추적하는 기록이므로 삭제하지 않는다. 책임
문서는 로그를 역참조하지 않으며, 필요할 때 `scripts/log search`로 관련 로그를 찾는다.

## 도구를 늘리지 않기

- 사용자 결정 없이 frontmatter 필드나 `scripts/log` 명령을 추가하지 않는다.
- 한 번뿐인 사례 때문에 skill이나 script를 바꾸지 않는다.
- 현재 본문 형식으로 표현하기 어려운 사례를 발견하면 임의로 형식이나 도구를
  바꾸지 말고, 무엇이 맞지 않는지와 그 이유를 먼저 사용자에게 보고한다.
- 기존 로그에 같은 패턴이 있는지 확인할 필요가 있는지 판단한다. 확인이 필요하면
  검색 범위와 예상 context 비용을 먼저 검토한다.
- 좁은 검색으로 확인할 수 있으면 관련 로그만 검색한다. 많은 로그를 읽어 context를
  오염시킬 가능성이 크면 무리하게 조사하지 않고, 해당 사례를 처리할 의견과
  선택지를 사용자에게 보고한다.
- 본문으로 도저히 담을 수 없고 다른 로그에도 일반적으로 필요한 문제라면 skill이나
  script를 바로 고치지 않는다. `로그 도구 개선` open 로그에 무엇이 문제인지, 왜
  일반 문제인지와 가능한 방향을 기록하고 사용자가 변경 여부를 결정하게 한다.
- 판단 기준은 횟수가 아니라 다음 세 가지다.
  1. 현재 본문으로 처리할 수 있는가?
  2. 이번 사례만의 문제인가, 여러 로그에 적용되는 일반 문제인가?
  3. 형식이나 도구 변경을 사용자가 결정했는가?
